# Advisor · Coste, respuestas sin modelo y Mimo remoto

> Parte de [Advisor](./advisor.md) (la portada lista todas las partes): el tope de gasto por persona y mes (y lo que sigue funcionando al llegar a él), lo que contesta el código sin llamar al modelo, el examen fijo de Mimo y Mimo remoto en staging.

## Cost guardrail (per-user monthly budget)

The advisor chat (and WhatsApp) calls Claude Opus 5.5 since 2026-10-19 (Sonnet 5.5 from 2026-10-12, Haiku 4.5 before), one request per tool round, so it's metered per user. A typical turn cost about $0.02–0.03 on Sonnet 5.5 with the cache warm (the first of a conversation ~$0.07); Opus 5.5 is twice the list price, so about double [I], and the €5 default of then covered about half as many turns a month (FIN-09; €6 since 2026-11-18); revisit with Finanzas:

- **What one reply costs, by kind of turn (PRO-393).** Each turn's `cost_events` row (`assistant_chat`, `whatsapp_chat`, `telegram_chat`) carries in `units` the fresh input, cache reads, cache writes (`cacheWriteTokens`, both TTLs) and the 1-hour part of them (`cacheWrite1hTokens`, priced at `cacheWrite1hPerMTok`, 8 $/MTok on Opus 5.5; 2× input when a model has none), output, and since PRO-393 `rounds` (model calls) and `toolCalls`. `scripts/mimoTurnCost.ts` (`services/mimoTurnCost.ts`) gives the average € per reply by Madrid week and channel, by kind (no tools / one tool round / two or more / no data, before PRO-393) and by whether the turn wrote the fixed block (≥ 20 000 tokens written) or read it — this last split also works on older rows, so it gives the «before». Target: 0,10 € a reply or less.
- Every turn's real token `usage` (input / output / cache-write / cache-read) is priced at the assistant model's list rate (`ADVISOR_PRICE_MODEL`, USD), converted to euros via `ADVISOR_EUR_PER_USD` (default 0.92), and added to a per-user, per-month running total stored in `users.advisor_spend_micros` (+ `advisor_spend_month_key`).
- Before each turn the route checks the total against `ADVISOR_MONTHLY_BUDGET_EUR` (default **€6**, the production value since 2026-11-18). At or over budget → `429 ADVISOR_BUDGET_EXCEEDED`, no model call is made. What the code answers goes first and works over the cap (see «With the cap used up», PRO-1302).
- **The sign-up doesn't count** (2026-11-18): the WhatsApp sign-up turns (until `complete_onboarding`, the first menu included) go to the cost ledger but not to `advisor_spend_micros` (`recordAdvisorUsage(…, { countsTowardBudget: false })`). The web's `onboarding` mode still counts (the client picks the mode, so it can't be an exemption).
- **Notice at 80 %** (2026-11-18): the turn that takes the month's total from under 80 % of the budget to 80 % or more gets one fixed line at the end of Mimo's reply, «Te queda poco de Mimo este mes; se renueva el día 1.» (`BUDGET_WARNING_LINE`, `crossesBudgetWarning`), in the app and on WhatsApp. No state: the total only grows within a month, so it happens once. Over the cap, WhatsApp avisos whose buttons need Mimo don't go ([WhatsApp](./whatsapp.md)); the «¿hiciste la cena?» buttons are recorded without Mimo.
- The month resets implicitly: the first chat of a new month overwrites the total with that turn's cost (same stateless pattern as the image quota — no cron). A user just under the line may run one final turn, so actual spend can exceed the cap by at most one turn (~€0.01) — acceptable for a soft cap.
- Pricing math lives in `services/advisorBudget.ts` and is unit-tested; the per-MTok rates track the model in `engine.ts`. The legacy `/advisor/:userId/ask` is rule/KB-based (no model call) and is not metered.
- **Monthly cap on all paid AI work** (`USER_MONTHLY_SPEND_CAP_EUR`, default €10, Madrid month, summed from the cost ledger — [Metrics](./metrics.md)). Every route that pays a provider checks it first (`middleware/spendCap.ts` → `429 SPEND_CAP_EXCEEDED`): this chat, `POST /stt`, `POST /tts`, recipe photo/URL import, image regeneration, ingredient auto-create / nutrition estimate. Every WhatsApp turn checks it too. Admins are exempt; a ledger read error fails open. Spoken turns are ordinary chat turns, so they use the same € budget; there is no separate voice-minutes quota since OpenAI Realtime was retired (2026-10-09).
- **Per-person caps** (Miguel, 2026-11-23): `USER_CAP_OVERRIDES_EUR` = `<userId>:<euros>` pairs, comma-separated (`services/capOverrides.ts`). For those users the number replaces **both** monthly caps, Mimo's and all paid AI, in the app and on WhatsApp (the limit message shows their own figure). Production since 2026-11-23: the general all-AI cap is €10 (it was €5, below Mimo's €6, so Mimo's never applied), and one creator who uses Mimo daily has €20.
- **With the cap used up (PRO-1302).** Until 23-nov the cap cut dry: «Has alcanzado tu límite mensual…» on every message, a tap or a «¿qué hay hoy?» included (18 messages of the most active households went unanswered, one halfway through a request). Now:
  - **What costs nothing keeps working**, before both caps, in the app and on WhatsApp: the code's replies (`codeReply.ts`: «¿qué hay hoy?», «mándame el menú», **«la lista de la compra»** / «¿qué me falta por comprar?» (`ver_lista`, the same `get_shopping_list`; on WhatsApp the list goes as its usual digest), and in the app's cook mode «siguiente» / «anterior» / «repite»), the avisos' buttons and the «¿hiciste la cena?» answers ([WhatsApp](./whatsapp.md)) and the courtesies («gracias», «vale», kept and not answered). In the app the chat route no longer has `requireSpendCapacity()`: it checks the all-AI cap and Mimo's own in the handler, after the code reply (`capReached`).
  - **The notice says what still works and where the menu and the list are, once a month** (`services/capNotice.ts`). WhatsApp: «Este mes ya he gastado lo que tengo para pensar respuestas nuevas (6 €); vuelvo del todo el día 1. Mientras, sigo contestando aquí los botones de mis avisos, «¿qué hay hoy?», «mándame el menú» y «la lista de la compra». Y el menú y la lista los tienes siempre en la app:» + the `/menu` and `/shopping` links (English version for whoever writes in English). App: the same, with cook mode's words and «en Menú y en Compra». The `cap_hits` row of the month (below) is the mark: written when the notice goes (`noteCap` on WhatsApp, `recordCapHit` in the app), read with `capHitThisMonth`. After it, a WhatsApp message that needs the model gets **nothing** (inbound `ignored`, `errorMessage` `over_cap_told`; the first one is `over_cap`); the app, which needs an answer for its panel, gets one short line («Sigo sin respuestas nuevas este mes (6 €); vuelvo el día 1. El menú y la lista, en Menú y en Compra.»). The mark is per person and month, whichever channel it came from. Telegram keeps the old line on every message (it writes no `cap_hits`). The amount doesn't change.
  - **The turn that reaches the cap ends whole.** The cap is only checked before a turn, so a turn is never cut halfway; the one that takes Mimo's spend to the cap or past it (`reachesCap`) ends with the notice (instead of the 80 % line) and writes the mark. If that turn ends asking something (a «?» in its last line, or buttons), the notice waits: the next message, if it answers it (WhatsApp: Mimo's last message ≤ 30 min ago asks something, `awaitsAnswer`; app: the last assistant message of the history ends asking), goes to Mimo **once** even over the cap (only while the month has no mark), and that reply carries the notice. The all-AI cap reached by other paid work (photos, imports) is told on the next message, as above.
  - Tests: `assistantCapSpent.test.ts` (the app route over the cap: «¿qué hay hoy?» and the list answer, the notice once and then the short line, the turn that reaches the cap, the answer that finishes it), `whatsappInbound.test.ts` (PRO-1302 block: a button and «¿qué hay hoy?» answer, the notice once, the turn that reaches the cap), `codeReply.test.ts` (`ver_lista`), `capHits.smoke.ts` (`told` from the real table).
- **Who reached a cap** (PRO-1090, D-148): the first time in a Madrid month that a user hits either cap — Mimo's (`asistente`, `ADVISOR_BUDGET_EXCEEDED`) or the whole-AI one (`ia`, `SPEND_CAP_EXCEEDED`) — in the app or by WhatsApp, `services/capHits.ts` writes one `cap_hits` row (user, household, cap, spent, cap, channel, time; unique per user and month, so later 429s of that month add nothing). Admins are never written, even though Mimo's own budget still answers them 429. Telegram turns aren't written (only `app` and `whatsapp`). A write error is logged and the 429 goes out anyway. Since PRO-1302 the row is also the mark that the cap notice went out (on WhatsApp it's written when the notice goes, not on every check). Read in `GET /admin/metrics` → `capHits` ([Metrics](./metrics.md)) and in Admin → Usuarios, «Han llegado al tope este mes». Tests `capHits.test.ts`, `capHits.smoke.ts`.
- **Anthropic out of credit** (PRO-1101, D-156): when the model call fails with Anthropic's 400 «credit balance is too low», Mimo answers **«Ahora mismo no puedo contestarte; lo estamos arreglando. Vuelve a escribirme en un rato.»** (`API_SALDO_REPLY`, `services/apiSaldo.ts`) instead of the generic error: in the app, `POST /assistant/:userId/chat` answers **200** `{ message, actionTaken: false, corrections: ['saldo_api'] }` (not the 500), and by WhatsApp it goes out instead of «Vaya, algo ha fallado…» (the inbound row is still `failed`). Any other failure keeps its usual answer. The error is noted in the error log (`saldo_api`, at most once an hour) and read in `GET /admin/metrics` → `apiSaldo` ([Errors](./errors.md), [Metrics](./metrics.md)); the office alerts Miguel's phone, as with the caps (D-148). The next model call that answers closes the streak. Tests `apiSaldo.test.ts`, `whatsappInbound.test.ts`, `apiSaldo.smoke.ts`.

## What the code answers, without the model (PRO-1292)

From 19 to 23 Nov «siguiente» in cook mode and «¿qué hay hoy?» / «mándame el menú» still went to the model (0,16–0,28 € a turn, after a pause) to read something already stored. Now, before calling the model (app chat and WhatsApp), a narrow recognizer (`recognizeCodeIntent`) answers them, by closed phrases and **only when the whole message is that** (a line break, another request or a doubt → the model, as before: «¿qué hay hoy? y cámbiame el jueves», «¿qué cenamos mañana que sea rápido?»). Openers and closers that change nothing are allowed («Hola Mimo, …», «venga, …», «…, porfa»); «¿Qué hay?» alone is a greeting, not the menu.

- **The menu (`ver_menu`):** today's, tomorrow's or a weekday's («¿qué hay hoy?», «¿qué cenamos mañana?», «el menú del jueves», «hoy qué comemos»), or the week («mándame el menú», «ver el menú», «pásame el menú semanal», «el menú de la semana que viene»). The code runs the same tools as the model (`get_todays_menu` with the day's words, `get_weekly_menu`), so it says what the app says. One day: «Hoy, martes 24:» and one line per meal (`- Comida: Lentejas estofadas`); a meal asked for («¿qué cenamos…?») shows only that line when the day has it. The week: one line per day, and the days with nothing say «sin planificar» (or «sin cocinar»); on WhatsApp it goes as the week's picture with its caption and the menu link, as before. No menu for that week, or nothing that day → the model answers (it can offer to make it).
- **Cook mode (`paso_cocina`, app only):** with a recipe on screen in `/recipes/<id>/cook` and the step the web sends (`context.cookStep`), «siguiente» («venga, siguiente», «siguiente paso», «pasa al siguiente»), «anterior» («atrás», «vuelve al paso anterior») and «repite» («¿me lo repites?», «otra vez») read that step of the recipe: «Paso 2 de 5: Pocha 150 g de cebolla…» («Paso 5, el último: …»; at either end, «Ya estás en el último/primer paso.» and the step again). The reply carries the same `uiHint: 'cooking_step'` as the tool, so the cook screen moves. Only a recipe the user may see, and only when the step count matches the recipe's; otherwise the model.
- **Free:** these turns never call the model, so they leave no chat row in `cost_events` and count nothing toward Mimo's monthly cap — they work with the cap used up (in the app too since PRO-1302, which also added the shopping list, `ver_lista`). Not in the onboarding (voice or WhatsApp sign-up).
- **History:** the reply is shaped like a model turn (`toolsUsed`, `toolTrace` of `get_todays_menu` / `get_weekly_menu` / `cooking_step`), so on WhatsApp the next turns see it with its `⟦hecho: …⟧` mark; in the app it is kept in `chat_messages` with its trace (PRO-148) and the reply text goes back with the panel's history like any other.
- **Event** `mimo_code_reply` with `kind` (`ver_menu`, `paso_cocina`) and the channel; counted in `/admin/usage` (see [Metrics](./metrics.md)).
- Tests: `codeReply.test.ts` (the phrases that are and aren't, the replies), `assistantCodeReply.test.ts` (the route: no model, no `recordAdvisorUsage`), `whatsappInbound.test.ts` (PRO-1292 block), e2e `cook-mode-code-step.spec.ts`. Source: [services/assistant/codeReply.ts](../apps/api/src/services/assistant/codeReply.ts).

## Examen fijo de Mimo (PRO-1304)

The measure every change to Mimo is checked against (prompt, tools, model, code around it): the same 75 cases, a score from 0 to 2 on six criteria and the price, side by side. It comes from the exam of Mimo's whole history (6-oct to 23-nov, the office's report of 2026-11-23): 75 real turns picked to represent what households ask (26 trivial, 33 normal, 16 hard; 22 that the code should answer), rewritten as invented cases with no one's data.

- **The cases:** `MIMO_EXAM_CASES` (`services/assistant/mimoExamCases.ts`), a literal copy of `examen-casos.json` (regenerated from there, never edited here). Each has the household (`hogar`), the situation (day, menu, catalogue, what Mimo just asked), the earlier turns, the message, what a right reply must do (`debe`) and must not (`no_debe`), the tools it should use, whether the code should answer (`sin_modelo`) and its main criterion. The household and situation are the synthetic user context; the history goes as the engine builds it (`buildChatHistory`'s rules).
- **The run** (`services/assistant/mimoExamRun.ts`): each case goes through `runToolLoop` with the channel's fixed block (`buildFixedBlock`, like `chat()`) and every tool simulated: reading tools answer with the case's situation, the others «Hecho (simulado): …». Nothing is read or written. A message the code answers today (`codeAnswerOf`: `recognizeCodeIntent`, `isCourtesyOnly` with no pending question, the dinner check-in buttons) doesn't reach the model.
- **The grader** (`services/assistant/mimoExam.ts`), 0–2 per criterion: (1) hecho de verdad y entero, (2) respeta la casa, (3) platos con sentido, (4) corto y sin relleno, (5) rápido, (6) verdad comprobada. `rapido` is code only: model rounds (2 or fewer, 4 for a menu or the sign-up; the time too when not remote: 15 s, 60 s for a menu), and at most 1 when the code should have answered. The other five come from a judge (`JUDGE_SYSTEM`: the case, the tools called and the reply; JSON with `nota` and `porque`; `null` = doesn't apply, only for 2, 3 and 6), capped by code checks: none of the expected tools (or an equivalent) called → `hecho_entero` 0, fewer than half → 1; longer than 400/800 (trivial), 800/1400 (normal), 1400/2400 (hard) characters → `corto_sin_relleno` 1/0, an unasked link → 1; «hecho» with no tool that changes anything → `verdad_comprobada` 0, the engine's `unverified_claim`/`partial_claim` → 1. A code-answered case gets 2 (its tests cover the reply). A case's score is the mean of the criteria that apply.
- **The price:** with «Mimo remoto» there's no `usage`, so tokens are estimated from what goes and comes back (≈3.5 characters per token) with the engine's cache: round 1 writes everything (the fixed block with the 1-hour TTL), each later round reads the previous one and writes the new part. `precioEur` is after a pause (fixed block cold), `precioCalienteEur` with it already cached; priced with the model's rate (`ASSISTANT_USD_PER_MTOK`, `ADVISOR_EUR_PER_USD`). Against the API, the tokens are Anthropic's. The judge's own cost isn't counted.
- **How to run it** (D-168: by the subscription, never by the API): in staging with «Mimo remoto» answering, `DATABASE_URL=<staging> pnpm --filter @ona/api exec tsx scripts/mimoExam.ts --remoto --dir=<the office's reports>/data/mimo/examen` (`[--case=h-001,h-002] [--concurrencia=2]`). Every round of Mimo and every judge go to `mimo_turnos_remotos` and the office answers them: today 69 cases reach the model (6 the code answers), 2–3 rounds each plus their judge: ≈210–280 rounds, close to the 300 the office answers per run (cases left without an answer come back with `error`; run them again with `--case`). It writes `<dir>/AAAA-MM-DD.json` (Madrid date): `version` (commit, model), `resumen` (mean score, by criterion, by kind of request, code-answered cases, `sin_modelo` cases that went to the model, tokens in / cache write / cache read / out and price) and `casos` (each one's reply, tools, rounds, six scores with their reason, code checks, tokens and price). A case that couldn't run (a round expired, the judge's JSON unreadable twice) has `error`, doesn't count in the means, and the script exits 1. Stability: `scripts/mimoExam.ts --comparar=a.json,b.json` gives the difference of the mean (stable under 0.2 points; exit 1 otherwise), per criterion, and the cases whose score moved more than a point.
- **Tests:** `tests/mimoExam.test.ts` (the 75 cases, no phones, mails or links, every expected tool exists in its channel; what the code answers; each code check; the judge's JSON; tokens cold and warm; a whole pass with a fake model and judge gives 75 scores with their price, and two equal passes differ by 0).

## Mimo remoto en staging (PRO-1102, D-157)

Staging's test households used to cost 5–6 $ of API an afternoon. With **`MIMO_REMOTO=1`** (staging only) no round of Mimo goes to Anthropic: the office answers it with the subscription.

- **Never in production.** The API refuses to boot with the mode on anywhere but staging (`config/mimoRemoto.ts`, read by `env.ts`): on Railway, unless `RAILWAY_ENVIRONMENT` / `RAILWAY_ENVIRONMENT_NAME` are `staging` (the build sets `NODE_ENV=production` in staging too, so it doesn't decide there); off Railway, when `NODE_ENV=production`. Off is the default.
- **Every round, every channel** (app, WhatsApp, Telegram): where `runToolLoop` would call `messages.create`, `chat()` gives it `remoteMessagesClient` instead. The request goes as is (model, system, messages, tools, `tool_choice`, `max_tokens`…) into a new row of **`mimo_turnos_remotos`** (`id`, `creado`, `estado` `pendiente | cogido | respondido | caducado`, `peticion`, `respuesta`; migration `0108_mimo_turnos_remotos`), and the engine polls it every 0.5 s for **at most 120 s**. No answer by then → `caducado` and an error, exactly as when Anthropic fails (WhatsApp sends its usual error message, the app its 500). An answer that lands while it expires is used.
- **The office's routes**, with their own Bearer token **`MIMO_REMOTO_TOKEN`** (mode off or no token → 404; wrong token → 401):
  - `POST /agent/mimo-remoto/siguiente` → the oldest `pendiente` round, now `cogido` (`{ id, creado, peticion }`; `FOR UPDATE SKIP LOCKED`, so two runs never get the same one). Waits up to **25 s** for one; **204** when none came.
  - `POST /agent/mimo-remoto/:id/respuesta` with `{ content, stop_reason }` in the Messages API format: `content` is a list of `{ type: 'text', text }` and `{ type: 'tool_use', id, name, input }` blocks; `stop_reason` one of `end_turn`, `tool_use`, `max_tokens`, `stop_sequence`, `refusal`. → `{ ok: true }`; 400 for a bad body, 404 for an unknown round, 409 `{ estado }` when it was already `respondido` or `caducado`.
- With the answer the engine carries on as if Anthropic had sent it: it runs every `tool_use`, sends the results back as the next round (a new row), and so on; the truncation, refusal and «hecho sin herramienta» rules behave the same.
- **Nothing is paid, nothing is metered:** the answer has no `usage`, and `recordAdvisorUsage` writes nothing to `cost_events` nor to the user's monthly budget while the mode is on. Other paid steps of a turn (transcription, photo import, guided texts) are unchanged.
- The office side lives in the office's own repo (`apps/oficina/mimo-remoto.ts`, `docs/mimo-remoto.md`): while the Hogares run is on, it takes the pending rounds and answers each with `claude -p` on the subscription (Opus 5.5, Mimo's `system` as is), 2 at a time and up to 300 per run. Outside that run nobody answers: Mimo in staging gives its error after 120 s.
- Tests: `mimoRemoto.test.ts` (request saved as is, `tool_use` → tool runs → another round, expiry at 120 s, routes, the API not booting in production) and `mimoRemoto.smoke.ts` (a test WhatsApp message through `processInbound` against Postgres: pending round, `cogido`, `tool_use`, second round, reply, no `cost_events`; expiry).
- Source: [services/assistant/mimoRemoto.ts](../apps/api/src/services/assistant/mimoRemoto.ts), [routes/mimoRemoto.ts](../apps/api/src/routes/mimoRemoto.ts), [config/mimoRemoto.ts](../apps/api/src/config/mimoRemoto.ts).
