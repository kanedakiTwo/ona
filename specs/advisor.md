# Advisor

AI assistant for nutrition guidance, menu queries, and recipe management via natural language. The assistant is called **Mimo**, of **Mimoia** (renamed on 2026-10-08; `ASSISTANT_NAME` / `BRAND_NAME` in `@ona/shared`). Every prompt mode (text, voice, onboarding, WhatsApp) opens with "Eres Mimo, el asistente de Mimoia", tells the model to introduce itself as "Hola, soy Mimo, de Mimoia" and never as Mimoia (the old name, which users may still use); pinned by `apps/api/src/tests/brandName.test.ts`.

## User Capabilities

**One Mimo, a companion on every page** (decision D-023, 2026-10-09). The advisor is no longer a page: Mimo lives in a floating button and a panel that opens over whatever the user is looking at.

- **Floating button** (`MimoButton`, `data-testid="mimo-button"`): a terracotta circle with the Mimoia spoon (the logo, the same symbol as the app icon, the favicon and the WhatsApp profile photo) on every signed-in page. **Inside the chat Mimo has its own face** (D-058, PRO-137): `MimoAvatar`, the spoon upright with two eyes, a smile and the heart as a cheek, cream on a forest circle, in the panel header (40 px) and beside each of Mimo's bubbles (28 px; not beside the user's). Test: `e2e/mimo-companion.spec.ts` (avatar in the panel, the button keeps the logo) and `e2e/brand.spec.ts`. It is hidden on login, register, reset, onboarding, invites and public pages (`mimoHiddenOn`). It stays clear of fixed bars:
  - default: above the 60 px bottom tab bar on mobile; bottom-right, 24 px from the edges, at `md+`;
  - recipe detail (`/recipes/<id>`): above the 84 px sticky action bar until `lg`;
  - cook mode: `z-110`, above the step controls.
- **Panel** (`MimoPanel`, `data-testid="mimo-panel"`):
  - Phones and tablets (< `lg`): a bottom sheet, 88dvh, over a backdrop (tap the backdrop to close).
  - Desktop (`lg+`): a 400 px right column with no backdrop. The page moves aside: `<main>` gets `padding-right: var(--mimo-panel-width)`, set by `MimoProvider` while the panel is open.
  - Header: «Mimo» and a status line («Escribe o habla», «Te escucho…», «Un momento…», «Pensando…», «Hablando… (toca para parar)», «Manos libres»). Buttons: read-aloud toggle, «Empezar de nuevo» (clears the conversation), «Cerrar». Esc also closes.
  - A «Voz» picker shows when the API offers several ElevenLabs voices; picking one plays a short preview and is remembered on the device.
  - Empty state: «Soy Mimo. Pregúntame lo que quieras…» with suggestions that depend on the page: cook mode («Siguiente paso», «Pon un temporizador de 10 minutos»…), recipe («¿Puedo hacerla sin horno?», «Adáptala para 4 personas»…), menu («¿Qué toca cocinar hoy?», «Cambia la cena del jueves»…), shopping («Añade leche a la lista», «Hazme la compra»…), or the default set.
  - Composer: «Manos libres» toggle, text input («Escribe a Mimo…»), mic button (tap to talk; tap again to stop and send), send button. While Mimo speaks, a «Parar» link stops it.
  - AI disclosure line under the composer (`data-testid="ai-disclosure"`).
  - **Recipes link to their page (PRO-85, 2026-10-15).** When a reply is about today's menu, the week or one recipe, the recipes come with the turn's `data` (`get_todays_menu` → `day`, a week → `days[]`, `get_recipe_details` → `{ id, name }`, or `{ recipeId, recipeName }`). The first whole-word mention of each recipe's name in Mimo's text (any case; the longer name wins) is a terracotta link to `/recipes/<id>` (`data-testid="mimo-recipe-link"`); tapping it opens the recipe and closes the panel. Notes («cenamos fuera») have no page and never link. If the model writes the dish differently from its recipe name, it stays plain text. The links are kept with the conversation (sessionStorage), not sent back as history.
- **Mimo knows the page.** Each turn sends the current path; Mimo understands «esta receta», «siguiente» or «este menú» (see Page context below).
- **The conversation survives navigation** within the tab (sessionStorage), so users can open Mimo on the menu, go to a recipe and keep talking.
- **Pages refresh after Mimo acts.** When a reply changed something (`actionTaken`), every react-query query is invalidated, so the menu, list or recipe behind the panel shows the change.
- **Old links:** `/advisor` is a client redirect to `/menu?mimo=1`; `?mimo=1` on any page opens the panel.
- There is no «Asesor» tab any more: the bottom tab bar and the desktop sidebar have 4 entries (see [Design System](./design-system.md)).

## Assistant Skills

The assistant can call back-end skills (function calling). Each skill has a name, description, JSON schema parameters, and an executor. Current skills:

- `get_todays_menu` — read the menu for today in Madrid time (or any `day`, see Conventions). Reads only the menu of the resolved week (no fallback to another week: "No hay menu para la semana del …") and lists every dish of each slot from `dishes[]`, recipes and notes, e.g. "comida: Lentejas + Ensalada, cena: Cenamos fuera" (via `services/menuText.ts`). Fixes the pre-2026-10 bug where it read the legacy `slot.recipeName` and answered "no hay comidas planificadas" for every day.
- `get_weekly_menu` — read the whole week's menu (this week, or next with `nextWeek`), day by day with dates and «sin cocinar» days; data `{ menuId, weekStart, days, skippedDays }`. No menu or nothing planned → text without menu data. On WhatsApp the reply is the week picture with a «Tu menú de esta semana» caption, not the model's list (see [whatsapp.md](./whatsapp.md)); on the web the model writes the week and its recipes link. Added 2026-10-15; the prompt says to use it (one call) instead of reading day by day.
- `get_recipe_details` — pull a recipe by name: ingredients, **numbered steps** (from `recipe_steps`), servings, tips and the original link (video or web, `source_url`), bounded to 4 000 chars (`recipeDetailsSummary`). Until 2026-10-12 it read a `recipe.steps` column that doesn't exist, so the model never saw a step and couldn't walk anyone through a recipe or give its video
- `get_weekly_nutrition` — calorie and macro summary for the week
- `get_shopping_list` — reads the same rolling list `/shopping` shows (today → next Sunday: menu items, staples, manual items) and names what's still missing, sorted by aisle, with "Ya comprado: N. En casa: M." ("¿qué me falta?"). Before 2026-10-11 it re-aggregated the latest menu and only told the model a count, so manual items and bought ones were invisible
- `suggest_recipes` — recommend recipes matching meal/season, never one that breaks the user's allergies, diet or dislikes. `cook_with_what_i_have` — «tengo calabacín y huevos, ¿qué hago?» (chat, voice and WhatsApp; PRO-31): the same search as the «Con lo que tengo» filter on `/recipes` (`services/withWhatIHave.ts`) with 1–3 free-text ingredient names (word match, plural-tolerant; extra ones are ignored and said so); answers with up to 5 recipes, each with what it uses and what's missing, basics (sal, aceite, agua, pimienta, harina) never counted; same allergy/diet/dislike rules as `suggest_recipes`
- `search_recipes` — search by name substring
- `complete_onboarding` — WhatsApp-first sign-up only: saves adults, kids, cooking frequency, favourite dishes and priority like the web onboarding (`saveOnboarding`, never health data), marks `onboardingDone` and generates the first week (same as `generate_weekly_menu`). Refuses (summary, no write) when a required answer is missing or the account is already onboarded. The WhatsApp prompt adds `WHATSAPP_ONBOARDING_PROMPT` while the user isn't onboarded (`ChatOptions.onboarding`)
- `generate_weekly_menu` — full menu generation for the user. `nextWeek: true` targets next Monday (used when the user says "la semana que viene" or accepts the WhatsApp Sunday nudge). Enqueues prep alerts like `POST /menu/generate`. A week that already has dishes or notes is **never remade** without `replaceExisting: true` (the user confirmed remaking the whole week): otherwise it changes nothing and points to `swap_meal` / `add_dish` / `set_meal_note` — asking for a dish never regenerates the week (PRO-63; an empty week row, which the web creates just by opening it, is generated without asking). **Acierto (PRO-155):** after generating it runs the menu evaluator ([Menus](./menus.md) → Acierto) and appends to its summary «Acierto con sus gustos: N/100 (alto|medio|bajo)», what's met, what «no está en el catálogo», what «no cabía esta semana» and, when low, the ways to add recipes this household hasn't used (photo, link, writing it); `data.fit` carries the verdict. The prompt (`systemPrompt.ts`, «Acierto del menu») gives Mimo a guide, not a fixed text: alto → sure and brief, naming one or two of their dishes; medio → says what it couldn't fit and why, and offers to put it in; bajo → humble, «con las recetas que tengo no he podido acercarme mucho a lo que os gusta (carbonara, rodaballo…)», and invites to add their recipes explaining one unused way, different each time. Without the line Mimo doesn't talk about it, and it never says only five favourites fit (there's no cap: `complete_onboarding` takes up to 30). Replay of the three levels: `scripts/replayWhatsAppTurns.ts --fit-cases=scripts/replayMenuFitCases.json --user=<uuid>` (needs the real model)
- `swap_meal` — replace a single meal slot of the menu of the resolved week (never "the latest menu", see Conventions); the slot keeps its «Solo hoy» diners (`servings`, PRO-102); it confirms only after reading the dish back from the saved row ("No he podido guardar el cambio…" otherwise) and returns `data.change` = week, date, dayIndex, meal and dish. Without a `recipeId`/`recipeName` parameter, runs the matcher (auto-picks). When the user names a recipe ("pon la fabada de mi madre el lunes"), the model passes `recipeName` (or `recipeId` when known) and the skill pins that recipe directly without the matcher. Recipes the user owns win over system recipes when names collide
- `toggle_favorite` — favorite/unfavorite a recipe
- `mark_meal_eaten` — log that the user actually ate a meal (records `eatenAt` timestamp)
- `create_recipe` — save a new user recipe. If the user asks for a basic recipe without details ("créalo tú"), the model writes a reasonable version and saves it without further questions. Since 2026-10 it persists through `createRecipeFromParts` (`services/recipeImport.ts`): the same ingredient matching (USDA auto-create) and soft-lint persist as URL/photo imports, with safe defaults (2 servings, lunch+dinner, all seasons; `normalizeRecipeParts`). The old raw INSERT skipped `servings` (NOT NULL) and failed in prod; the mock-DB tests never caught it.
- `edit_recipe` — author-only field edits on a user recipe (name, prepTime, cookTime, difficulty, notes, tips). Voice cannot edit ingredients/steps inline; with `openEditor: true` it returns a hint pointing at `/recipes/<id>/edit` so the user can continue in the form
- `update_household` — set the user's `adults` + `kidsCount` (children 2–10 years; <2 don't count, >10 count as adults). Drives shopping-list portion sizing immediately. Triggered by phrases like "ahora somos 2 adultos y un niño" or "quítame el niño"
- `add_recipe_to_mine` — copy a system (or another user's) recipe into the caller's catalog so they can edit it. Lookup by `recipeId` or `recipeName` (prefers Mimoia system matches; refuses if the only matches are recipes the user already owns). Returns the new recipe id + name. Same wire as the `POST /recipes/:id/copy` endpoint surfaced in the UI as "Añadir a mis recetas"
- `import_recipe_from_url` — "guárdame esta receta: <enlace>": extracts a YouTube video, recipe article or Instagram/TikTok post caption with the same pipeline as `POST /recipes/extract-from-url` and saves it as the user's recipe (soft lint, `internalTags: ['auto-extracted','from-url']`). Returns `{ recipeId, name }` with `uiHint: 'recipe'`; non-recipe links and unreadable pages come back as a plain-text summary the model relays; an Instagram/TikTok caption without the recipe comes back as «No he podido leer la receta de este vídeo; mándame una captura» for the model to relay verbatim. Shared persist in `services/recipeImport.ts`
- `update_memory` — persist any preference the user mentions ("recuerda que no me gusta el cilantro", "tengo freidora de aire", "los lunes no cocino más de 20 min"). Accepts `facts: [{ key, value, confidence?, remove?, replace? }]`. Lists are **merged** with what's stored (`mergeMemoryFacts`: union without duplicates; `remove` takes items out; `replace: true` rebuilds the list) and an inference never overwrites a fact the user set by hand (`source: manual`) unless the user asked for it (confidence 1). Writes through `setMemoryBatch` with `source='inferred'` and default confidence 0.8 (1.0 if the user is emphatic). Canonical keys live in `@ona/shared` `MEMORY_KEYS` — see [User Memory](./user-memory.md). The assistant's system prompt already carries a Spanish digest of every stored fact, so a write here changes the next response's grounding.
- `recipe_variation` — generate a variation of a recipe (e.g., dairy-free version)
- `nutrition_advice` — return advisor summary based on `user_nutrient_balance`
- `get_pantry_stock` — what's at home: the real pantry (`pantry_items`, with quantities and expiry dates, what `/pantry` shows) plus items marked "ya lo tengo" on the latest shopping list, deduped by name. It used to read only the list flags, so the pantry kept in the app was invisible to the assistant
- `mark_in_stock` — "tengo X" / "se me acabó X": sets the list item's `inStock` **and** adds the item to (or removes it from) the pantry, whichever exist. With no list it still writes the pantry
- `check_shopping_item` — set/toggle the `checked` flag of a shopping-list item (mark groceries as bought)
- `get_my_recipes` — list recipes authored by the user (`recipes.authorId = user.id`)
- `get_menu_history` — list past weeks' menus to answer "when did I last eat X"
- `scale_recipe` — return ingredient quantities scaled to a different `servings` count without mutating the recipe
- `evaluate_food_health` — frame "is X healthy?" through Mimoia's cooking principles so the model answers with criterion (not neutral), in cooking words: veg/legume/fibre, real food vs ultra-processed and added sugar, how often it fits the week, a better kitchen alternative; never body effects (PRO-67)
- `suggest_substitution` — frame ingredient substitutions through the philosophy: never propose margarine, refined vegetable oils, artificial sweeteners
- `get_variety_score` — count distinct ingredients / vegetables / proteins in the current week's menu (principle 2, «Verdura todos los días, y variada»; advice in cooking words, no microbiome since PRO-67)
- `get_eating_window` — average first/last eating hour and window length from `eatenAt` timestamps (principle 7, «Comidas a su hora, sin picoteo»; advice in cooking words, no insulin since PRO-67)
- `get_week_balance` — kitchen balance of the current week's menu (no `recipeName`) or of one recipe: how many meals carry vegetables, on how many days there are legumes, which days repeat fried dishes, which recipes are salty or carry processed ingredients (from ingredient names, step texts and `nutritionPerServing.fiberG`/`saltG`). Answers in cooking words ("Esta semana vas corto de verdura… El jueves y el viernes repiten fritos."), never a score. Replaced `get_inflammation_index` (0–100 "anti-inflammatory" score) on 2026-10-11 (PRO-09, constitution §6: no health effects or disease names; an "inflammation index" reads as a medical-device calculator). The prompt tells Mimo to talk about kitchen balance and to send questions about a disease, a symptom or health effects to a health professional (doctor or dietitian-nutritionist). Guard: `tests/weekBalance.test.ts` (no tool, description, prompt instruction or default principle says "inflam…" or names a disease; the principles block appended to the prompt and the fixed health rule are guarded by `tests/principiosMimo.test.ts` and `tests/healthAdvice.test.ts`)
- `start_cooking_mode` — resolve a recipe and emit a `cooking_navigate` hint so the client routes to `/recipes/:id/cook`
- `set_timer` — emit a `cooking_timer` hint that `CookingShell` consumes via `subscribeCookingCommands` to start a timer at the current step
- `cooking_step` — emit a `cooking_step` hint with `direction: 'next' | 'previous' | 'repeat'` to advance the cooking shell

**UI-parity skills** (`services/assistant/appSkills.ts`, 2026-10). The goal is that anything the web app can do is reachable from chat. These skills call the app's own REST API as the user (`appApi.ts`: loopback + a 5-min JWT), so validation, side effects and permissions match the UI exactly.
- **Menu:**
  - `set_meal_note`: "apunta que el jueves viene la abuela" (replaces the slot's dishes with a note by default).
  - `clear_meal`, `set_day_skipped` (day without cooking / back on). **A meal not eaten at home is removed, not noted (PRO-113, 2026-10-18):** "el viernes no comemos en casa", "cenamos fuera", "comemos en casa de Paqui" → `clear_meal` (its ingredients leave the list); the whole day → `set_day_skipped`. The prompt and both tools' descriptions say so; before, Mimo left a «Cenamos fuera» note (reviewer, 2026-10-10).
  - `add_dish`, `remove_dish`: multi-dish slots.
  - `set_meal_servings`, `lock_meal`, `move_meal` (move/swap slots).
  - `ban_recipe_this_week`: vetoes the recipe for the week **and changes it where it already is**, like «Vetar esta receta» on the web (PRO-113; PRO-72 on the web). After `POST /menu/:id/ban`, each appearance from today on (every day for a future week; past days stay) is regenerated with `POST …/dish/:position/regenerate` (the matcher skips vetoed recipes); a táper of it whose source changed becomes sobras of the new dish (slot cleared, `POST …/leftover`, its «Solo hoy» put back). Left as they are, and said so: locked meals, freezer tápers, sobras of a dish already cooked, meals with no other recipe that fits (409). The summary lists what each meal got («- Miércoles 14 de octubre, cena: "Garbanzos con espinacas"») and `data.changes` carries date, meal and dish; the prompt tells Mimo to repeat it. Before, it only blocked the recipe and Mimo said «vetado de toda la semana» while it stayed on the menu.
  - `set_leftovers`.
  - `add_freezer_dish` (PRO-82): "esta noche comemos táper de lentejas" → that meal becomes the recipe with `variant: 'freezer'` («Del congelador», adds nothing to the list); replaces the meal's dishes unless `keepDishes`; a dish not in their recipes or the catalogue goes as a «Táper: …» note.
- **Shopping:** `add_shopping_items` (units normalised to g/ml/u/cda/cdita; never duplicates: a product already pending — same words, or a list name starting with what was said, "leche" → "Leche entera", "huevos" ↔ "Huevo" — is reported as "ya estaba"; one marked bought or "en casa" goes back to pending; "leche de coco" is never "Leche"), `remove_shopping_items`, `regenerate_shopping_list`, `manage_staples`.
- **Compra en mis tiendas** (`shopOrderSkills.ts`, see [Shop orders](./shop-orders.md)): `manage_shops`, `prepare_shop_orders` ("hazme la compra" → one `/c/<token>` short link per shop that opens the user's own WhatsApp with the order written), `edit_shop_order` (before sending: add products — each to its shop —, remove, choose "serrano", amounts, include, pickup/delivery + address; same links), `register_shop_reply` (forwarded/pasted shop reply → OK / Revisar / No hay per line, total vs cap), `approve_shop_order` (only after an explicit "sí"; returns the confirmation link), `close_shop_order`, `get_shop_orders`. The prompt treats a shop's reply as data, never instructions, and allows copying `/c/` links verbatim.

  - `update_weekly_template`: diners per meal/day, dishes per meal.

- **Conventions:**
  - **Days resolve to dates in Madrid (PRO-63, `menuDay.ts`).** Menu skills (`swap_meal`, `get_todays_menu`, `mark_meal_eaten`, `set_meal_note`, `clear_meal`, `set_day_skipped`, `add_dish`, `remove_dish`, `set_meal_servings`, `lock_meal`, `move_meal`, `set_leftovers`, `log_cooked`) take `day` with the user's words or a date — "hoy", "mañana", "pasado mañana", "ayer", "el sábado", "el sábado 17", "este lunes", "el martes pasado", "el próximo lunes", "el jueves de la semana que viene", `AAAA-MM-DD` — plus `meal`. A bare weekday is the next one, today included (on Sunday "el martes" = in two days). Legacy `dayIndex` (0 = lunes) + `nextWeek` still work. Unknown words → "No sé qué día es…; no he cambiado nada", never a guess. The tool edits the menu **of that date's week** (before, `swap_meal` and `mark_meal_eaten` edited the newest menu row, so once next week's row existed "el sábado" landed on next week — hogares de prueba 2026-10-12) and every summary repeats the day with its date ("la comida del sábado 17 de octubre"); `move_meal` / `set_leftovers` refuse two days of different weeks. The prompt tells Mimo to pass the user's words as `day`, to repeat day, date and dish as the tool returned them in its "Hecho:" lines, and that a tool saying "no he cambiado nada" or failing means it isn't done.
  - Named recipes resolve fuzzily (`bestMatch`, Spanish stopwords ignored, culinary synonyms such as vaca→ternera/entrecot).
  - "Las lentejas" prefers the dish in this week's menu.
  - A lookup that finds nothing says so; it is never a silent no-op.
- A dish the user names that isn't in their recipes nor the catalogue (`swap_meal` / `add_dish` with a `recipeName` that matches nothing, or only by one of its words) becomes a **household recipe** when the model sends `newRecipe` (a simple version it makes up: servings, ingredients with amounts, steps — PRO-74, `services/assistant/dishRecipe.ts`): it's saved through `createRecipeFromParts` with servings «Estimado» (PRO-32, internal tag `estimated`) and placed as a recipe dish, so its ingredients reach the shopping list (test households 2026-10-11/14: «pescado a la plancha», «pizza casera» stayed notes and the list had no fish). `add_dish` replaces an earlier note with the same text instead of doubling it. Without `newRecipe`, or if saving fails, it goes on the menu **as a note with the user's words** ("pizza casera" → note "Pizza casera") and the tool tells the model to call again with `newRecipe`; the closest real recipe, if any, is only offered. Never "no existe, ¿la creo?" before placing it (2026-10-08, WhatsApp). The prompt rule lives in the shared critical rules, so the app chat, voice and WhatsApp behave alike. Lookups only search the catalogue plus the user's own recipes, never another user's private ones.

**Decisiveness (resolutive mode).**
- The prompt tells the model to do everything a message asks in the same turn, with parallel tool calls and up to `MAX_TOOL_ROUNDS = 6`.
- It doesn't ask permission for reversible changes; it confirms only destructive or bulk ones.
- An explicit request beats a stored like or dislike, but **never an allergy, intolerance or health restriction**. For those, the model warns in one line and asks for confirmation. (Fixed 2026-10-07: the first version said "restricción" too.) Since 2026-10-07 the tools enforce it too: `swap_meal` with a named recipe that breaks an allergy/diet changes nothing and returns the conflict, and it only places the recipe on a second call with `confirmRestriction: true`. `suggest_recipes` and the random swap never return such recipes (see [Menus → Restrictions & allergies](./menus.md)). The memory digest now reads "Le disgustan (evítalos al proponer; si el usuario pide algo explícitamente, hazlo)".
- If a week has no menu yet, the model generates one and then applies the changes.
- No backstop rounds since 2026-10-12. The regex guards ("no puedo…", "dame un momento…", "hecho" without a tool) used to force a corrective round; with the small model they produced the oddest replies ("Tienes razón, ya estaba hecho desde hace un turno"). Now the prompt carries those rules, and a past-tense claim with no tool this turn (`claimsAction`) is only **flagged** (`corrections: ['unverified_claim']`) for the daily review.
- The user context now includes **today's date and time in Madrid** with its dayIndex, plus **this week's menu** read from `dishes[]`. Before, it read the legacy `slot.recipeName` and was always empty.
- **The saved menu says what is done, not Mimo's memory (PRO-101, 2026-10-18).** A fixed block in every mode's prompt (`MENU_STATE_RULE`, `systemPrompt.ts`): before confirming, denying or correcting a change (this turn or an earlier one), Mimo looks at the saved menu — the «Menu de esta semana» block of the context, re-read on every message, or `get_todays_menu` / `get_weekly_menu`. If the menu shows it, it's done: no apology, no redo, no «no lo hice / no lo comprobé / me lo inventé». The context block is only the current week: next week (e.g. Monday asked on a Sunday) is looked up with the tools. The list and the pantry aren't in the context: Mimo checks them with their tool before saying something is marked. The menu Mimo reads (context and menu tools, `mealLinesForDay`) shows diners set by hand as `comida [solo hoy: 4]: …` («Solo hoy: 4» in the app). Why: the test households got «Antes te dije que lo había ajustado, pero este turno no veo que lo guardara», «No hice ningún cambio… me lo inventé», «el menú no me muestra cuántos comensales hay» and a Sunday reply that «corrected» a good next-week menu by reading this week's. **Tests:** `tests/mimoMenuState.test.ts` (rule in every mode's cached instructions, `[solo hoy: N]`, and the battery cases below fail on the real replies).
- **«Efecto bola de nieve» in the web chat (PRO-170, 2026-10-18).** When a turn generates a week (`generate_weekly_menu` or `complete_onboarding`, `generatedMenuThisTurn`) in the household's first `SNOWBALL_WEEKS` = 2 generated weeks, `POST /assistant/:userId/chat` puts the same line as WhatsApp on top of Mimo's reply: «Las primeras semanas acertaré menos con los gustos de tu casa. Dime qué cambiarías y lo apunto: así iré acertando cada vez más. Es el efecto bola de nieve ⛄» (`withSnowballLine` in `menuText.ts`; count `generatedWeeksOf` in `menuWeek.ts`, see [whatsapp.md](./whatsapp.md)). A count that fails → no line.
- The card or app link comes from the most visual skill of the turn (menu/list/recipe > nutrition > confirmation > text). An empty final text says "Hecho." (never a tool summary, which may carry notes meant for the model).

**Knows how to cook (2026-10-12).** The prompt lets Mimo answer cooking questions with its own knowledge (techniques, times, temperatures, tricks, utensils, substitutions, storage), even for dishes that aren't in the catalogue ("¿cómo hago un gallo San Pedro a la brasa de 2 kg?" used to get a refusal or a catalogue search). Data about the user's account (menu, saved recipes, list, pantry, nutrition) still comes only from the tools, and a saved recipe is explained from its real steps. No medical advice: see **Health questions** below. Asked to create a recipe without details ("créala tú"), it writes a complete version and saves it without interrogating the user. Named dishes always go in `recipeName` (a `swap_meal` without it picks a random recipe); a catalogue recipe that contains every word the user said (`namesAllWords`: "hamburguesa Gipsy Chef" → "Hamburguesa perfecta de Gipsy Chef") is placed as that recipe, not as a note.

**A baby at home: its portion is set aside before the salt (PRO-174, 2026-10-18).** A cooking rule in every mode's prompt (`BABY_PORTION_RULE`, `systemPrompt.ts`): when the household has a baby (profile, memory or the conversation) or the user asks to adapt a dish for one, «Aparta la ración del bebé» is its own step right before the first step that adds salt, spice or pepper, honey, a stock cube, soy sauce or cured meat — never at the end or as a note. No health reasons: Mimo doesn't say why nor that something is good or safe for a baby (constitution §6, red line 4; health questions keep `HEALTH_RULE`). Why: Mimo salted the potatoes in step 2 of a merluza al horno and only said at the end «Para Leo, antes de sazonar, aparta…». **Tests:** `tests/mimoBabyPortion.test.ts` (rule in every mode; the battery case `merluza-horno-bebe` fails on the real reply and passes a correct one).

The cooking-mode skills (`start_cooking_mode`, `set_timer`, `cooking_step`) are bridged to the `CookingShell` UI by `MimoProvider`: `cooking_navigate` routes to `/recipes/:id/cook`, and `cooking_timer` / `cooking_step` go through [`apps/web/src/lib/cookingCommands.ts`](../apps/web/src/lib/cookingCommands.ts), a tiny pub/sub bus subscribed to from `CookingShell`. Typed and spoken turns dispatch the same way. If no shell is mounted, commands silently drop (the assistant still gave the confirmation).

The model responds with either a plain text message or tool calls. `runToolLoop` (engine.ts) executes **every** `tool_use` block of a response (parallel calls are answered in one user message, failures flagged `is_error`) and loops for up to `MAX_TOOL_ROUNDS = 6` rounds — so "genera el menú y dime qué toca hoy" runs both skills in one turn. The round after the last is sent with `tool_choice: none` to force a text answer. The response's `skillUsed`/`uiHint`/`data` come from the last skill with a non-`text` uiHint (falling back to the last skill), so the web still renders one card per turn.

**Health questions: Mimo is not a doctor (PRO-62, 2026-10-13; constitution §6).** Every mode's prompt carries a fixed block, `HEALTH_RULE` (`services/assistant/healthGuard.ts`): a question about someone's health — a baby or small child (what they can eat and from what age, honey, fever, a runny nose), pregnancy, diabetes or sugar, blood pressure, cholesterol, an allergic reaction, medication, an illness or any symptom — gets (1) a one-line referral to the paediatrician (babies, children) or their doctor, (2) the §6 sentence literally, «Mimoia no sustituye a un profesional sanitario.», and (3) only cooking ideas, never justified by health. Mimo never talks about body effects (glucose, blood sugar, insulin, spikes, blood pressure, cholesterol, inflammation, defences, microbiome, digestion, weight; «sube», «va bien para», «ayuda a»…), nor portions, timings or walks for health reasons, asked or unprompted; never names a disease as something a dish avoids or improves; never says a food is safe for a baby or from what age; urgent-sounding cases → call the paediatrician/doctor now or 112. Adapting a recipe to a saved restriction (sin gluten, sin sal…) is cooking and goes ahead. Why: on 2026-10-11 the test households got «A los 10 meses ya puede tomar miel sin riesgo de botulismo», «eso le ayuda más a la insulina», «omega-3 que va bien para la insulina» and «Nada frío (los mocos empeoran)»; on 2026-10-12, how rice «sube el azúcar» and how to «suavizar la subida». **Engine net:** a reply that refers to a professional (pediatra, médico, dietista, centro de salud, 112) without the §6 sentence gets it appended (`ensureHealthDisclaimer`), and a reply that talks about body effects anyway is flagged `health_talk` for the daily review (`talksHealthEffects`; no forced rewrite). **Tests:** `tests/healthAdvice.test.ts` (rule in every mode; the grader `healthReplyProblems` fails each real bad reply and passes the rule's own examples; the engine net). **Live eval** (the CI can't call the model): `ANTHROPIC_API_KEY=… pnpm --filter @ona/api exec tsx scripts/evalHealthAnswers.ts [--mode=whatsapp|text|voice] [--runs=3] [--case=<id>] [--out=eval.json]` sends the five real questions (`HEALTH_EVAL_CASES`: honey at 10 months, baby with a runny nose, melon and diabetes, salmon/lentils for a diabetic — that question reconstructed —, rice al caldero of 2026-10-12) through the current engine with a synthetic context and simulated tools (no DB, nothing written or sent), grades each reply with the same grader and exits 1 on any failure. Run it before shipping a change to the prompt, the model or `kb/`. The same script runs the rest of the battery, `MIMO_EVAL_CASES` (`services/assistant/mimoEvalCases.ts`, grader `mimoReplyProblems`, where a case can give what a simulated read tool answers): `comensales-turno-anterior` and `semana-que-viene-domingo` (PRO-101), `merluza-horno-bebe` (PRO-174: «aparta la ración del bebé» before the first seasoning, no health reasons).

**Cooking principles, not a health framework (PRO-67, 2026-10-13).** The prompt ends with «Principios de cocina de Mimoia»: the literal text of `kb/principios-mimo.md` («Cómo cocina Mimoia», ten principles approved by Miguel on 2026-10-12: real food, veg every day and varied, season first, legumes, olive oil, whole fruit and real bread, meals at their time, no dogma or guilt, cooking should be fun, Mimo is not a doctor). It is the only file of principles loaded (`KB_FILE`, `knowledgeBaseReady`; also by the legacy `services/advisor.ts`); the public facts below live apart. It replaced `kb/10 mandamientos.md`, which went whole into the prompt with inflammation, insulin, microbiome and a cardiologist as origin. The tool texts went to cooking words too: `evaluate_food_health` (no «impacto en insulina»), `get_variety_score` (no «microbioma resiliente») and `get_eating_window` (no «reduce la insulina crónica»), and the default principle about glucose and «resistencia insulínica» (`ONA_PRINCIPLES`, `/profile/creencias`) is now «Comida de verdad, poco ultraprocesado». Guard: `tests/principiosMimo.test.ts` (the prompt in every mode includes «Cómo cocina Mimoia» and, outside the two sentences that forbid them — `HEALTH_RULE` and principle 10 —, never says «inflam», «insulin», «microbioma», «cardiólogo» or a §6 disease; neither do the skill texts nor the default principles).

**Beta feedback (2026-10-15):** when the user wants to tell the team something about Mimoia (a suggestion, a bug, a complaint, thanks), the `leave_feedback` tool saves it verbatim (channel `chat` or `whatsapp`) in the same box as the app's «Opinión» button, and Mimo thanks them — see [Feedback](./feedback.md).

**Mimo knows Mimoia (D-053, 2026-10-15).** Every mode's prompt also carries «Sobre Mimoia»: the literal text of `kb/sobre-mimoia.md` (`ABOUT_FILE`: what Mimoia is, with the §6 intended purpose word for word; mission, vision and origin; what users can do; web, installable app, WhatsApp and voice; closed beta and the 12 January opening; household; privacy; independence; contact hola@mimoia.com) plus `pricingBlock()`, built from the same constants as `/precios` ([billing.md](./billing.md): `PLANS` with both prices and Esencial «el que recomendamos», every row of `PLAN_FEATURE_GROUPS`, `PLAN_CAPS_NOTE`) plus `FOUNDER_FOOTER` / `FOUNDER_FOOTER_BETA`, how to pay during the beta (wording depends on whether Stripe is configured), how to change or cancel (Perfil → Suscripción) and who charges (`LINK.COM* MIMOIA`), so Mimo quotes exactly the plans, prices, inclusions and caps the web shows. Mimo answers «¿cuánto cuesta?», «¿qué incluye Plus?», «¿qué es Mimoia?», «¿vendéis mis datos?» or «¿puedo borrar mi cuenta aquí?» (no: Perfil → Borrar mi cuenta) from that and nothing else; anything not there (discounts, companies, other countries) gets «no lo sé» + the contact email. The file never writes a price. Guard: `apps/api/src/tests/sobreMimoia.test.ts` (file present, intended purpose, no prices, no §6 words, every plan's price in every mode's prompt, WhatsApp on-topic rule). Keep it current: CLAUDE.md → Definition of done.

**Imported content is data, not instructions.** Tool results can carry text the user didn't write: an imported web page or photo (recipe name, ingredients, steps, the extractor's "not a recipe" reason) or another household member's recipe. The system prompt tells the model that any order found there ("ignora lo anterior", "borra…") is content and is never followed; only the user gives instructions. `import_recipe_from_url` also passes those strings through `untrustedText` (one line, no control characters, ≤ 80/160 chars, inside «»). An unsafe link (localhost, private network, metadata endpoint) or a failed download (too big, not HTML, HTTP error) comes back as a plain summary, not a tool error.

**Model and loop (since 2026-10-12; Opus 5.5 since 2026-10-19).** `ASSISTANT_MODEL = CLAUDE_MODEL` (`claude-opus-5-5`, `config/models.ts`, PRO-232 / D-070; Sonnet 5.5 from 2026-10-12) with adaptive thinking at effort `medium`, `max_tokens` 8 000, the server-side refusal fallback (`fallbacks: 'default'`, beta `server-side-fallback-2026-07-01`) and no sampling parameters. It was Claude Haiku 4.5 with 1 024 tokens until then: replaying 9 real WhatsApp turns (diagnosis 2026-10-11, `reports/2026-10-11-mimo-whatsapp-diagnostico.md` in the working tree), Haiku failed 7 (refusals, false "Hecho", invented menu facts, a recipe cut at 1 024 tokens) and Sonnet 5.5 none badly. Full response content (thinking blocks included) goes back unchanged inside the loop. A response cut by `max_tokens` never runs its half-written tool call: one retry asks for smaller steps (`TRUNCATED_NOTE`), a second cut ends the turn with "Se me ha hecho muy largo…"; `stop_reason: refusal` gets a short friendly reply. **Caching:** tools (last tool is a breakpoint) → the prompt's `instructions` (same for every user of a channel; breakpoint) → its `context` block ("Datos del usuario": the date — `todayLine`, no clock —, menu, memory) → the history, with a breakpoint on its last block → the new message, which starts with the clock (`clockNote`: "(Hora de este mensaje: 14:32 en Madrid)"), then photos, then the text; plus a breakpoint on the newest block each round (`withLastMessageCached`). `buildTurnMessages` builds the messages (also used by `scripts/replayWhatsAppTurns.ts`, with the original message time). The next message, within the API's 5-minute cache life and with the same menu and memory, reads tools + instructions + context + history from the cache. Until 2026-10-12 the time was inside the one cached block, so nothing was reused; until 2026-10-16 it was in the context block, so each message re-wrote the context and the history (`cost_events`, Sonnet 5.5, 7 days: ~4 700 tokens written per message sent within 5 minutes of the previous one; ~33 000 after a longer pause, when the cache has expired anyway). Known limit: once the history window slides (20 messages, `HISTORY_MAX_MESSAGES`) its start changes every message, so long conversations still re-write the history. **Tools per channel** (`toolsFor`): WhatsApp doesn't get `set_timer` / `cooking_step`, and `complete_onboarding` is only offered during the WhatsApp-first sign-up. **Trace:** every tool's input and result (bounded) come back as `toolTrace` (WhatsApp stores it per turn; see [WhatsApp](./whatsapp.md)). Images can be passed with the message (`opts.images`, WhatsApp photos). Each round logs `[assistant] round N: <skills>`. `ChatOptions.onToolStart(names)` fires before each tool round. WhatsApp uses it to send a "me pongo con ello" note as soon as a slow skill starts.

## Voice (one brain)

Typed and spoken turns go to the same Claude assistant; there is no separate voice model. The mic records with silence detection → `POST /stt` (OpenAI transcription) → the text is sent with `mode: 'voice'` (short spoken replies) → the reply is read aloud by `POST /tts` (ElevenLabs, browser voice as fallback). Spoken turns are always read aloud; typed turns only when «Leer las respuestas en voz alta» is on. «Manos libres» listens again after each reply. Full detail (recorder timings, TTS limits, fallbacks) in [Voice (Mimo)](./voice-mode.md).

## Page context

`POST /assistant/:userId/chat` takes `context: { path }` (≤ 200 chars). `describePage` maps the path to a page kind and `pageContextNote` appends a hidden note to the message, «[Pantalla actual (no lo menciones): …]»: viewing recipe «X» (`/recipes/<id>`, `/edit`), cooking recipe «X» in cook mode (`/recipes/<id>/cook`: «siguiente», «temporizador» refer to it), the weekly menu (`/menu`), the shopping list and shop orders (`/shopping`, `/compra`), the catalogue (`/recipes`, `/cookbooks`), the profile; anything else adds nothing. A recipe is only named if the user can see it (`canViewRecipe`); otherwise no note. Onboarding turns never get one. Pure functions in `services/assistant/pageContext.ts`, tested in `pageContext.test.ts`.

## API

- `POST /assistant/:userId/chat` (auth) — body `{ message, history, mode?, context? }`
  - `history` is the recent conversation, capped at 20 messages by the client
  - `mode`: `'text'` | `'voice'` | `'onboarding'`; anything else is treated as `'text'`
  - `context.path`: the page the user is on (see Page context)
  - Response: `{ message, skillUsed?, uiHint?, data?, actionTaken? }`
  - `:userId` must match the authenticated user, else **403** (the chat loads that user's context and bills their budget)
  - Returns **429** `code: 'ADVISOR_BUDGET_EXCEEDED'` once the user has spent their monthly euro budget (see Cost guardrail)
- `POST /stt` (auth, 60/min, spend cap): multipart `audio` ≤ 10 MB → `{ text }`; 503 `STT_DISABLED` without `OPENAI_API_KEY`, 502 `STT_FAILED` on a transcription error. Cost feature `mimo_voice_transcription`.
- `GET /tts/voices`, `POST /tts { text, voice }`: read-aloud (see Voice).

## Channels

`chat(userId, message, history, db, opts)` is transport-agnostic. `opts.mode` picks the system-prompt flavour: `'text'` (typed in the app, default), `'voice'` (spoken in the app: short replies meant to be heard), `'onboarding'` (`/onboarding/voz`, see [User Memory](./user-memory.md)), `'whatsapp'` (see [WhatsApp](./whatsapp.md) — WhatsApp markup, no screen language, `[[opciones: …]]` reply-button convention, cooking timers/steps redirected to the app). Every channel shares the same skills, memory digest and monthly budget.

## Cost guardrail (per-user monthly budget)

The advisor chat (and WhatsApp) calls Claude Opus 5.5 since 2026-10-19 (Sonnet 5.5 from 2026-10-12, Haiku 4.5 before), one request per tool round, so it's metered per user. A typical turn cost about $0.02–0.03 on Sonnet 5.5 with the cache warm (the first of a conversation ~$0.07); Opus 5.5 is twice the list price, so about double [I], and the €5 default covers about half as many turns a month (FIN-09); revisit with Finanzas:

- Every turn's real token `usage` (input / output / cache-write / cache-read) is priced at the assistant model's list rate (`ADVISOR_PRICE_MODEL`, USD), converted to euros via `ADVISOR_EUR_PER_USD` (default 0.92), and added to a per-user, per-month running total stored in `users.advisor_spend_micros` (+ `advisor_spend_month_key`).
- Before each turn the route checks the total against `ADVISOR_MONTHLY_BUDGET_EUR` (default **€5**). At or over budget → `429 ADVISOR_BUDGET_EXCEEDED`, no model call is made.
- The month resets implicitly: the first chat of a new month overwrites the total with that turn's cost (same stateless pattern as the image quota — no cron). A user just under the line may run one final turn, so actual spend can exceed the cap by at most one turn (~€0.01) — acceptable for a soft cap.
- Pricing math lives in `services/advisorBudget.ts` and is unit-tested; the per-MTok rates track the model in `engine.ts`. The legacy `/advisor/:userId/ask` is rule/KB-based (no model call) and is not metered.
- **Monthly cap on all paid AI work** (`USER_MONTHLY_SPEND_CAP_EUR`, default €10, Madrid month, summed from the cost ledger — [Metrics](./metrics.md)). Every route that pays a provider checks it first (`middleware/spendCap.ts` → `429 SPEND_CAP_EXCEEDED`): this chat, `POST /stt`, `POST /tts`, recipe photo/URL import, image regeneration, ingredient auto-create / nutrition estimate. Every WhatsApp turn checks it too. Admins are exempt; a ledger read error fails open. Spoken turns are ordinary chat turns, so they use the same € budget; there is no separate voice-minutes quota since OpenAI Realtime was retired (2026-10-09).

## Multi-dish + notes nutrition

The advisor's weekly nutrient/calorie aggregators iterate `slot.dishes` and process only `kind:'recipe'` entries (see [menus.md "Multi-dish slots"](./menus.md)). Notes contribute zero calories — a user who logs "comemos en casa de Paqui" as a note for lunch will see that meal as 0 kcal in the summary. By design.

## Constraints

- The panel shows the conversation from the browser tab only: sessionStorage `mimo.chat.v1` keeps the last 40 messages across navigation, and a new tab starts empty. Since PRO-148 (2026-10-17) the server also keeps the web chat for 90 days (see «Web chat kept 90 days» below), but nothing reads it back into the panel
- The client sends the last 20 messages as history with each request
- One turn at a time: while Mimo is thinking, a new message is ignored
- All assistant responses are in Spanish by design
- **AI disclosure (EU AI Act art. 50, in force since 2026-08-02):** the panel always shows a caption under the composer ("Mimo es un asistente de inteligencia artificial (IA): puede equivocarse y no sustituye a un profesional sanitario.", `data-testid="ai-disclosure"`), and the empty state introduces Mimo. The wording lives in `AI_DISCLOSURE*` in `packages/shared/src/constants/aiDisclosure.ts`, shared with WhatsApp; pinned by `apps/web/e2e/ai-disclosure.spec.ts`.
- Without `OPENAI_API_KEY`, `POST /stt` answers 503 and only typing works (plus the Web Speech fallback in browsers without MediaRecorder)
- The model used (Claude family) is configured via the LLM provider in `services/providers/`
- The advisor has read-write access to the user's data via skills (it can generate menus, swap meals, create recipes, etc.) — destructive intents are confirmed in copy (see Decisiveness)
- The health rule (PRO-62) is a prompt instruction: the model can still slip. The CI pins the rule, the grader and the engine net, not the model's answers; `scripts/evalHealthAnswers.ts` checks those against the live model and has to be run by hand. The engine only appends the §6 sentence and flags `health_talk`: it doesn't remove body-effect talk from a reply
- The legacy `/advisor/:userId/summary` and `/advisor/:userId/ask` routes remain in the API; no page calls them since `/advisor` became a redirect

## Web chat kept 90 days (PRO-148, D-064)

- Every web turn of `POST /assistant/:userId/chat` (modes `text`, `voice`, `onboarding`) leaves **two rows** in `chat_messages`: the user's own words (without the hidden «Pantalla actual» note; `meta: { mode, path }`) and Mimo's reply with what it did (`meta: { mode, tools, corrections, toolTrace, ms }`, the same trace `whatsapp_messages.meta` keeps). Each row carries the user, their household (`primary_household_id` at that moment) and `channel = 'web'`.
- The route writes them after the model answers (`recordWebChatTurn`, `services/chatMessages.ts`); a failed write is logged and the user still gets the reply. Requests rejected before the model (403, 400, 429 budget) store nothing. The engine is untouched: the trace comes from the engine's response.
- Purpose: the household profile («ficha viva», D-064) learns from the web chat as it already does from WhatsApp. Nothing reads the rows back into the chat: the panel keeps using sessionStorage, and a new tab still starts empty.
- Retention: the scheduler tick deletes rows older than **90 days** once a day (`purgeOldChatMessagesIfDue`, `CHAT_RETENTION_DAYS`). Deleting the account deletes them (FK cascade on `user_id`); if a household is deleted while its member stays, the rows stay with `household_id = NULL`.
- Tests: `apps/api/src/tests/chatMessages.test.ts` (rows + route, engine faked) and `chatMessages.smoke.ts` (purge 91 vs 89 days, account deletion, real Postgres).
- Source: [apps/api/src/services/chatMessages.ts](../apps/api/src/services/chatMessages.ts), table `chat_messages` in [schema.ts](../apps/api/src/db/schema.ts) (migration `0055_chat_messages`), purge call in [notificationScheduler.ts](../apps/api/src/services/notificationScheduler.ts).
