# Authentication

User registration, login, and session management for Mimoia.

## User Capabilities

- Users can register with username, email, and password, plus the required box **«Tengo 14 años o más»** (LOPDGDD art. 7, PRO-23): «Crear cuenta gratis» stays disabled until it's ticked, and `POST /register` answers **400** without `ageConfirmed: true` (`registerSchema`, message «Para usar Mimoia tienes que tener 14 años o más.»). The moment is stored in `users.age_confirmed_at` (migration 0039). There is no sign-up from WhatsApp (it only links an existing account)
- Below it, a **separate, optional, unticked** box «Quiero recibir cada viernes por email una receta de la semana y novedades de Mimoia» (PRO-132; `NEWSLETTER_OPT_IN_LABEL`, consent version `2026-10-17`) with the hint «Te lo recomendamos: te va a sorprender. Opcional; te das de baja con un clic.» (PRO-95). `POST /register { newsletterOptIn: true }` stores `users.newsletter_opt_in`, `newsletter_consent_at` and `newsletter_consent_version` (migration 0047); the account then gets the Friday email (see [Newsletter](./newsletter.md)). The profile has the same switch
- Users can log in with either username or email plus password
- **«¿Has olvidado la contraseña?»** under the password on `/login` → `/recuperar`: they write their email, «Enviarme el enlace» → `POST /auth/forgot { email }` and the page always says «Si hay una cuenta con <email>, te acabamos de mandar un enlace. Caduca en 1 hora. Si no lo ves en unos minutos, mira en la carpeta de spam.», whether or not the account exists. An existing, not suspended account gets the reset email ([Email](./email.md)) with a one-time `/reset?token=…` link valid 1 hour (at most 3 an hour per account); `/reset` sets the new password as before
- Every new account gets a welcome email, beta / household / general ([Email](./email.md)); it never delays or fails the registration
- **From launch day (2026-12-15) signing up starts the 14-day trial without card** (PRO-135): it counts from the creation of the household (beta households: from launch day). Without a plan when it ends, the account is **paused** — it can log in and see everything, but not generate new menus or use Mimo — until someone in the household chooses a plan; nothing is deleted. Before launch day nobody is paused. See [Billing](./billing.md)
- Logged-in users receive a JWT token used for subsequent API calls
- Users can log out (clears local token; no server-side invalidation)
- Newly registered users are redirected to onboarding before accessing the app
- Existing users with completed onboarding go directly to `/menu` after login
- Registering with an email that is on the pre-launch [waitlist](./waitlist.md) (waiting or invited) marks that entry `joined` — fire-and-forget, it never blocks or fails the registration
- `/login` and `/register` honour `?next=<path>`: after success the user lands on `next` instead of `/menu` / `/onboarding`. Only same-origin relative paths are accepted (`safeNext`: must start with `/`, not `//` or `/\`, no newlines), so it can't become an open redirect. The "Crear cuenta" / "Inicia sesión" cross-links carry `next` along. Used by `/whatsapp/conectar`, `/invites/[token]`, the private-recipe notice and the signed-out redirect of every protected page (see "Public vs Protected Routes").
- Sign out: «Salir» at the bottom left of the desktop sidebar (`md+`, Miguel 2026-10-21) and in Perfil → «Tu cuenta» (mobile). Both clear the session and this device's cached data and go back to the landing (`logout` in `lib/auth.tsx`)

## Closed beta (PRO-27)

- `REGISTRATION_MODE` (`invite` by default, `open` to open on launch day; CI's smoke job and staging run `open`). The public web reads it from `GET /public/config` (`{ registration }`, no auth; PRO-167) and, with `open`, sends every public call to action to `/register` ([Waitlist](./waitlist.md) «Open registration»). In `invite`, `POST /register` only creates an account when one of these holds, else **403 `REGISTRATION_INVITE_REQUIRED`** («Mimoia está en beta cerrada…»):
  1. `inviteCode` = a **campaign invitation link** that exists, isn't expired and has uses left (one use is taken atomically);
  2. `waitlistToken` = the **one-time link of a waitlist invitation** (PRO-97): `mimoia.com/entrar/<token>` (`app/entrar/[token]/route.ts`) → `/register?entrada=<token>`. The page asks `GET /waitlist/invite/:token` who it is for, shows «¡Te toca, <nombre>! Vienes de la lista de espera.» and fixes the email (read-only, «Es el correo de tu invitación: no se puede cambiar.»). On submit the API checks the link is valid, unused and for that email, and uses it up atomically with the account (given back if the insert fails). Errors, in Spanish: used → **410 `WAITLIST_INVITE_USED`** («ya se ha usado… inicia sesión», the page shows it with a link to `/login` and the button disabled); unknown → 403 `WAITLIST_INVITE_NOT_FOUND`; another email → 403 `WAITLIST_INVITE_EMAIL_MISMATCH`. An **invited email without the link is rejected** with 403 **`WAITLIST_INVITE_LINK_REQUIRED`** («…crea tu cuenta desde el botón «Crear mi cuenta» del correo…»). Exception: entries invited before PRO-97 (no link exists) still get in with the email alone. In `open` mode a link is optional, but if sent it is checked and used up the same way;
  3. `householdInviteToken` = an unconsumed, unexpired household invitation (`/invites/:token`) — this path must never break;
  4. the email is in `ADMIN_EMAILS`.
- Campaign links: `mimoia.com/i/<code>` (`app/i/[code]/route.ts`) → `/register?campana=<code>`; the form sends it as `inviteCode` (kept in `sessionStorage.ona.campana` across a /login detour). The household path comes from `?next=/invites/<token>`. A valid campaign is recorded on the account (`users.invite_campaign_id`, table `invite_campaigns`, migration 0042) in either mode. Created and listed in `/admin` → Invitaciones ([Admin](./admin-dashboard.md)); counted in `GET /admin/metrics` → `campaigns` ([Metrics](./metrics.md)).
- **«Invitar a otro hogar» and attribution (PRO-162):** every account has its own invitation code, in the waitlist's format (`users.referral_code`, unique, migration 0053); someone who came from the waitlist keeps their list code, so what they already shared still counts. It is assigned on sign-up (or the first time it's asked for): `GET /referrals/me` (auth) → `{ code, link }`, link `<web>/?invita=<code>`. The landing remembers `?invita=`, `?ref=` and `utm_*` in the browser for 30 days (`lib/signupAttribution.ts`, `localStorage.ona.signupAttribution`) and `/register` sends them (its own URL first) as `invitedBy`, `signupSource`, `utmSource`, `utmMedium`, `utmCampaign`. The API stores the inviter's **code** (`users.invited_by_code`, never their email) when the code belongs to an account or an active waitlist person, it isn't the same person (same email) and they aren't joining the inviter's own household (a member, not another home); `?ref`/`utm_*` go to `users.signup_attribution`. A bad or unknown code never fails the sign-up — it is just not stored. With registration closed, `?invita` still leads to the waitlist as before (see [Waitlist](./waitlist.md)); with `REGISTRATION_MODE=open` the invited person signs up directly. Tests: `accountReferrals.test.ts`, `accountReferrals.smoke.ts` (real API + DB), e2e `invite-link.spec.ts` (390×844).
- **«Invitar a otro hogar» button (PRO-163, D-059):** in Perfil (under the six cards, apart from Casa's «Invitar a alguien», which brings someone into *this* household, PRO-118) and under the shopping list (`components/referrals/InviteHouseholdButton.tsx`, `data-testid="invite-household-perfil"` / `"invite-household-compra"`): «¿Conoces otra casa a la que le vendría bien? Mándale tu enlace para que pruebe Mimoia.» and **«Invitar a otro hogar»**, which opens `https://wa.me/?text=` with Miguel's text A (`inviteHouseholdShareText`, `@ona/shared`): «Yo uso Mimoia para el menú de la semana: le escribes por WhatsApp y te lo hace, con la lista de la compra. Pruébalo con mi enlace: <enlace>» (Legal reviews it before publishing). On a computer (`md+`) also **«Copiar»** (the same message to the clipboard). Each tap → `POST /usage/invite-shared` (auth, 204) → one `invite_shared` event, no props ([metrics.md](./metrics.md)). Mimo does the same with `share_invite_link` ([advisor.md](./advisor.md)). Tests: e2e `invite-household-button.spec.ts` (390×844), `appSkills.test.ts`.

- Tests: `inviteCampaigns.test.ts` (gate + per-campaign counts), `waitlistInvites.test.ts` (the link), e2e `waitlist-invite.spec.ts` (link fixes the email, creates the account, reuse is an error, invited email without link rejected) and `closed-beta.spec.ts` (the four paths; the e2e API runs `invite` and `global-setup.ts` creates the «e2e» campaign every spec signs up with).

## Onboarding (post-registration)

- Onboarding is required before any in-product page (menu, recipes, shopping, Mimo) is meaningful
- The `users.onboardingDone` flag tracks completion
- **«Afina tu menú» first (PRO-146, [taste.md](./taste.md)):** right after creating the account and before the WhatsApp/web choice, 10 recipe cards («Dime qué te *apetece*.», «Saltar» always visible, never blocks); shown once (`users.taste_state.onboardingAt`), so a reload continues with what comes next
- The web onboarding collects: household composition (`adults` + `kidsCount` for children aged 2–10; under 2 doesn't count, over 10 counts as adult; with 2 adults or more, once, the step offers to prepare the invitation for the other person — PRO-261, see [Household](./household.md) → «Ofrecer la invitación»), cooking frequency, **«¿Cómo cocináis en casa?»** (PRO-217, D-069: «Cocino cada día» · «Cocino unos días y aprovecho para otros» · «Batch cooking: cocino una o dos veces y dejo hecha la semana» · «Improviso: decido cada día»; one tap, required; under it, optional, «¿Congeláis la carne o el pescado cuando compráis?» — «Sí, casi siempre» · «A veces» · «No» → `freezesMeatFish`, a habit in `prep_habits`, PRO-221, see [User memory](./user-memory.md); sent as `cookingStyle` and saved in the household's ficha as `cooking_style`, origin onboarding — see [Ficha del hogar](./household-profile.md); the draft keeps it; `e2e/onboarding-cooking-style.spec.ts` at 390×844), **«Entre semana, ¿cómo te gusta cocinar?»** (PRO-138: «Rápido · En media hora, a la mesa» = 30 min in total Mon–Fri, «Poco rato de trabajo · Aunque luego se haga solo» = 20 min of work Mon–Fri, «Sin prisa» = no limit; the weekend is always «sin prisa»; stored as `time_available` in the memory, see [Menus](./menus.md) → Time to cook) with an optional «¿Algo más? Cuéntanos tu caso» field (`cookingNote`, ≤ 500 chars, read by the AI into the memory and, since PRO-242, the weekly template's diners («a mediodía mi hijo come en el instituto entre semana» → one diner less at weekday lunch); the first menu waits for that read at most 15 s — see [User memory](./user-memory.md) — and kept as `users.onboarding_note` for the household ficha's daily signals, PRO-151; `users.onboarding_completed_at` records the first time the answers were saved, web or WhatsApp — see [Ficha del hogar](./household-profile.md)), dietary restrictions, nutritional priority (six steps since PRO-217; five after PRO-146 removed the three favourite dishes: `favoriteDishes` is optional in `onboardingSchema`, default `[]`, up to 30 — no cap of 5 since PRO-155 — and «Me encanta» replaces it; `e2e/onboarding-cooking-time.spec.ts` at 390×844). Dietary restrictions are health data: the step shows the separate, unticked health-data consent box and only stores them when it's ticked (`healthConsent: true` in the body records the consent) — see [Privacy](./privacy.md) → Health-data consent (PRO-21)
- Until `onboardingDone = true`, the landing page redirects authenticated users to `/onboarding`
- **Left halfway, resumed (PRO-178, 2026-10-18).** Every «Siguiente» of the web questions saves the step reached and the answers so far on the account (`PUT /user/:id/onboarding-draft`, `onboardingDraftSchema` in `@ona/shared`, column `users.onboarding_draft`, migration 0068; returned as `onboardingDraft` by `GET /user/:id`; ignored once onboarded, cleared when the sign-up is saved, web or WhatsApp). Coming back — any device, after logging out — `/onboarding` skips the WhatsApp/web choice (unless WhatsApp is already linked) and opens on that step with those answers. Allergies and restrictions are never in the draft (health data, stored only with the consent at the end), so a sign-up left on the last question resumes on «¿Hay algo que no comas?» (step 4). An unfinished sign-up with no draft (left before this, or on the choice) starts at «1 de 5» as before
- **`/menu` without the sign-up finished goes to `/onboarding` (PRO-178).** Logging in (which lands on `/menu`), the welcome email's «Abrir Mimoia» and any link to `/menu` used to show «Tu semana está en blanco» and «Generar mi menú» — a menu without the answers. `/menu` now waits for `GET /user/:id` → `onboardingRequired` when the browser doesn't already know the account as onboarded (no extra request otherwise) and, if true, replaces itself with `/onboarding` without loading or creating the week. `onboardingRequired` is false for an account that finished the sign-up (also when it finished on WhatsApp or another device: the browser's copy is updated) and for a **member who joined someone else's household** by invitation (they read that household's menu; `needsOnboarding` in `services/onboarding.ts`; since PRO-271 they're asked their allergies and diet right after accepting, see [Household](./household.md) → «Alergias y dieta al entrar en una casa»). A failed check never blocks the menu, **nor one still unanswered after 8 s** (`API_SLOW_MS`; the installed app on Windows sat on a near-empty «Cargando...» after signing up, 2026-10-21 — a late «pending» answer still goes to `/onboarding`) (`hooks/useOnboardingGate.ts`; `e2e/desktop-windows.spec.ts`, tests `apps/api/src/tests/onboardingDraft.test.ts`, `e2e/onboarding-resume.spec.ts` at 390×844) Only the answer fetched for that visit counts: an earlier visit's cached «pending» (an account that logged in, landed on `/menu` and then finished the sign-up) used to send it back to `/onboarding` and loop `/menu` ↔ `/onboarding` for good (a beta tester, 2026-10-22); finishing the sign-up (web or WhatsApp) also writes «done» into the gate's cache (`markOnboardedInCache`; not into `/onboarding`'s, which still shows the WhatsApp sign-up's «Tu menú está listo»), and `/onboarding` shows «Cargando...» instead of the questions while an onboarded account is on its way to `/menu`.
- **WhatsApp first (2026-10-10):** when WhatsApp is available for the account (`GET /whatsapp/status` → `available`), `/onboarding` opens on «¿Dónde quieres hablar principalmente con *Mimo*?» («Puedes usar Mimoia tanto desde WhatsApp como desde la web. Te haremos un par de preguntas donde elijas, y así vas viendo cómo se usa.», 2026-10-15) with **«Por WhatsApp» (recomendado)** and «Prefiero la web». WhatsApp mints the one-time code (same linking as `/whatsapp/conectar`: «Enviar desde WhatsApp» opens the chat with «Vincular Mimoia: XXXXXX» written); once the phone sends it the page shows «Mimo te está escribiendo» + «Abrir WhatsApp» and polls `GET /user/:id` until `onboardingDone`, then shows «Tu menú está listo» (allergies with the health-data consent; adding something rebuilds the week — PRO-161, [WhatsApp](./whatsapp.md)) and «Ver mi menú» goes to `/menu`. Mimo asks the first steps in the chat and builds the first menu (`complete_onboarding`, see [WhatsApp](./whatsapp.md)); health data is never asked there. «Prefiero la web» (also reachable from either WhatsApp screen) runs the classic six questions, and «Atrás» on the first of them returns to the choice. Already linked and not onboarded → straight to «Mimo te está escribiendo». Not available → the classic questions, as before (`OnboardingWhatsApp.tsx`, `e2e/onboarding-whatsapp.spec.ts`)
- Finishing onboarding generates the user's **first real menu** for the current week (`POST /menu/generate`) before landing on `/menu`, built from those answers. **Friday to Sunday (Europe/Madrid wall clock) it also generates the next week**, one after the other, and lands on `/menu?week=<next Monday>` (PRO-65; `firstMenuWeeks` in `@ona/shared`, `apps/api/src/tests/firstMenuWeeks.test.ts`, `e2e/first-menu-next-week.spec.ts`). **The first menu starts on the sign-up day (PRO-244):** the client sends `fromDate` (today, Madrid) and the days of the current week that already went by are not generated — they stay without dishes (not «sin cocinar»), add nothing to the list and can still be filled by hand. `/onboarding` only redirects to `/menu` by itself when the user was already onboarded on arrival, so it doesn't race that navigation. The WhatsApp onboarding (`complete_onboarding`) follows the same rule since PRO-244: from today on, plus the whole next week Friday to Sunday (`apps/api/src/tests/firstMenuWhatsApp.test.ts`). It used to land on an auto-created empty week. The client marks the user onboarded only **after** that generate answers (button "Preparando tu menú..."): marking it first let `/onboarding`'s "already onboarded" redirect reach `/menu` before the menu existed, and `/menu` auto-created an empty week on top (fixed 2026-10-08, guarded by `e2e/registration-onboarding.spec.ts`, which now sees the "Tu semana está en blanco" card). An already-onboarded user who opens `/onboarding` goes straight to `/menu`. If generation fails, `/menu` still offers "Generar mi menú"
- **Primeros pasos on `/menu` (PRO-07, 2026-10-11).** The first time a new account reaches `/menu` (once the current or a future week has loaded — a weekend sign-up lands on next week), three steps over the real screen, each lighting up its element with the rest dimmed: «Toca «···» en un plato para cambiarlo» (the «···» options button of the day's featured dish — tapping the dish itself opens the recipe; changing it goes through «···»; PRO-68, 2026-10-13; if the day has no dish yet, the first «···» on screen — an empty slot's; read-only, the whole dish), «Aquí tienes la lista de la compra: se hace sola» (the «Compra» tab, or the sidebar link on desktop), «Este es Mimo: pídele lo que quieras» (Mimo's floating button). Closing calls `POST /user/:id/first-steps` and it never comes back, on any device. Stored on the account, not the browser: `users.first_steps_pending` (migration 0044, `NOT NULL DEFAULT false`), returned as `firstStepsPending` by `GET /user/:id`. **Only `POST /register` writes `true`**, so every account created before the column existed (and any row inserted another way) counts as already seen — no backfill, no existing data touched. ## Profile data shape

The `users` table holds the canonical scalar fields (`sex`, `age`, `weight`, `height`, `activityLevel`, `adults`, `kidsCount`, `cookingFreq`, `restrictions`, `favoriteDishes`, `priority`, `onboardingDone`). `users.householdSize` is a deprecated text column kept only as a backfill source for users registered before migration 0005; new code reads `adults` + `kidsCount` and writes `householdSize = null` on every save. The `user_settings.template` JSONB column stores the richer profile-page state as a single blob: `{ physical, preferences, mealTemplate }`. The `/profile` page reads/writes both: scalar fields go through `PUT /user/:id`, and the rich blob goes through `PUT /user/:id/settings`. Restrictions are kept in both places (`users.restrictions`, which onboarding writes and the menu generator reads, and `preferences.restrictions` in the blob): the profile shows the **union** of the two (trimmed, lowercased, deduped — `unionRestrictions` in `@ona/shared`), so a diet or allergy picked in onboarding appears ticked, and saving writes that same list to both, never dropping either side (PRO-64; `apps/web/e2e/profile-restrictions.spec.ts`).

## Roles and suspension

- `users.role` is `'user' | 'admin'`. Default `'user'`. On every login the server reconciles role against the `ADMIN_EMAILS` env var (case-insensitive): matches are upgraded to admin, ex-admins removed from the env are downgraded.
- `users.suspended_at` is set by the admin via `/admin/users` (see [User Management](./user-management.md)). Login rejects suspended users with `code: 'SUSPENDED'`. Existing JWTs of a suspended user are invalidated at the per-request `requireAuth` check.
- The auth context client-side carries `role` next to `userId` so the navbar can render the admin entry without an extra fetch. The server still re-checks role on every privileged request — the client value is decoration.

## Constraints

- Username and email are both unique across users (registration returns 409 if either exists)
- Passwords are stored hashed with bcrypt (10 rounds)
- JWT tokens are signed with `JWT_SECRET` and expire after `JWT_EXPIRES_IN` (default `90d` — "long but not infinite"). On expiry the API returns `401` with `code: 'TOKEN_EXPIRED'`; the web client treats that like `USER_NOT_FOUND` (wipes local auth, bounces to `/login`). Tokens issued before expiry was introduced never expire — they age out as users re-login. A token with a bad signature or malformed (e.g. after `JWT_SECRET` is rotated) returns `401` with `code: 'INVALID_TOKEN'`, handled the same way.
- A deployed API (`NODE_ENV=production` or running on Railway) **refuses to boot** when `JWT_SECRET` is missing or shorter than 32 characters (`config/jwtSecret.ts`); locally it falls back to `ona-dev-secret`. Rotating the secret logs every user out once.
- `POST /register`, `/login`, `/auth/reset` and `/auth/forgot` are rate-limited per client IP (in-memory fixed window): register `10/hour`, login + reset `20 / 5 min`, forgot `5 / 15 min`. `POST /auth/forgot` answers `200 { ok: true }` at once for any valid email (the email goes out in the background, so neither the answer nor its timing says whether the account exists); 400 `INVALID_EMAIL` for a malformed one. Over the limit returns `429` with `code: 'RATE_LIMITED'` and a `Retry-After` header. The limiter is per-process (approximate across restarts/instances) and relies on `app.set('trust proxy', 1)` to read the real client IP behind Railway's edge. Test harnesses (CI + `apps/web/scripts/test-e2e.sh`, whose Playwright specs register one user per test from localhost) switch the limiters off with `RATE_LIMIT_DISABLED=true`; the flag is **ignored on a deployed API** (same `isDeployedRuntime` check as `JWT_SECRET`: `NODE_ENV=production` or running on Railway), so production limits can't be disabled by env. See `middleware/rateLimit.ts`.
- Login with invalid credentials returns 401 (no distinction between "user not found" and "wrong password")
- Login with a suspended account returns 403 with `code: 'SUSPENDED'`
- All in-product API routes require the JWT in `Authorization: Bearer <token>` header
- `requireAdmin` middleware extends `requireAuth` for admin-only endpoints — see [Roles & Authorization](./roles.md)

## Public vs Protected Routes

**One rule (2026-10-15):** every page needs an account unless it is on the open list in `lib/routeAccess.ts`. A signed-out visitor on any other page goes to **`/login?next=<path+query>`** once the session has resolved (`RootShell` paints an empty cream page meanwhile, so the wrong page never flashes), and logging in brings them back there (`safeNext`). New pages are protected by default; unknown URLs signed out land on `/login` too. Before, signed out, `/menu`, `/profile` and `/advisor` hung on «Cargando...», `/shopping` and `/compra` were blank and `/recipes/new` showed a form that couldn't save. Tests: `apps/api/src/tests/routeAccess.test.ts` (the lists), `e2e/app-signed-out.spec.ts`.

**Open** (no account needed):
- Marketing and legal: `/`, `/como-funciona`, `/precios`, `/blog`, `/blog/[slug]`, `/privacidad`, `/terminos`, `/aviso-legal`
- `/login`, `/register` — `/register` stays reachable for invited households, but no public CTA links to it pre-launch (they lead to the [waitlist](./waitlist.md))
- `/recuperar` (ask for the link), `/reset` (password recovery) and `/invites/[token]` (household invitation) — drawn like `/login` (no sidebar, bottom bar, Mimo button or desktop left margin), also for a signed-in user
- `/lista/[code]`, `/lista/baja` (waitlist), `/newsletter/baja`, `/offline` (service-worker fallback)
- Link handlers (`route.ts`): `/i/[code]` (campaign), `/entrar/[token]` (waitlist invitation), `/c/[token]` (shop-order short link)
- **Open, chrome by session** (signed out: public chrome PublicNavbar + Footer on the public grid; signed in: the app shell): `/recipes` (the public catalogue, see [Recipes](./recipes.md) → "Catálogo público"), `/recipes/[id]` and `/recipes/[id]/cook` (catalogue recipes; cook mode full-screen; a private recipe answers «Esta receta es privada.» — API `GET /recipes/:id` uses `optionalAuthMiddleware` and 404s private recipes without a token), `/whatsapp/conectar` (signed out: «Entra en tu cuenta de Mimoia (o créala)…» with login/register links carrying `?next=`; see [WhatsApp](./whatsapp.md))
- `/recipes-ona` and `/recipes-ona/[id]` are permanent redirects to `/recipes` and `/recipes/[id]`

**Protected** (everything else; signed out → `/login?next=…`; signed in, the app shell unless noted):
- `/menu`, `/menu/history`, `/shopping`, `/compra`, `/compra/tiendas`
- `/recipes/new`, `/recipes/[id]/edit`, `/cookbooks/[id]`
- `/profile` and every `/profile/*` page
- `/advisor` — no longer a page (D-023): a client redirect to `/menu?mimo=1`, which opens Mimo. Mimo itself is the floating button on every protected page (see [Advisor](./advisor.md))
- `/onboarding`, `/onboarding/voz` — full-screen, without the app shell
- `/admin` — admin dashboard, also gated by `requireAdmin` (see [Admin Dashboard](./admin-dashboard.md)). The old `/curator` route 301-redirects here.
