# Menus · Cómo se genera el menú

> Parte de [Menus](./menus.md) (la portada lista todas las partes): el algoritmo, lo que lee de la ficha, la puerta de calidad del catálogo, lo que el hogar ha dicho del menú, las recetas «de diario» y el tiempo de cocina.

## Generation Algorithm

The generator (`menuGenerator.ts`) uses iterative optimization:

1. Loads user profile (sex, age, weight, height, activity level), restrictions, and favorites. The meals, diners and dishes come from the household's **semana tipo** (below), whoever generates; a household that never touched it has **lunch + dinner** every day (breakfast is opt-in). Onboarding answers count too (`onboardingPreferences.ts`): recipes sharing a word with a *favourite dish* get the favourites' 2× weight (legacy: the web sign-up stopped asking for favourite dishes with PRO-146), and priority **Rapidez** or cooking **Poco** caps Mon–Fri at 30 min **in total** when the user has no `time_available` memory (an empty one — the onboarding's «Sin prisa» — means no limit). Since 2026-11-03 the sign-up asks neither: «Poco» is what batch cooking stores (`cookingFreqForStyle`), which matters for the WhatsApp sign-up (no time question there); the web sign-up always leaves a `time_available`, and the priority only comes from Perfil or Mimo. Priority *Ahorro*/*Variedad* and cooking *3-4 veces* don't change the generator yet. **«¿Qué tal?» ratings** (PRO-111, `services/householdRatings.ts`): a recipe the household rated 5 («Repetir a menudo») gets the favourites' weight; one rated 1 («Mejor no») never comes out in the automatic menu — the weekly generator, «Cambiar al azar», an added meal and a regenerated dish — but can still be picked by hand («Elegir otra receta», Mimo naming it). 2–4 stars change nothing. The 1-star recipes are not added to the week's «Vetadas» list. Tests: `householdRatings.test.ts`. **«Afina tu menú» verdicts** (PRO-146, [taste.md](./taste.md), same `loadHouseholdRatingSets`): «No para mí» from anyone in the household never comes out in the automatic menu (beats 5 stars and another member's «Me encanta»), «Me encanta» weighs like a favourite, «Me apetece» gets ×1.5 on its rounded pool weight in the weekly generator (`LIKE_WEIGHT`, `likedRecipeIds`; the draw is now weighted rather than duplicated copies, same odds as before for everything else). Tests: `taste.test.ts`
2. Loads every recipe the user can see — system catalogue + their own + their household's (never another user's private recipes, see [Recipes → Recipe visibility](./recipes.md)) — with ingredient names and cached `nutritionPerServing`
3. Calculates a target calorie count using BMR × activity × number of meal slots
4. Detects current season
5. Runs up to **200 iterations**, each time:
   - Builds a candidate menu by picking a random matching recipe per slot (skipping locked slots)
   - Scores each candidate using **real per-serving nutrition** from `recipe.nutritionPerServing` × the user's `householdSize / recipe.servings` ratio
   - Fitness (lower is better, in percentage points) = ½ × calorie deviation + macro deviations (carbs/fat/protein vs `TARGET_MACROS`) + **Mimoia's opinion** (`metabolicScore.ts`, the former kb/10 mandamientos — insulin and inflammation over calories; internal to the generator, never shown or said to the user; Mimo's prompt now carries `kb/principios-mimo.md`): 3 × 100 × (1 − metabolic quality) + 0.5 × 100 × (1 − plant variety). Quality = mean per-recipe score from ingredient names (+ plants, oily fish, olive oil, fermented; − refined carbs/sugar, processed meats and seed oils). Variety = distinct plants / 20 per week. **Seasonality is read from the ingredients too** (Spanish calendar, `SEASONAL`): in-season produce +0.1, out-of-season −0.15 (±0.3 cap). The season tags are unreliable (26 of 56 prod recipes are tagged all four seasons). Measured on the local catalogue: menu quality from −0.08 to +0.14 on average, at a cost of ~3 macro points (2026-10-07)
   - Keeps the best (lowest fitness) menu seen so far; stops early if fitness drops below `OPTIMAL_FITNESS`

Recipes whose `nutritionPerServing` is not yet cached (e.g. unmapped ingredients) fall back to the legacy ingredient-name heuristic and are deprioritized when better-data alternatives exist.

For each meal slot, the matcher (`recipeMatcher.ts`) filters recipes by:
- Recipe's `meals[]` includes the target meal type
- Recipe's `seasons[]` includes current season (or is empty = always-available)
- Recipe ID is not already used elsewhere in the menu (no repeats within the week)
- **One main protein per day (PRO-238, 2026-10-19):** lunch and dinner of the same day don't share the main protein (`mainProteinOf` in `menuGenerator.ts`, the classification of `tasteDeck.ts`: carne, pescado, legumbre, huevo; «verdura» never blocks). Only main/single dishes count, locked slots included. If nothing else fits the slot, the same protein is allowed. Why: «lentejas estofadas» for lunch and «lentejas guisadas» for dinner the same Sunday (two recipes, so the no-repeat rule let it through). **Tests:** `tests/menuSameProtein.test.ts`.
- The recipe doesn't break the user's **restrictions** (allergies, diets, free text) or **dislikes** — see *Restrictions & allergies* below
- **Equipment filter — appliances only (PRO-1140, Miguel 2026-11-05):** the household's `equipment` list (memory, else the ficha's `equipment` fact) takes a recipe out only when the recipe needs an **appliance** the list doesn't have. The vocabulary is a closed list in `@ona/shared` (`constants/equipment.ts`): **appliances** (`KITCHEN_APPLIANCES`: horno, freidora de aire, freidora, robot de cocina/Thermomix, microondas, olla express/exprés/rápida, olla de cocción lenta, batidora, batidora de varillas/amasadora, picadora/procesador, plancha eléctrica, sandwichera, gofrera, tostadora, panificadora, yogurtera, heladera, deshidratador, roner) and **basic utensils** (`BASIC_UTENSILS`: fuegos, sartén, wok, plancha, cazuela, olla, cazo, paellera, bol, fuente, bandeja, molde, tabla, cuchillo, varillas, rallador, vaporera, papel de horno…), which every kitchen is taken to have. A line matches a name when it is that name or starts with it («Horno precalentado» → horno, «Cazuela de barro» → utensil, «Bandeja de horno» → utensil); appliances first, longest name first, so «olla express» is never «olla». A word in neither list **doesn't filter** and is counted for Cocina in `scripts/auditCatalogRecipes.ts` («Equipo que no es aparato ni utensilio de la lista», `unknownEquipmentCounts`). The household's list is read the same way (its utensils are ignored); an empty or absent list = no filter. Equipment the ficha says is missing right now (next bullet) compares appliances by their canonical name too. Same rule in the smart menu's checker (`checkPlan`). Nothing stored changes. Why: a household with 5 appliances (and no sartén, cazuela, bol or olla in its list) kept 17 recipes and got the same menu every week. Tests: `equipmentAppliances.test.ts` (5-appliance household over the 2026-10-22 catalogue with equipment and times set by rule: ≥ 60 recipes within 30 minutes, two weeks in a row share ≤ 4 of 14 dishes)
- **The household's ficha** (PRO-253, [Ficha del hogar → Who reads the ficha](./household-profile-aprende.md)): equipment a fact in force says is missing right now («Sin horno hasta nuevo aviso», «el horno está roto») takes out every recipe that needs it — even for a household without an equipment list — and the dislikes of every member and an ingredient the household rejects (affinity −2) join the user's dislikes. Weekly generation and every «Aleatorio» / add-course path (`withFichaFilters`, `services/profile/reader.ts`); no ficha or a read error = today's filters only
- **What the menu reads from the ficha** (PRO-1201, Miguel 2026-11-12: «que se tenga en cuenta la ficha del cliente para todo»). Filters: allergies and diets of every member (Restrictions below), dislikes of every member and affinity −2, equipment and equipment missing right now (above), time per day (Time to cook), the «semana tipo», the comunidad autónoma's holidays, the school menu. Weights of the draw (they never take a recipe out): favourites, «Me encanta» and 5 stars ×2, «Me apetece» ×1.5, the fresh fridge, and since PRO-1201:
  - **Cuisines they like** (`cuisine_bias`, cuisine → 0–100; Mimo asks in the sign-up and in the chat), against the recipe's internal tag `cocina:<slug>`: 80–100 **×1.5** (like a «Me apetece», less than a favourite), 40–79 ×1, 0–39 **×0.15** (much less, never out); a recipe without the tag or a cuisine nobody names ×1 — so Spanish and Mediterranean stay neutral unless they are named. A family covers its cuisines and back («asiática» → japonesa, china, tailandesa, coreana, india…; «mediterránea» → española, italiana, griega; «latinoamericana» → mexicana, peruana…), the cuisine itself wins over its family. Whole household, like the dislikes: the generating member's memory plus every member's `cuisine_bias` fact; per cuisine, if anyone is under 40 the lowest wins, else the highest.
  - **Cook's level** (`cooking_skill`): «easy» **×0.1** on a `difficulty: hard` recipe, «medium» ×0.7, «advanced» or none ×1. The generating member's (memory, else their fact in the ficha), else the household's.
  - Both on the rounded weight (`tasteWeight`, `services/menuTastes.ts`; `MatcherOptions.tastes`, built by `withFichaFilters` + `memoryTastes`), in the weekly generator (the sign-up's first week too, the autopilot), «Cambiar» / «Aleatorio», adding a meal or a course, regenerating a dish and the review of saved menus (`menuSlotPick.ts`). Without a ficha, the same draw as before. Tests: `recipeMatcher.test.ts` (1,000 draws: «asiática: 20», «mexicana: 90», «easy»; no ficha), `profileReader.test.ts` (household merge).
- **Catalogue quality gate** (PRO-73, Miguel 2026-10-13, answer C): a system recipe is skipped while it has no steps, 2 ingredients or fewer, a main protein per serving under 80 g or over 300 g (meat, fish, seafood, eggs, tofu added up; cured meats and yolks are garnish and don't count), or pasta/rice/dry pulses per serving under 50 g or over 150 g. The two quantity ranges are for a lunch or dinner main: a dessert (`course: dessert`) or a recipe only for breakfast or a snack (crêpes, flan, arroz con leche) skips them (`skipsQuantityRanges`, 2026-10-20, so the eggs of a dessert don't hold it back). The 80 g protein **minimum** doesn't apply to a starter (`course: starter`: «Ensalada César», «Paté de bacalao») nor to a dish with rice, legumes or pasta as its base, dry or cooked («Garbanzos con espinacas y huevo», «Arroz al horno», «Fideos caldosos con mejillones», «Espaguetis con almejas»; not green beans, flours, rice vinegar, «pasta de curry» or pastry doughs such as «pasta brisa» or «pasta filo») — there the meat, fish, seafood or egg goes with the dish (Miguel, 2026-10-21; pasta and noodles since PRO-338, 2026-10-23; `proteinMinimumApplies`, `hasRiceOrLegumeBase`); the 300 g maximum still does. A household whose ficha has a `protein_minimum` fact about any member («proteína en cada plato»; today only Miguel's, written by hand until «Tu ficha» lets people say it) keeps the minimum everywhere, pasta included: the loader reads the household ficha (`loadFichaMenuConstraints`, [Household profile](./household-profile.md)). Migration 0088 added it as a `users` column and 0089 drops it: «todo lo que sabemos de un usuario está en su ficha» (D-064). Computed on read in `matchableRecipes.ts` (`catalogAuditIssues`, rule in `catalogRecipeAudit.ts`); nothing is written, so a recipe comes back as soon as Cocina fixes it. Users' own recipes are never audited. Applies to every `matchRecipes` path (weekly generation, «Aleatorio», add-course, the assistant's random swap); not to `suggest_recipes`, the «Elegir otra receta» picker or an explicitly named recipe. A unit weight the catalogue doesn't know (e.g. «dorada 2 u») never flags (eggs default to 55 g). Bone-in cuts, whole fish and shellfish in their shell count their edible grams, stock bones none (`ingredients.edible_fraction`, PRO-194, PRO-281, PRO-282, see [Nutrition](./nutrition.md) → Edible weight); a line noted «peladas», «sin concha» or «en lomos» counts whole. Read-only report: `scripts/auditCatalogRecipes.ts` (`--seed`, `--fixture=`, or a `DATABASE_URL`). On the 2026-10-15 catalogue (78 recipes) it flags 28 (32 with the strict minimum); full lunch+dinner weeks remain with no restrictions in every season and in autumn also for vegetarian or gluten-free; vegetarian + gluten-free drops to ~10 of 14 in autumn, and vegetarian to ~9 in spring/summer, until the vegetarian fixes land (`catalogRecipeAudit.test.ts`)

## Lo que el hogar ha dicho del menú (2026-11-19)

Three weeks of conversations: Mimo answered «lo tendré en cuenta» and the next menu didn't (rice after «prescindir del arroz», four legume dishes after «que no me sugieras legumbres», «patatas guisadas» and «oreja» after «cenas ligeras»). Mimo saved them as a free note the generator never read. Now (`menuRules.ts`, read by `fichaMenuConstraints` / `withFichaFilters`):

- **«Sin X»** joins the dislikes (a family counts whole, see Restrictions).
- **Weekly limits** («arroz no más de un día a la semana», «lentejas dos veces como mucho»): the ficha's `menu_rule {rule: max_per_week, target, times}`. A dish counts when its name or an ingredient has that food (a family counts whole); once the week has that many, no more are drawn (hard; locked and preset dishes count).
- **Light meals** («cenas ligeras»): `menu_rule {rule: light, meal}`. That meal draws from light dishes first (`isLightDish`: no stew, legume dish, fry, pizza, cured pork, offal, ≤ 600 kcal when known); only when none fits, another (warning `light_short_…`).
- **What was saved as text** before: the household's `notes` and `nutrition_principles` (ficha and memory) and a style `affinity` are read with fixed patterns (`rulesFromNotes`): only foods and families it knows, a cap with a number is a limit, «sin», «no me sugieras», «prescindir de», «evitar»… an avoid, «cenas ligeras» a light dinner. «No me gusta que repitas…» is not an avoid.
- **Never a sweet as lunch or dinner** (`isSweetDish`: course dessert, a «postre»/«dulce» tag, a cake-like name, or sweet ingredients with nothing savoury), except as the dessert of a 3-dish meal (`findForCourse`).
- Which meals are cooked and how many dishes («6 cenas y 1 comida», «las cenas, primer y segundo plato») live in the semana tipo (`set_week_type_slot` with `off` and `dishes`).

## Recetas «de diario» y el arranque (PRO-1200)

Why (Miguel, 2026-11-12): a new household has no favourites, «Me apetece» or stars, so the matcher drew from the whole catalogue and, with the catalogue growing with blogs and creators, a first menu could bring katsudon. The first menus should look like what that home already eats.

- **The tag:** internal tag `diario` (`EVERYDAY_RECIPE_TAG`, `isEverydayRecipe` in `@ona/shared`, next to `RETIRED_RECIPE_TAG`; public tags count too), set by Cocina (COC-513). With no `diario` recipe in the catalogue the household sees, everything works as before (`everydayPolicy` → null).
- **Arranque (starting):** the household has fewer than **2 other weeks with a menu** (distinct `menus.week_start`, same household/user scope as favourites, the week being generated aside) **or fewer than 5 signals** (recipes with a favourite, a «Me apetece» or «Me encanta» of any member, or 4-5 stars; each recipe once). A read error counts as starting. `loadIsStarting` in `services/everydayMenu.ts`.
- **While starting,** every drawn dish — the weekly generator (`buildRandomMenu`: free dishes, dishes of a week-type type, the fridge dish) and every automatic change through `menuSlotPick.ts` («Cambiar», «Que elija Mimoia» with or without a type chip, the week-type draw, the review when restrictions change) — picks only among the `diario` recipes that pass the usual filters; in the generator this goes before the «not the same protein at lunch and dinner» preference. A slot none fits takes the whole catalogue (never an empty slot for this).
- **After starting,** at most **2 dishes a week from outside `diario`** («para descubrir», `DISCOVERIES_PER_WEEK`), drawn with the usual weights; once the week has them, the rest keep to `diario` (same fallback). In a single change, the rest of the week's dishes say how many are left (`slotEveryday`).
- **What the household chose never counts as outside** and is never held back: favourites, 5 stars and «Me encanta», «Me apetece», onboarding favourite dishes; locked slots and the week type's concrete recipes are not drawn. The fridge dish (PRO-229) prefers `diario` while starting and is not counted after.
- **By hand, nothing changes:** «Elegir otra receta», the search and Mimo naming a recipe can put any recipe.
- Tests: `everydayMenu.test.ts` (invented catalogue: a new household only gets `diario`; a slot none fits gets another; past starting, at most 2 from outside; favourites don't count; no `diario` → the same menu as before).

## Time to cook (PRO-138)

- A day's limit comes from `time_available[weekday]` in the memory (`weekTimeBudgets` / `dayTimeBudget`, `@ona/shared` `types/cookingTime.ts`): either **in total** («Rápido: en media hora, a la mesa», or a plain number as Mimo writes it) or **of work** («Poco rato de trabajo, aunque luego se haga solo»). The weekly generator and every single-slot path (Cambiar al azar, add a meal, regenerate) apply it.
- The matcher (`recipeMatcher.ts`, step 6, `fitsTimeBudget`): a «total» day compares `totalTime` (else `prepTime + cookTime`); a «trabajo» day compares `activeTime` (else `prepTime`). **With a limit, a recipe without that time does not pass** (until 2026-10-17 it always passed and only `prepTime` was compared, so a 3-hour stew with 20 min of prep reached a 30-minute Tuesday). Without a limit every recipe passes. A cocido with 15 min of work and 200 in total fits a «20 min de trabajo» day. Tests: `recipeMatcher.test.ts`, `onboardingPreferences.test.ts`.
- Catalogue times: on every boot (`db:migrate`) and at the end of `db:seed`, `catalogRecipeTimes.ts` fills **only empty** times of system recipes: Cocina's prep/cook/total for the 10 recipes that had none, `totalTime = prepTime + cookTime` when missing, and `activeTime` from the steps (sum of hands-on steps; simmering, oven, resting, marinating, soaking, cooling (enfriar), fridge (nevera, frigorífico), freezing, «templar», rising (levar), fermenting and boiling with minutes («Cuece a fuego medio 40 minutos») don't count — the last ones since PRO-187; a hands-on step without minutes → `prepTime`; never above the total). Each filled recipe is logged as `[catalog-recipe-times] «…»: … trabajo N (de pasos|de preparación) min` for Cocina to review, plus a «N de M recetas del sistema con tiempo total y de trabajo» line. **Recompute (PRO-187):** a system recipe whose stored `activeTime` is exactly what the rule before PRO-187 gave (`computeActiveTimeLegacy`) gets it recomputed with the new rule (e.g. one hour in the fridge + 10 min of cutting: 70 → 10), logged as `[catalog-recipe-times] «…»: trabajo A → B min (recalculado con la regla nueva, …)`; any other value (set by hand or by Cocina) is never touched, and the write only applies if the value hasn't changed since the read. User recipes are never touched. Tests: `catalogRecipeTimes.test.ts`.
- **Realistic totals (PRO-284, 2026-10-21):** Miguel found the totals too long (cooking them took ~20 % less). Right after the fill, on every boot and at the end of `db:seed`, `recipeTimeTrim.ts` (`applyCatalogTimeTrim`) recomputes the times of system recipes: **total** = prep + cook − overlap, where the overlap is the prep done while a step goes by itself (the same passive steps as above; up to half the prep, never more than those steps' minutes; soaking the day before doesn't count) — never below `cookTime` nor the passive steps' minutes, never above the old total — except to count the waits (PRO-1078: resting, rising, the fridge…; see [Recipes](./recipes.md) → `totalTime`); **prep** × 0.8 once per recipe (internal tag `tiempos-pro284`, which a `PUT` keeps); **hands-on** drops by what the prep dropped, never above the total. `cookTime` is never changed. Idempotent: a second boot changes nothing, and a total an admin edit puts back to prep + cook is recomputed. Each recipe is logged `[catalog-time-trim] «…»: preparación A → B · total A → B · trabajo A → B min (cocción N, sin cambios; …)` for Cocina, plus a summary with **how many recipes now fit a 30-minute limit** by total and by hands-on time, and the mean total of the recipes of up to 45 min before → after. The time limits of the menu read these new values, so short days now take recipes that didn't fit before. A recipe saved by the batch import gets the total rule and the tag at once (its prep comes from the rewriter, told to estimate for someone who cooks with ease and to count prep done meanwhile only once). User recipes are never touched. Tests: `recipeTimeTrim.test.ts`, `recipeTimeTrim.smoke.ts`.
