# Menus

Weekly meal plan generation and management.

## User Capabilities

- Users can generate a weekly menu (Monday–Sunday) for the current week or any future week with one click. A week with no dishes (new or emptied) shows a "Tu semana está *en blanco*" card with **"Generar mi menú"** above its empty slots; otherwise **Regenerar semana**
- The **first menu** is built when the web onboarding ends: the current week, plus the next one when onboarding finishes Friday to Sunday (Madrid time), and `/menu` then opens on the next week (PRO-65, see [Auth](./auth.md))
- **Layout "D · Luz y foto"** (2026-10-08). The header is compact: eyebrow "Semana del 5 al 11 de octubre", h1 "Hoy, *jueves*" (or "Mañana, *viernes*" / "*Viernes* 9" for another day), and one **"···"** that opens the **week sheet**. There is no greeting, "Nº", or progress bar. Week actions live in that sheet; every per-meal action lives behind the meal's own "···" (the **meal sheet**). Nothing is lost: each action below says where it lives
- Users can move between weeks with **‹ ›** beside the week range in the page header ("Semana anterior" / "Semana siguiente", mobile and desktop, since 2026-10-10), or from the week sheet (‹ › around "Esta semana" / "Próxima semana" / "Semana pasada" / "En N semanas" / "Hace N semanas", plus "Volver a esta semana"), or by editing `?week=YYYY-MM-DD`. On another week a "<label> · volver a hoy" link sits under the h1. The selected day resets to today (current week) or Monday
- Past weeks are read-only. Meals stay visible (with "Empezar a cocinar"), but the "···" buttons, Regenerar, Vaciar and Generar are hidden. A past week without a menu reads "Sin menú esta semana. Esta semana ya pasó. Vuelve a la actual para planificar."
- **Vista día** (mobile default) shows one day. A day strip (L M X J V S D + date; selected = ink pill, today in terracotta, "sin cocinar" days struck through) switches the day. The day's **featured meal** (the first one, chronologically, that holds a recipe) is a full-bleed photo with an overlapping caption card: eyebrow "Comida · 28 min · 3 raciones", the title (links to the recipe), an ink pill **"Empezar a cocinar"** (→ `/recipes/:id/cook?servings=N`) and "···". The other meals are rows (photo, eyebrow "Cena · 25 min", title → recipe, "···"). An empty slot is one quiet **"Añadir plato"** card (opens AddDishSheet) + "···". A meal the rest of the week has and this day lacks (no slot; `absentMeals`: at least half of the cooked days have it, and two at least, so a household that never has lunch at home sees nothing) is a dashed card **«El viernes no hay comida»** + «Añadir» (creates the slot, like «Añadir comida → Comida»; 2026-10-19, a day's dinner passed for its lunch). Below the meals: **"Añadir comida"** and **"Saltar día"**. If the featured recipe has no photo (or it fails to load) the hero drops the image area: the caption is a normal card at the top with the meal's small icon on a bone square, and the name appears once. Other photo-less recipes get a bone block with the small meal icon, never a grey placeholder or a second copy of the name. **Eaten meals (PRO-185):** a slot with `eaten` (Mimo's `mark_meal_eaten`, or «Marcar como cocinada» on the web) shows «✓ Comido» where «Empezar a cocinar» was, plus a «Ver receta» button (hero), or a «✓ Comido» chip (rows); a note-only slot («Cenamos fuera») shows its text once, as the title, not again as «+ Cenamos fuera»
- **Vista semana** (mobile; toggled from the week sheet, persisted in `localStorage.ona.menu.view`) is a vertical stack of day sections (`WeekGridView`). Each has a sticky header (tap = that day in Vista día), rows with thumbnail, meal eyebrow, `shortRecipeName` title and time chip, and on mount it scrolls today into view. **Drag-and-drop**: drop a row on another to swap the two slots via `POST /menu/:menuId/move-slot` (`pointerWithin`; drops outside rows are no-ops). Each row's portalled "..." menu offers Elegir receta, Aleatorio, Añadir plato, Bloquear/Desbloquear, Vetar receta and Quitar slot. Notes edit inline. Skipped days show "Reactivar"
- **Meal sheet** (single-recipe slot): Ver receta, **Elegir otra receta** (`RecipePickerSheet`, the catalogue minus what breaks the user's allergies or diet — `GET /recipes?fitsMe=1`, with the line «Solo salen las recetas que encajan con tus alergias y tu dieta.» — with "Mimoia"/"tuya" badges and name search; pins via `PUT /menu/:menuId/day/:day/meal/:meal` `{ recipeId }`; 0 results offers **"Crear receta «<query>»"** → `/recipes/new?name=<query>` and, from the meal sheet, **«Usar "<query>" como plato»**, which replaces the slot's dishes with that text as a note — keeping «Solo hoy» — instead of adding a note next to the dish, PRO-74), **Cambiar al azar** (matcher), **Añadir plato** (AddDishSheet), **Tipo de comida**, **Fijar/Desfijar**, **Vetar esta receta**, **Marcar como cocinada** (cook log with menu/day/meal context, and the slot is marked eaten via `PATCH /menu/:menuId/day/:day/meal/:meal` `{ eaten: true }`, which sets `eaten` + `eatenAt` like Mimo; on an eaten slot it becomes **Desmarcar** → `{ eaten: false }`, back to «Empezar a cocinar», PRO-185), the **Comensales** stepper and **Quitar <comida>**. Multi-dish and note slots show a "Platos" list instead (drag to reorder, "Cambiar" per dish, quitar, edit notes) plus Añadir plato, Fijar, Comensales and Quitar. Empty slots get Añadir plato, Fijar, Comensales and Quitar. While a slot is locked ("Fijada" chip), every change except Desfijar is disabled. Regenerations and lock toggles are queued offline; offline replay of a manual pick loses its `recipeId` (the server auto-picks)
- **Confirmations** (PRO-72): «Saltar día», «Quitar <comida>» / «Quitar slot», «Vetar esta receta» / «Vetar receta» and «Vaciar semana» ask in the app's own `ConfirmSheet` (a `MenuSheet` with "Cancelar" + the action), never the browser's `window.confirm`: in-app and automated browsers don't always show that window and count it as «Cancelar», so the action silently did nothing (test households, 2026-10-11/14). Guarded by `apps/api/src/tests/menuNoNativeConfirm.test.ts` (no `confirm(` under `components/menu/` or `app/menu/`) and `e2e/menu-confirm-sheets.spec.ts` (fails on any native dialog)
- **Imprimir la semana** (PRO-112): the week's «···» sheet (`WeekActionsSheet`, when the week has a menu) has «Imprimir la semana» → `/menu/imprimir?week=YYYY-MM-DD`. The page previews an A4 landscape sheet: «Menú · semana del …», the 7 days as columns and one row per meal the week has (dish names — recipes and written dishes — and the first recipe's minutes), with «Mimoia» discreet in the corner. «Incluir la lista de la compra» (ticked by default) adds a second sheet with the week's shopping list by aisle (items in stock left out; `GET /shopping-list?from=<lunes>&to=<domingo>`), each with a ☐ to tick on paper. «Imprimir» opens the browser's print dialog, which also saves as PDF; the toolbar and the app chrome don't print (`@page A4 landscape`). Nothing is generated on the server. Logic in `lib/printWeek.ts`; e2e `print-week.spec.ts`
- Users can shape a single week without touching their preferences. **Quitar <comida>** removes the slot (`DELETE /menu/:menuId/day/:day/meal/:meal`), and the day's **"Añadir comida"** opens a sheet («Añadir comida al jueves») listing the meals the day lacks (`POST …/meal/:meal`; the matcher picks a recipe, and when none fits — no breakfast in the catalogue, or all used this week — the meal is added **empty**, with «Añadir plato», instead of the old 404 that left the button doing nothing). Both apply to **this menu only**: the profile's `mealTemplate` is untouched, so next week follows the original preferences
- Users can override the diner count for one slot with the meal sheet's **Comensales** −/+ stepper ("Solo hoy · Quitar"). It is persisted as the slot's `servings` (`PATCH /menu/:menuId/day/:day/meal/:meal` `{ servings: number | null }`; `null` clears). Changing the slot's dish keeps it: the web picker and «Aleatorio» (`PUT …/meal/:meal`, dish routes) and Mimo's `swap_meal` (`slotWithDishes`, PRO-102: the Ruiz family's «Solo hoy: 4» went back to 5 after a swap with Mimo). `sumDinersByRecipe` in `shoppingList.ts` sums per-slot diners, so repeated recipes with different overrides scale independently. The caption's "N raciones", the dish's link to its recipe (`/recipes/:id?servings=N`; the detail opens at N) and the cook link use the **batch** (`batchServings` in `lib/menuDay.ts`, PRO-75): the override, else the household size plus each planned leftover of that meal
- Users can **veto** a recipe for the rest of the week: **Vetar esta receta** → confirm ("Vetar"). It goes into `menu.banned_recipe_ids` and the slot it was in gets another recipe at once (the web chains `POST /menu/:menuId/ban` with an Aleatorio of that slot, PRO-72; other days that already hold it keep it; vetoing with Mimo changes every appearance from today on, see [advisor.md](./advisor.md) `ban_recipe_this_week`, PRO-113), and the matcher excludes it from every later Aleatorio / Elegir-without-recipe / Añadir / whole-week regenerate. A collapsible "Vetadas esta semana" panel under the day lists each veto with "Levantar veto". Vetoes carry over when `POST /menu/generate` re-runs for the same week
- Users can mark a whole day **"sin cocinar"** with **"Saltar día"** (confirm: «¿Marcar <día> como sin cocinar?» → "Saltar día"). This empties every non-locked slot and persists the index on `menu.skipped_days`; whole-week regenerate skips the day. The day then shows "Día marcado sin cocinar." + **"Reactivar día"**, which only clears the flag (slots are re-added by hand or Aleatorio). Skipped days carry over across regenerates
- Users can **fix a meal type** with **Tipo de comida** → a sheet of 10 tags (Cremas, Legumbres, Pizza, Asiático, Mediterráneo, Ensalada, Parrilla, Batch cooking, Pasta, Arroz). Aleatorio / Elegir-without-recipe then only pick recipes whose `tags` include it (`PATCH … { pinnedType: MEAL_TYPE_TAGS | null }`). The pin survives recipe swaps and "Quitar pin" clears it. An empty intersection returns 404 with a Spanish hint
- **Note dishes** ("comemos fuera", "+ pan") are edited inline: in the meal sheet's "Platos" list (Vista día / desktop) and in Vista semana rows. Enter / blur persists via `PATCH /menu/:menuId/day/:day/meal/:meal/dish/:position` `{ text }`, and Esc reverts
- Users can mark a slot as a **leftover** from a previous slot via `POST /menu/:menuId/day/:targetDay/leftover`, body `{ sourceDay, sourceMeal, targetMeal }`. The target slot is cloned with `kind: 'leftover'` and a `leftoverOf` back-reference; the shopping-list aggregator collapses the repeated `recipeId` onto the source row. The leftover does **not** copy the source's `servings` (PRO-75): with «Solo hoy: N» on the source, N already covers the táper; without it, the leftover counts the household's diners (see [Shopping](./shopping.md) → `withLeftoverBatches`). The meal shows a terracotta "Sobras de [día] [comida] · ya en la compra" chip instead of «Solo hoy: N» (Vista semana drops its «N pax» chip) and its sheet hides Elegir / Cambiar al azar / Tipo / Vetar, since the leftover is tied to its source. *UI affordance to trigger the endpoint from the card itself is deferred to a follow-up — the endpoint is available for the assistant via the voice skill.*
- Users can put a **táper from the freezer** in a meal (PRO-82): **Añadir comida → Del congelador** (in the day footer's sheet; asks «¿Para qué comida?» when the day lacks more than one meal, then the same recipe picker as «Elegir otra receta»). It saves a recipe dish with `variant: 'freezer'` (`POST …/meal/:meal/dish { kind: 'recipe', recipeId, variant: 'freezer' }`), linked to its recipe, with the chip «Del congelador · no suma a la compra» (Vista semana: «Congelador» on the thumbnail). It never adds to the shopping list, whatever week the original was cooked in (see [Shopping](./shopping.md)); its sheet hides Elegir / Cambiar al azar / Tipo / Vetar, prep alerts skip it, it can't be the source of planned leftovers, and Mimo's menu text says «(del congelador)». Mimo does the same with `add_freezer_dish` ([Advisor](./advisor.md))
- Users can regenerate the whole week from the week sheet / desktop header (**Regenerar semana**). It re-runs the algorithm and keeps locked slots. **Vaciar semana** (week sheet, confirm) keeps them too
- Users can share the week as text with a link (**Compartir** in the week sheet in both views; desktop: **Compartir semana**) via `menuShareText`
- Users can view past menus via `/menu/history` (**Historial** in the week sheet): one paper card per saved menu ("Semana del 5 al 11 de octubre", creation date, up to four `RecipeCover` thumbnails of its recipes — photos first, "+N" when there are more; `lib/menuHistory.ts`), linking to `/menu?week=<weekStart>`. Thumbnails reuse the per-week menu query of `/menu` (one `GET /menu/:userId/:weekStart` per distinct week)
- Users can tap a meal photo or title to open the recipe detail
- Users can opt in to local meal-time notifications (breakfast / lunch / snack / dinner times configured in the profile's "Recordatorios" card) — the app fires a reminder at the chosen times — see [PWA](./pwa.md)

## Multi-dish slots

Each `MealSlot` holds `{servings?, dishes: Dish[]}` where every `Dish` is either a `RecipeDish` (`{kind:'recipe', recipeId, recipeName?, course?, pinnedType?, variant?, leftoverOf?, imageUrl?, prepTime?, totalTime?}`) or a `NoteDish` (`{kind:'note', text}`). The list is ordered and the order is what the UI renders — there's no semantic role per position.

Per-meal-type dish count lives in `userSettings.template.mealDishCounts: { breakfast?: 1|2|3, lunch?: 1|2|3, dinner?: 1|2|3, snack?: 1|2|3 }`. Default 1. The generator maps:
- `1` → matcher restricted to `course IN ('main') OR course IS NULL` (single-plate convention; starters and desserts are auto-skipped).
- `2` → `[starter, main]`.
- `3` → `[starter, main, dessert]`.

When a course has no candidates, the generator emits a warning `no_<course>_available_<meal>_d<dayIndex>` in the `POST /menu/generate` response and produces fewer dishes for that slot. The UI can surface the warning list as a toast.

Notes are excluded from the matcher and added only via manual UI (`+ Añadir plato` → "Añadir nota") or `POST /menu/:menuId/day/:day/meal/:meal/dish` with `{kind:'note', text}`. Notes contribute zero to shopping list and nutrition aggregation.

### Dish-level routes

All under `/menu/:menuId/day/:day/meal/:meal/dish` and gated by the `:menuId` IDOR guard (400 non-UUID / 404 unknown / 403 foreign — see "Access control" below):

- `POST` — append a dish. Body discriminated by `kind`: `{kind:'recipe', recipeId, course?, pinnedType?}` or `{kind:'note', text}` (text ≤120 chars).
- `DELETE /:position` — remove. Subsequent positions decrement; empty `dishes[]` is allowed (slot remains, UI shows "+ Añadir plato" placeholder).
- `PATCH /:position` — `{text?, pinnedType?, newPosition?, course?}`. Precedence: if `newPosition` is present, it's the only operation (pure reorder); otherwise patches text/pinnedType/course. Fields that don't apply to the dish kind are silently ignored.
- `POST /:position/regenerate` — Aleatorio on one dish; respects its `course`. 400 on note dishes; 409 when no candidates match.

### Slot-level vs dish-level state

- **Slot-level** (unchanged surface): `servings`, `locked`, slot-DnD move (whole slot moves between (day, meal) via `POST /move-slot`).
- **Per-dish**: `course`, `pinnedType`, `variant: 'planned' | 'leftover' | 'freezer'`, `leftoverOf.dishPosition`, in-slot reorder via `PATCH .../dish/:position {newPosition}`.

`POST /menu/:menuId/day/:day/meal/:meal/leftover` clones only the recipe dishes of the source slot (notes are skipped — they don't propagate as "leftovers").

`PUT /menu/:menuId/day/:day/meal/:meal` (regenerate-meal) re-picks **only the recipe dishes** of the slot, preserving each dish's `course` and any `NoteDish` entries at their positions.

## Menu Structure

A menu is stored per-user per-week:
- `weekStart` is the Monday of the week (`YYYY-MM-DD`)
- `days` is a 7-element array; each day is `{ breakfast?, lunch?, dinner?, snack? }`
- Each filled slot is `{ recipeId, recipeName, servings?, pinnedType?, kind?, leftoverOf?, imageUrl? }` — `imageUrl` is **not** persisted in the JSONB; the API resolves it per request from the joined `recipes.image_url` so a regenerate-image takes effect on the very next response. `servings` is the optional per-slot diner override; `pinnedType` is one of MEAL_TYPE_TAGS (`'cremas' | 'legumbres' | 'pizza' | 'asiatico' | 'mediterraneo' | 'ensalada' | 'parrilla' | 'batch-cooking' | 'pasta' | 'arroz'`) that constrains the matcher's candidate pool; `kind: 'leftover'` plus `leftoverOf: { day, meal }` marks a slot cloned from another via the leftover endpoint.
- `locked` is a nested object: `{ "<dayIndex>": { "<meal>": true } }`
- `bannedRecipeIds` is a string-array of recipe ids the user vetoed this week; the matcher excludes them across every regeneration call. Carries over when the user re-runs `POST /menu/generate` for the same week.
- `skippedDays` is an integer-array (0-6) of day indices the user marked "sin cocinar"; whole-week regenerate leaves these days empty (no slots get inserted).

## Generation Algorithm

The generator (`menuGenerator.ts`) uses iterative optimization:

1. Loads user profile (sex, age, weight, height, activity level), restrictions, and favorites. The meal template defaults to **lunch + dinner** every day (breakfast is opt-in from the profile's plantilla). Onboarding answers count too (`onboardingPreferences.ts`): recipes sharing a word with a *favourite dish* get the favourites' 2× weight (legacy: the web sign-up stopped asking for favourite dishes with PRO-146), and priority **Rapidez** or cooking **Poco** caps Mon–Fri at 30 min **in total** when the user has no `time_available` memory (an empty one — the onboarding's «Sin prisa» — means no limit). Priority *Ahorro*/*Variedad* and cooking *3-4 veces* don't change the generator yet. **«¿Qué tal?» ratings** (PRO-111, `services/householdRatings.ts`): a recipe the household rated 5 («Repetir a menudo») gets the favourites' weight; one rated 1 («Mejor no») never comes out in the automatic menu — the weekly generator, «Cambiar al azar», an added meal and a regenerated dish — but can still be picked by hand («Elegir otra receta», Mimo naming it). 2–4 stars change nothing. The 1-star recipes are not added to the week's «Vetadas» list. Tests: `householdRatings.test.ts`. **«Afina tu menú» verdicts** (PRO-146, [taste.md](./taste.md), same `loadHouseholdRatingSets`): «No para mí» from anyone in the household never comes out in the automatic menu (beats 5 stars and another member's «Me encanta»), «Me encanta» weighs like a favourite, «Me apetece» gets ×1.5 on its rounded pool weight in the weekly generator (`LIKE_WEIGHT`, `likedRecipeIds`; the draw is now weighted rather than duplicated copies, same odds as before for everything else). Tests: `taste.test.ts`
2. Loads every recipe the user can see — system catalogue + their own + their household's (never another user's private recipes, see [Recipes → Recipe visibility](./recipes.md)) — with ingredient names and cached `nutritionPerServing`
3. Calculates a target calorie count using BMR × activity × number of meal slots
4. Detects current season
5. Runs up to **200 iterations**, each time:
   - Builds a candidate menu by picking a random matching recipe per slot (skipping locked slots)
   - Scores each candidate using **real per-serving nutrition** from `recipe.nutritionPerServing` × the user's `householdSize / recipe.servings` ratio
   - Fitness (lower is better, in percentage points) = ½ × calorie deviation + macro deviations (carbs/fat/protein vs `TARGET_MACROS`) + **Mimoia's opinion** (`metabolicScore.ts`, the former kb/10 mandamientos — insulin and inflammation over calories; internal to the generator, never shown or said to the user; Mimo's prompt now carries `kb/principios-mimo.md`): 3 × 100 × (1 − metabolic quality) + 0.5 × 100 × (1 − plant variety). Quality = mean per-recipe score from ingredient names (+ plants, oily fish, olive oil, fermented; − refined carbs/sugar, processed meats and seed oils). Variety = distinct plants / 20 per week. **Seasonality is read from the ingredients too** (Spanish calendar, `SEASONAL`): in-season produce +0.1, out-of-season −0.15 (±0.3 cap). The season tags are unreliable (26 of 56 prod recipes are tagged all four seasons). Measured on the local catalogue: menu quality from −0.08 to +0.14 on average, at a cost of ~3 macro points (2026-10-07)
   - Keeps the best (lowest fitness) menu seen so far; stops early if fitness drops below `OPTIMAL_FITNESS`

Recipes whose `nutritionPerServing` is not yet cached (e.g. unmapped ingredients) fall back to the legacy ingredient-name heuristic and are deprioritized when better-data alternatives exist.

For each meal slot, the matcher (`recipeMatcher.ts`) filters recipes by:
- Recipe's `meals[]` includes the target meal type
- Recipe's `seasons[]` includes current season (or is empty = always-available)
- Recipe ID is not already used elsewhere in the menu (no repeats within the week)
- The recipe doesn't break the user's **restrictions** (allergies, diets, free text) or **dislikes** — see *Restrictions & allergies* below
- **Catalogue quality gate** (PRO-73, Miguel 2026-10-13, answer C): a system recipe is skipped while it has no steps, 2 ingredients or fewer, a main protein per serving under 80 g or over 300 g (meat, fish, seafood, eggs, tofu added up; cured meats and yolks are garnish and don't count), or pasta/rice/dry pulses per serving under 50 g or over 150 g. Computed on read in `matchableRecipes.ts` (`catalogAuditIssues`, rule in `catalogRecipeAudit.ts`); nothing is written, so a recipe comes back as soon as Cocina fixes it. Users' own recipes are never audited. Applies to every `matchRecipes` path (weekly generation, «Aleatorio», add-course, the assistant's random swap); not to `suggest_recipes`, the «Elegir otra receta» picker or an explicitly named recipe. A unit weight the catalogue doesn't know (e.g. «dorada 2 u») never flags (eggs default to 55 g). Bone-in cuts count their edible grams (`ingredients.edible_fraction`, PRO-194, see [Nutrition](./nutrition.md) → Edible weight). Read-only report: `scripts/auditCatalogRecipes.ts` (`--seed`, `--fixture=`, or a `DATABASE_URL`). On the 2026-10-15 catalogue (78 recipes) it flags 32; full lunch+dinner weeks remain with no restrictions in every season and in autumn also for vegetarian or gluten-free; vegetarian + gluten-free drops to ~10 of 14 in autumn, and vegetarian to ~9 in spring/summer, until the vegetarian fixes land (`catalogRecipeAudit.test.ts`)

### Restrictions & allergies

`services/dietaryRestrictions.ts` compiles each entry once per call. Restrictions come from the profile (`users.restrictions`) **and** long-term memory (`user_memories.restrictions`, e.g. "soy celíaco" told to the assistant), merged by `mergeRestrictions`.
- **Allergies** ("sin gluten", "sin lactosa"/"sin lácteos", "huevo", "frutos secos" (also excludes peanuts), "cacahuetes", "marisco" (crustaceans + molluscs), "pescado", "soja", "apio", "mostaza", "sésamo", "sulfitos"…, with prefixes like "alergia a…", "intolerante a…", "soy…" stripped, so «soy celíaco» told to Mimo is the gluten rule and «soy vegetariana» the diet, PRO-197) map to EU allergen tags. A recipe is out if the tag appears in its `allergens` union, in any ingredient's catalogue `allergen_tags` or `contains_tags`, or in the name-based inference (`inferAllergenTagsFromName`, conservative).
- **Diets**: "vegetariano" (no meat or fish/seafood, by curated whole-word ingredient terms + fish tags), "vegano" (also no dairy, egg, honey, gelatine), "pescetariano", "sin carne", "sin cerdo", "halal" (pork + the alcohol rule below).
- **«Sin alcohol»** (PRO-144, beta 2026-10-16: a household with a 3-year-old got «Riñones al jerez»): a chip in onboarding and the profile; also understood as «nada de alcohol», «cocinamos siempre sin alcohol», «sin bebidas alcohólicas». Skips every recipe with an alcoholic drink among its ingredients — vino, jerez, cerveza (also «sin alcohol»), sidra, brandy, coñac, licor, ron, oporto, vermut, cava, champán, whisky, ginebra, vodka, mirin, sake… — even when it could be left out (the wine of a sofrito): better too many than too few. Whole words («ron» ≠ «ronqueta», «cava» ≠ «cavar»); vinegars («vinagre de vino / de Jerez / de sidra») and «levadura de cerveza» don't count. It is the only rule that also reads the **recipe name** («Carrilleras de ternera con vino tinto», whose stored ingredients omit the wine). `ALCOHOL_TERMS` / `nameHasAlcohol`; over the catalogue fixture it hides exactly 5 recipes (`dietCatalog.test.ts`). Like every restriction it is stored in `users.restrictions` and so, today, only with the health-data consent and never from WhatsApp.
- **Prudent rules** (PRO-61, Miguel 2026-10-12, after the hogares de prueba got «Costillas a la riojana», «Ropa vieja del cocido», a pizza with «Harina de fuerza» and «Arroz tres delicias» with «Salsa de soja»): a false positive costs a recipe, a false negative a reaction. *Meat* also covers cuts and offal named without the animal («Costillas», «Rabo», «Oreja», «Riñones», «Morcillo», «Hueso de caña», «Entraña»…), the dish «cocido» (an ingredient starting with «Cocido» or saying «del/de cocido» — «garbanzos cocidos» stays vegetarian), «Ropa vieja», and Worcestershire sauce (anchovies). *Gluten* covers any flour, pasta, noodle, semolina or dough that doesn't name a gluten-free base (arroz, maíz, garbanzo, almendra, trigo sarraceno, mandioca), soy sauce/tamari/shoyu unless «sin gluten», beer, malt, Worcestershire, biscuits, puff pastry, batter; anything labelled «sin gluten» never counts. Rules live in `inferAllergenTagsFromName` (allergens) and `MEAT_TERMS`/`FISH_TERMS` (diets). Checked over the whole catalogue (fixture of the 78 system recipes, `dietCatalog.test.ts`): generated weeks with «vegetariano» or «sin gluten» never contain a recipe that breaks them.
- **Compound ingredients** (PRO-198, el recién llegado 2026-10-17: «sin cerdo» got «Ropa vieja del cocido», whose «Sobras del cocido madrileño» names no pork): each tag of an ingredient's `contains_tags` («cerdo», «pollo», «gluten», «alcohol»…) counts like a word of its name for diets, free text, dislikes and «sin alcohol», and like a catalogue allergen tag for allergies. So «sin cerdo» and «halal» skip the ropa vieja (and anything with «Caldo de cocido», generic sausages or «Foie gras de untar»), «vegetariano» skips a stock labelled «pollo», and «vegetal» never excludes. Who labels what: [Nutrition → What a compound ingredient contains](./nutrition.md) (`compoundIngredients.test.ts`)
- Known false positives kept on purpose: «panceta» and «pasta de curry/miso» count as gluten (substring rules). Known data gap: a recipe whose ingredient list omits the animal (e.g. «Arroz al caldero» = «Arroz, Ajo») can't be caught; recipe names are not checked (except by «sin alcohol»).
- **Anything else** ("cilantro", "picante") and every **dislike** are whole-word, accent/case-insensitive, plural-tolerant ingredient terms ("cebolla" excludes "cebolla morada" and "cebollas", not "cebollino").
- Before 2026-10-07 this was an exact ingredient-name match, so allergies and diets filtered nothing.
- Every path that picks recipes on Mimoia's own initiative applies it (also «Afina tu menú», with every household member's restrictions and vetoes and the recipe name, PRO-197, [taste.md](./taste.md)): weekly generation, "Aleatorio" slot regenerations, add-course, and the assistant's random swap and `suggest_recipes`. Those paths all load through `services/matchableRecipes.ts`. An explicitly named recipe (assistant `swap_meal` by name) that breaks an allergy/diet is **not placed**: the tool returns the conflict and the model must get the user's confirmation (`confirmRestriction: true`). Dislikes still yield to explicit requests. The menu's **«Elegir otra receta»** picker hides recipes that break an allergy or diet (`GET /recipes?fitsMe=1`; dislikes are not hidden there). A recipe id sent straight to `PUT /menu/…/meal/:meal { recipeId }` is not re-checked.
- The onboarding and profile chips share one list, `RESTRICTION_PRESETS` (`@ona/shared`), and a test checks that every preset compiles to a real rule.

Then picks one at random from the pool. **Favorites get double weight** — they appear twice in the random pool.

## Single-Meal Regeneration

`PUT /menu/:menuId/day/:day/meal/:meal` replaces one slot:
- Refuses if that slot is locked (returns 400)
- Excludes recipes already used in the rest of the week from the candidate pool
- Applies the same restriction/season/favorites logic
- Returns 404 if no matching recipe is available

## Manual Slot Shaping (per-week overrides)

The user can adapt one week without editing the saved `mealTemplate`:

- `POST /menu/:menuId/day/:day/meal/:meal` (auth) — add a slot the template didn't include. Optional body `{ recipeId }`; if absent the matcher picks one. Returns **409** when the slot already exists (use PUT to replace it instead), **404** when the matcher can't find a recipe, **201** + the updated menu otherwise.
- `DELETE /menu/:menuId/day/:day/meal/:meal` (auth) — drop the slot for this week. Refuses with **400** when the slot is locked, **404** when the slot doesn't exist. The user's `mealTemplate` is **not** mutated, so next week starts fresh.
- `PATCH /menu/:menuId/day/:day/meal/:meal` (auth) — partial update for slot metadata. v1 only honours `{ servings: number | null }`: a positive integer (1–24) sets a per-slot diner-count override, `null` clears it. The override is consumed by the shopping-list aggregator and ignored by the recipe matcher. Returns **400** on out-of-range servings, **404** when the slot is empty.
- `POST /menu/:menuId/move-slot` (auth) — atomic move/swap of a slot to another day/meal. Body `{ fromDay, fromMeal, toDay, toMeal }`. Empty target → move (source slot becomes empty). Occupied target → swap. Locked source or target → **400**. Used by the drag-and-drop in "Vista semana" so the client doesn't sequence DELETE + POST and risk leaving the menu half-mutated. Each slot travels whole («Solo hoy» included), and every leftover that points at a moved slot (`leftoverOf`) is repointed to its new place, so the moved dish still cooks the táper and the list counts it the same (PRO-102, `moveSlotInWeek` in `services/menuDishes.ts`; before, Laura's Monday curry for 2 moved to Thursday and its táper still pointed at the empty Monday). Mimo's `move_meal` goes through this route.

The recipe matcher and the per-week locks are unaffected by manual shaping.

## Lock Behavior

`PUT /menu/:menuId/day/:day/meal/:meal/lock` toggles `locked[day][meal]`:
- Locked slots (with vetoes and "sin cocinar" days) carry into every new row for the week: `POST /menu/generate` (regenerate and "Vaciar semana") and the assistant's `generate_weekly_menu`, via `services/menuWeek.ts`. The assistant's `generate_weekly_menu` never remakes a week that already has dishes unless the user confirmed it (`replaceExisting: true`), and its dish tools edit the menu of the week the named day falls in, not the newest row (PRO-63, see [Advisor → Conventions](./advisor.md)). Before 2026-10-07 regenerate wrote `locked: {}` and the locked dishes were lost. Their recipes go into `usedRecipeIds` first, so the rest of the menu doesn't repeat them
- **No accidental wipes**: `empty: true` over a week that has dishes → **409 `MENU_NOT_EMPTY`** unless `force: true`. Only the confirmed "Vaciar semana" sends `force`. The /menu page auto-creates an empty week only on a real 404 (`ApiError.status`). A failed GET (500, offline) shows "No hemos podido cargar tu menú" + "Reintentar" and never writes. Covered by `menuWeekRoute.smoke.ts` + `e2e/menu-load-failure.spec.ts`

## Registro de cambios (PRO-149)

Cada cambio de los platos de un menú deja filas en `menu_edits` (migración `0056_menu_edits`), una por receta que sale o entra: hogar, menú, día (0-6), comida, acción, receta de antes y de después (id y nombre copiado), quién (`user` | `mimo`), canal (`web` | `whatsapp`) y fecha. Es la señal de la ficha viva del hogar (D-064): «quitó el ceviche y puso tortilla». **Generar el menú no es un cambio** (`POST /menu/generate` y `generate_weekly_menu` no escriben).
- Acciones por ruta: `PUT …/meal/:meal` y `…/dish/:position/regenerate` → `swap` (o `add` si el hueco estaba vacío); `POST …/meal/:meal`, `…/dish` y `…/dish/random` → `add` (`freezer` con `variant: 'freezer'`, PRO-82); `DELETE …/meal/:meal` y `…/dish/:position` → `remove`; `POST /ban` → `ban` (sin día, receta en «antes»); `POST …/leftover` → `leftover` (con `from_day`/`from_meal`); `POST /move-slot` → `move` (una fila por receta que cambia de sitio, en las dos direcciones si se intercambian); `POST …/skip` → `skip_day` (una por receta quitada, o una sin receta si el día estaba vacío).
- No dejan fila: bloquear, comensales, notas, tipo/orden de un plato, quitar un veto y reactivar un día.
- Un solo punto de escritura, `recordMenuEdits` (`services/menuEdits.ts`), llamado por cada ruta tras su `update`; nunca falla ni bloquea el cambio. **Mimo** entra por las mismas rutas (`assistant/appApi.ts` manda `x-mimoia-internal` y el canal en `x-mimoia-channel`), así que sus herramientas de `appSkills.ts` quedan como `mimo` con su canal. **Pendiente:** `swap_meal` escribe el menú directamente desde `assistant/skills.ts` y todavía no deja fila.
- `GET /menu/:menuId/edits` devuelve el registro del menú (más antiguo primero), con el mismo control de acceso que el resto de `/menu/:menuId`. Sin interfaz todavía.
- Se borra con el menú, con el hogar y con la cuenta de quien hizo el cambio (cascada). Tests: `menuEdits.test.ts`, `menuEditsRoute.smoke.ts`.

## Access control (IDOR guards)

Every menu route is scoped to the caller — a logged-in user can only read or
mutate their own menus (or, when `SHARED_HOUSEHOLD_SCOPE` is on, those of a
fellow household member). This closes a former gap where any authenticated
user could read/modify any menu by id.

- `POST /menu/generate` **requires auth** and the body `userId` must equal the
  authenticated user (`403` otherwise). It used to be open — anyone could
  overwrite any user's week by passing their id; that is no longer possible.
- `GET /menu/:userId/:weekId` and `GET /menu/:userId/history` resolve the read
  scope from the **token**, never the path param. Requesting another user's id
  returns `403` unless they share your household.
- Every `/menu/:menuId/...` mutation (regenerate, add/delete/move slot, lock,
  ban, leftover, skip, servings) passes through a `:menuId` param guard:
  `400` if the id isn't a UUID, `404` if no such menu, `403` if it belongs to
  another user/household. Owner-or-same-household access mirrors the shopping
  list rule (`canAccessRow` in `scopeResolver.ts`).

## Time to cook (PRO-138)

- A day's limit comes from `time_available[weekday]` in the memory (`weekTimeBudgets` / `dayTimeBudget`, `@ona/shared` `types/cookingTime.ts`): either **in total** («Rápido: en media hora, a la mesa», or a plain number as Mimo writes it) or **of work** («Poco rato de trabajo, aunque luego se haga solo»). The weekly generator and every single-slot path (Cambiar al azar, add a meal, regenerate) apply it.
- The matcher (`recipeMatcher.ts`, step 6, `fitsTimeBudget`): a «total» day compares `totalTime` (else `prepTime + cookTime`); a «trabajo» day compares `activeTime` (else `prepTime`). **With a limit, a recipe without that time does not pass** (until 2026-10-17 it always passed and only `prepTime` was compared, so a 3-hour stew with 20 min of prep reached a 30-minute Tuesday). Without a limit every recipe passes. A cocido with 15 min of work and 200 in total fits a «20 min de trabajo» day. Tests: `recipeMatcher.test.ts`, `onboardingPreferences.test.ts`.
- Catalogue times: on every boot (`db:migrate`) and at the end of `db:seed`, `catalogRecipeTimes.ts` fills **only empty** times of system recipes: Cocina's prep/cook/total for the 10 recipes that had none, `totalTime = prepTime + cookTime` when missing, and `activeTime` from the steps (sum of hands-on steps; simmering, oven, resting, marinating, soaking, cooling (enfriar), fridge (nevera, frigorífico), freezing, «templar», rising (levar), fermenting and boiling with minutes («Cuece a fuego medio 40 minutos») don't count — the last ones since PRO-187; a hands-on step without minutes → `prepTime`; never above the total). Each filled recipe is logged as `[catalog-recipe-times] «…»: … trabajo N (de pasos|de preparación) min` for Cocina to review, plus a «N de M recetas del sistema con tiempo total y de trabajo» line. **Recompute (PRO-187):** a system recipe whose stored `activeTime` is exactly what the rule before PRO-187 gave (`computeActiveTimeLegacy`) gets it recomputed with the new rule (e.g. one hour in the fridge + 10 min of cutting: 70 → 10), logged as `[catalog-recipe-times] «…»: trabajo A → B min (recalculado con la regla nueva, …)`; any other value (set by hand or by Cocina) is never touched, and the write only applies if the value hasn't changed since the read. User recipes are never touched. Tests: `catalogRecipeTimes.test.ts`.

## Acierto: cuánto se parece a lo que os gusta (PRO-155)

- Right after a week is generated (web `POST /menu/generate`, Mimo's `generate_weekly_menu` / `complete_onboarding`), one small **Claude Haiku** call (`services/menuFit.ts`, `claude-haiku-4-5`, feature `menu_fit` billed to the household) compares the week's recipes with what we know the household likes: the favourite dishes it told us (`users.favorite_dishes`) and its «Me encanta» (`recipe_verdicts`). For each dish the model also sees the catalogue recipes sharing a word with it (published catalogue + own recipes).
- Result (`MenuFit`, `@ona/shared`, stored in `menus.fit`, migration 0065): `score` 0–100 and level (**alto** ≥ 70, **medio** ≥ 40, **bajo**), what's met (with the recipe) and what's missing and why: **no está en el catálogo** or **no cabía esta semana**. Hand check: a dish that a catalogue recipe covers word for word (`catalogCoversDish`) or a «Me encanta» is never «no está en el catálogo». Also `unusedAddMethods`: photo, link or written recipe the household hasn't used yet (`usage_events` `recipe_imported` / `recipe_created`).
- Missing favourites («no está en el catálogo», only dishes they told us) become **deseos del catálogo** (`recordCatalogWish`, source `evaluador`; [Catalog import](./catalog-import.md)).
- `/menu` shows **one line under the week** (`MenuFitLine`, `data-testid="menu-fit"`, current and future weeks): alto «Este menú se acerca mucho a lo que os gusta (85 %): hay …»; medio «Se acerca bastante… No he podido meter …; puedes ponerlo en lugar de otro plato»; bajo «Con las recetas que tengo no me he acercado mucho a lo que os gusta (5 %): aún no tengo …. Si añades tus recetas, las tendré en cuenta.» + «Añadir una receta» → `/recipes/new`. Mimo tells it in its own words ([Advisor](./advisor.md)).
- **Best effort**: no API key, error, > 8 s or an unusable answer → `fit: null`, the menu goes out the same and no line is shown. Without favourites or «Me encanta» there is nothing to compare: no call. «Vaciar semana» / empty weeks don't run it.
- Limits: the verdict is about the week **as generated**; later swaps don't update it (the next generation does). Only the generating user's favourites and «Me encanta» count (not the rest of the household, not the ficha yet). The menu matcher still weighs favourites by shared words (`recipesMatchingDishes`): the smart menu is PRO-139.
- Tests: `menuFit.test.ts` (the real case of 2026-10-16, reasons, wishes, cost, fallbacks), `assistant-skills.test.ts` (reaches Mimo), `e2e/menu-fit.spec.ts` (the line, and none without a verdict).

## Constraints

- All menu routes require auth (including `POST /menu/generate`, which also
  enforces that the body `userId` matches the token)
- The default template assigns breakfast + lunch + dinner to every day (no snack)
- A user's `userSettings.template` can override per-day meal slots **and the diner count for each slot**. The profile UI persists the override as `{ mealTemplate: { [día]: { [comida]: number } } }` — Spanish day + meal names, integer >= 1 = "this many comensales for that slot", absence = slot off. The menu generator runs `normalizeMealTemplate` (on/off projection) and `extractMealDiners` (per-slot counts) on every load to coerce that shape — or the legacy `string[]` shape from before 2026-05-30, or the legacy `DayTemplate[]` — into the canonical 7-day array of `{ breakfast?, lunch?, dinner?, snack? }` plus a parallel 7-day map of `{ breakfast?: n, lunch?: n, ... }`. The generator seeds each newly built slot's `servings` from that map, so the shopping list and recipe-detail "Para X" scale to the configured comensales without further user action. Empty `mealTemplate` falls back to the default template; unknown day/meal keys are dropped silently; per-slot overrides on the menu card still win over the template default
- If no menu exists for the requested week, `GET /menu/:userId/:weekId` returns 404
- The shopping page redirects users to `/menu` if no menu exists for the current week
- **Household scope (PR 1B):** menus carry both `user_id` and `household_id`. Inserts always populate both; reads filter by `household_id` when the env flag `SHARED_HOUSEHOLD_SCOPE=true` (default ON in dev/test, OFF in prod). When the flag is on, every member of a shared household reads the same menus. See [Household](./household.md)
