# Business Metrics & Cost Ledger

One JSON endpoint (plus the product-analytics `GET /admin/usage`) that tells the "Dirección" and Finance agents (and Miguel) how many households use Mimoia each week, how many "resolve" their week, how they retain, and what each active household really costs in paid AI/messaging providers. Built on an append-only **cost ledger** (one row per paid provider call) and a small **activity log** for shopping-list use.

## Why this exists

Mimoia is pre-launch and will be run as a one-person company with AI agents. Pricing needs the real cost per active household per week, and the morning brief needs activation/retention numbers. Before this, only per-user counters existed (advisor € budget, image quota, a voice-minutes cap since retired), none per call, none per household.

## User Capabilities

- An admin (JWT, see [Roles](./roles.md)) or an agent holding the read-only token can call `GET /admin/metrics?weeks=8` and get JSON for the last N ISO weeks (1–52, default 8; Europe/Madrid clock, current week flagged `partial`).
- The token is sent as header `x-metrics-token` and must equal the env var `METRICS_READ_TOKEN` (constant-time compare). It opens thirteen read-only GETs (`tokenRoutes.test.ts` pins them from the source): this endpoint, `GET /admin/usage` (below), `GET /admin/errors` ([Error tracking](./errors.md)), `GET /admin/waitlist` ([Waitlist](./waitlist.md)), `GET /admin/price-survey` ([Billing](./billing.md)), `GET /admin/feedback` ([Feedback](./feedback.md), counts only), `GET /admin/assistant-reviews/flags` ([WhatsApp](./whatsapp.md)), `GET /admin/catalog-wishes` ([Catalog import](./catalog-import.md)), `GET /admin/extension-gaps` and `GET /admin/extension-sends` (below, [Shop orders](./shop-orders.md)), `GET /admin/newsletter/stats` ([Newsletter](./newsletter.md)), `GET /admin/menu-planner/comparison` ([Smart menu](./smart-menu.md)) and `GET /notices/afina/stats` ([Taste](./taste.md)) — every other `/admin/*` route still needs an admin JWT. With the env var unset, token access is off (always 401 `METRICS_TOKEN_DISABLED`); a wrong token is 401 `METRICS_TOKEN_INVALID`, with no fallback to JWT; any method other than GET/HEAD with the token is 405 `METRICS_TOKEN_READ_ONLY`.
- `includeInternal=1` also counts admin and suspended accounts (useful pre-launch, when almost every user is internal).
- Response:
  - `weekly[]`: `week` (Monday), `isoWeek` (`2026-W41`), `partial`, `activeHouseholds`, `resolvedWeekHouseholds`, `menuHouseholds`, `menuReadyByMondayHouseholds` (PRO-246, see Definitions), `newHouseholds`, `costEur { total, byProvider, byFeature }`, `internalCostEur`, `systemCostEur { total, byProvider, byFeature }` and `systemEventsByFeature` (PRO-309, below), `costPerActiveHouseholdEur`, `eventsByFeature` (PRO-247, see Definitions), `installedAppHouseholds` and `pushEnabledHouseholds` (each `{ android, ios, desktop, total }`, see «App instalada y avisos» below).
  - `cohorts[]`: households by signup week with `size` and `retention { w1..w4 }`.
  - `campaigns[]` (PRO-27): signups in the window grouped by the **campaign invitation link** their first user registered with (`campaign: null` = no link): `signups`, `activated` / `activationRate` (active in the signup week), `week3Eligible`, `week3Active`, `week3Rate` (active in signup week + 3, over the signups whose week 3 has started). This is how Miguel's circle («familia», «amigos-padel») is read apart from strangers. Each row also has an `origin` (PRO-1017, D-129, D-132 point 2), and rows are grouped by campaign and origin: `circulo` (a link of Miguel's circle: `circulo-*`, `beta-privada-*`, `colegio-estudio` / «colegio estudio»; case, accents and spaces don't matter), `campaña` (any other campaign link), and without a campaign link `desconocido-por-invitacion` (the household's first user signed up with the personal link `?invita=` of a household of the circle: they don't know Miguel and **count for the 13-nov signal**, D-020), `invita` (with the personal link of any other household or list person) or `sin-enlace`. A household of the circle is one with a member who signed up with a circle link; its codes are its members' account codes and the list codes of list people with an account in it (`services/circleInvitations.ts`). Counts only: no codes or ids. Tests `circleInvitations.test.ts`, `circleInvitations.smoke.ts` (real API and database, both routes).
  - `totals`: distinct `activeHouseholds`, `activeHouseholdWeeks`, `newHouseholds`, `resolvedHouseholdWeeks`, `costEur`, `internalCostEur`, `systemCostEur`, `costPerActiveHouseholdWeekEur`, `eventsByFeature` and `systemEventsByFeature` (window sums), `costEvents`, `unpricedCostEvents` (these two also count internal accounts and system calls).
  - `errors`: `{ windowDays: 7, newGroups, activeGroups, openGroups, events }` from the in-house error tracker over the last 7 days (rolling, by `last_seen`; not per ISO week): error groups first seen / seen / seen and unresolved, and Σ `count` of the groups seen (cumulative, so an upper bound of the window's events). Detail per group: `GET /admin/errors` ([errors.md](./errors.md)).
  - `waitlist`: `{ entries, waiting, invited, joined, unsubscribed, last7Days, referredSignups, newsletterOptIns }` — all time, from `waitlist_entries` (`last7Days` = signups in the last 7 × 24 h; `referredSignups` / `newsletterOptIns` count active entries only). Segments, sources and the suggested next batch: `GET /admin/waitlist` ([waitlist.md](./waitlist.md)).
  - `notifications` (PRO-216, D-069; for the Monday review of the weekly aviso budget in `/ona-semana`): `enabledHouseholdsNow { whatsapp, push, total }` (households with WhatsApp avisos on or a push subscription, **current state**: switches have no history) and `weekly[]` per ISO week: `householdsWithNotices`, `candidates`, `sent`, `merged` (went inside another aviso's message), `droppedByBudget`, `outsideWindow` (Meta's 24 h window, no template), `failed`, `answered` (sent or merged by WhatsApp and the person wrote within 12 h), each also `byKind` and `byPriority` (1–4), plus `priority1Dropped` (should be 0), `optOutHouseholds` (wrote BAJA) and `kindOffHouseholds` (`notifications_off` usage events). From `notice_candidates` ([Notifications](./notifications.md) → «Tope semanal de avisos»); aggregates only (`services/notifications/metrics.ts`, tests `noticeMetrics.test.ts`).
  - `definitions` (the rules below, in plain language; `definitions.featureDefinitions` says what one call of each ledger feature is) and `dataSince { costLedger, activityLog }` — the first ledger/activity row, so earlier weeks aren't misread as "free" or "unresolved".
- Code that needs a user's spend (e.g. budget limits) calls `getUserMonthlySpendEur(userId, now?)` in `services/costLedger.ts`: estimated EUR billed to that user so far this calendar month (Europe/Madrid), all paid features.

## Definitions

- **Household**: the primary household of at least one counted user. Activity is attributed to the row's own `household_id` when it has one, else to the user's current primary household.
- **Excluded accounts**: `role = admin` and suspended users (current status). Their spend is reported apart as `internalCostEur`. There is no demo-account flag in the schema.
- **Active household (week)**: at least one of — generated a menu, logged a cooked meal, used the shopping list, created a recipe, sent a WhatsApp message to Mimo, or triggered a paid AI feature (chat with Mimo, typed or spoken; voice transcription or read-aloud; recipe import/extraction; image). Old Realtime voice sessions (`voice_transcripts`, no longer written since 2026-10-09) still count for past weeks. Opening a screen is not tracked. Mimoia-initiated WhatsApp templates don't count.
- **Resolved week**: the household has a menu whose `week_start` is that week AND used the shopping list (checked an item, toggled in-stock, or added an item — from the web or through the assistant/voice) during that week **or the Saturday/Sunday right before it** (people shop at the weekend for the menu starting Monday; Mimoia's shopping reminder fires Saturday). Opening the list does not count: the `shopping_lists` row is rewritten on every read, including by the WhatsApp shopping reminder.
- **Households with the week's menu** (`menuHouseholds`, PRO-246): households with a menu whose `week_start` is that week (generated, regenerated or emptied: any menu row of the week). **Ready by Monday** (`menuReadyByMondayHouseholds`): of those, the ones whose *first* menu for that week was created before 00:00 of that Monday, Europe/Madrid (22:00 UTC on Sunday in summer, 23:00 in winter) — they prepared the week before it started; a later regenerate inserts a new row but doesn't move the first creation time. The loader returns `MIN(created_at)` per (household, week) and the cut-off is applied in `buildWeekly`. Counts only; admin and suspended accounts out unless `includeInternal=1`.
- **New household**: created (at registration) that week. **Cohort retention wK**: share of the signup cohort active in week signup+K; `null` until that week starts; the current week is partial.
- **Cost**: ledger cost of counted users. `costPerActiveHouseholdEur` = week cost / active households (`null` with none active); `costPerActiveHouseholdWeekEur` = window cost / Σ weekly active households.
- **System cost** (`systemCostEur`, PRO-309, D-108): calls with no user behind them (`cost_events.user_id` null) — rewriting recipes for the catalogue import (`catalog_import_rewrite`), matching ingredients (`ingredient_match`), the daily conversation reviewer and other system jobs — by provider and feature, with their calls in `systemEventsByFeature`. They are not in `costEur` nor in the cost per household, so a catalogue batch does not set off the per-household cost alert (D-048). An admin's or suspended user's spend stays in `internalCostEur`.
- **Calls by feature** (`eventsByFeature`, PRO-247): number of `cost_events` rows per feature, for the same accounts as `costEur` (internal accounts out). One row is one paid call, so `costEur.byFeature[f] / eventsByFeature[f]` is the average cost of one call. What a call is, per feature (`FEATURE_DEFINITIONS`, also in the response): `assistant_chat` / `whatsapp_chat` / `telegram_chat` one turn with Mimo (all its model calls summed); `whatsapp_guided` one call to the writer of a message Mimo sends by itself (morning brief, cooking reminder, dinner check-in, shopping reminder, weekly nudge, and the last message of the WhatsApp onboarding), billed even when its text is rejected and the fixed text goes out (messages sent with the fixed text without calling the writer don't count); `whatsapp_service` / `whatsapp_template` one message sent; `recipe_image` one photo generated (a retry after a failed check is another row); `recipe_image_describe` / `recipe_image_check` one description / one check; transcriptions one voice note or recording; `chat_tts` one reply read aloud. Counts only, no user data.

## Cost ledger (`cost_events`)

Every paid provider call writes one row — user (nullable), household (user's primary at record time), feature, provider, model, units (tokens / audio tokens / minutes / messages / images / characters), estimated `cost_micros` (micro-euros; `NULL` when the model isn't priced — counted in `unpricedCostEvents`, never dropped). Recording is fire-and-forget: it never slows or fails the user's request; errors are logged.

Attribution: every authed request runs in a per-request context carrying the user, so deep calls (matcher, unit fallback, translator) are billed without threading ids. Each WhatsApp inbound turn runs in its own context that the budget check fills in once the phone resolves to a user. Schedulers and scripts have no context → system.

WhatsApp service messages (since 2026-10-01 Meta bills them): one row per message sent, always. The tier is counted over all `whatsapp_service` rows of the month (Mimoia has one number); if that count can't be read the message is recorded as priced. Neither templates nor service messages count as household activity (they're Mimoia's messages; the user's own inbound message already counts).

Not costs, so not recorded: USDA / BEDCA lookups, YouTube/article fetches.

## Prices

All rates live in `config/pricing.ts` (source + date in comments), in the provider's currency; USD is converted with `ADVISOR_EUR_PER_USD` (the same knob the advisor budget uses, default 0.92). The advisor's € budget prices the assistant's model (`ADVISOR_PRICE_MODEL` in `advisorBudget.ts`, kept in sync with `ASSISTANT_MODEL`) from the same table, so budget and ledger never disagree. Anthropic rates checked against the official page on 2026-10-16: Sonnet 5.5 and Opus 5.5 cache reads are 0.05× input (Sonnet 5.5 reads were recorded at double the real rate until then); Haiku 5.5 ($0.10 / $0.50) is in the table for model comparisons. `COST_PRICE_OVERRIDES` (JSON, e.g. `{"openai/gpt-realtime":{"perMinute":0.15}}`) corrects or adds a price without a code change; malformed values are ignored with a warning.

The `openai/gpt-realtime*` entries stay in the table so historical `voice_realtime` rows keep their price. ElevenLabs is priced per 1,000 characters by model (`elevenlabs/<model>`). Marked UNVERIFIED (estimates, override when known): Realtime voice blended **$0.10 / session-minute** (historical; token rates verified, the per-minute blend is derived), AIKIT Imagen-fal image **$0.04** (historical rows only). AiKit `gpt-image-2` is **€0.0044 a photo**, in euros: what AiKit charges, read off the key's spend counter on 2026-10-19 (D-090); OpenAI `gpt-image-1` medium 1536×1024 **$0.063** (measured 2026-10-08). Meta WhatsApp Spain is verified against Meta's EUR list rates effective 2026-10-01 (checked 2026-10-13): utility template and service message **€0.0166**, marketing **€0.0585**.

## Activity log (`activity_events`)

Append-only `(user, household, kind, created_at)` for actions no other table timestamps durably: `shopping_check`, `shopping_stock`, `shopping_add`. Written by an app-level middleware when the matching shopping-list route answers 2xx, and by the assistant tool runner when `check_shopping_item` / `mark_in_stock` succeed. Never blocks the request.

## Eventos de uso (`usage_events`, `GET /admin/usage`)

Analítica de producto en una tabla propia, sin terceros. Una fila por cada cosa que hace un usuario: `(created_at, household_id, user_id, name, channel, props)`. `channel` es `web` | `whatsapp` | `voice` (null = desconocido). `props` solo admite slugs, números y booleanos (máx. 8 claves, los filtra `trackEvent`): nunca texto libre, nombres, URLs ni teléfonos. Usuario y hogar son `SET NULL` al borrarse, así que una cuenta borrada deja solo recuentos anónimos. `trackEvent` nunca lanza error ni espera a la base de datos.

`GET /admin/extension-gaps?days=7` (JWT de admin o el token; `days` entero, acotado a 1–90, 7 por defecto; [Shop orders](./shop-orders.md)) → `{ days, gaps[] }`: lo que la extensión del navegador no tenía en su tabla en los envíos recibidos esos días, para hacerla crecer. Cada hueco: la línea pública (`name`: la regla de compra, el nombre de catálogo —solo de un ingrediente de alguna receta del sistema, y tras una lista blanca de caracteres— o null; `choice`: solo una opción fija de la regla; `origen`: `regla`, `catalogo` o `tecleado`), `estado` (`busqueda` = entró por búsqueda; `fallida`), producto elegido (`productoId`, `producto`), `motivo` (`no_encontrado`, `no_publicado`, `error` o null) y `veces`, de más a menos. Nunca el texto tecleado ni su búsqueda; sin usuarios ni hogares. Con el token (PRO-322) el `producto` es null si pasa de 80 caracteres o de 12 palabras, y la respuesta trae `productosFiltrados` (cuántos se quitaron); con el JWT de admin, completo.

`GET /admin/extension-sends?days=1` (JWT de admin o el token; `days` entero, 1–90, 1 por defecto) → `{ days, sends[] }`: un registro por resultado de la extensión guardado esos días, del más reciente al más antiguo: `fecha` (cuándo llegó), `ok`, `error`, `anadidas`, `deshecho`, `duracionMs` (null si la versión de la extensión no lo manda) y `lineas[]` con la línea pública (`name`, `choice`, `origen`, como arriba), `estado`, `motivo`, `producto` y `unidades`. Sin hogar, usuario, `envioId`, total del carro ni texto tecleado. Con el token (PRO-322, norma 12.3), `fecha` es solo el día en Europe/Madrid (`AAAA-MM-DD`) y `producto` sale como mucho con 80 caracteres y 12 palabras (si no, null), con `productosFiltrados` en la respuesta; el JWT de admin ve la hora y el producto entero (hasta 160). Es el último resultado de cada pedido: un fallo seguido de un reenvío, o un envío deshecho y vuelto a enviar, solo deja el último. Los errores de todos los envíos quedan en las `props` de `basket_extension_sent`, que `/admin/usage` no enseña (solo cuenta por día, evento y canal): no son visibles con el token. Trabajo futuro: un recuento por `error` en `/admin/usage`.

## App instalada y avisos (PRO-83)

- Al abrirse Mimoia como app instalada (`display-mode: standalone`, o `navigator.standalone` en iPhone) con sesión iniciada, la web llama a `POST /usage/app-opened` sin cuerpo, como mucho una vez al día por navegador (`localStorage`). La API deduce el dispositivo del navegador (android si dice Android; ios si dice iPhone/iPad/iPod; desktop el resto) y guarda solo esa palabra, en un único `app_opened_installed` por hogar y día de Madrid (aunque llegue tres veces). Responde 204 siempre; sin sesión, 401.
- `app_opened_installed` y `notifications_off` son **pasivos**: sale en los recuentos de `/admin/usage`, pero no hace «activo» a un hogar (ni en `activeHouseholds` ni en el embudo).
- `/admin/metrics` → `weekly[].installedAppHouseholds`: hogares que abrieron la app instalada esa semana, por dispositivo; `total` cuenta cada hogar una vez aunque use dos.
- `weekly[].pushEnabledHouseholds`: hogares con avisos activados al final de esa semana, de `push_subscriptions` (suscripción que sigue existiendo hoy y creada hasta ese domingo), por dispositivo deducido de su `user_agent`. Solo cifras: ni ids ni navegadores en la respuesta.

Conservación: el tick del planificador borra una vez al día los eventos de más de 180 días (`purgeOldUsageEventsIfDue`).

## Constraints

- Queries aggregate in SQL to distinct (household, week|day) pairs and per-week cost sums; the rules above run as pure, unit-tested functions.
- The token is mounted on the thirteen GETs above only: `GET /admin/metrics`, `GET /admin/usage`, `GET /admin/assistant-reviews/flags`, `GET /admin/extension-gaps` and `GET /admin/extension-sends` live in `routes/metrics.ts` (a unit test pins that list); `GET /admin/errors`, `GET /admin/waitlist`, `GET /admin/price-survey`, `GET /admin/feedback`, `GET /admin/catalog-wishes`, `GET /admin/newsletter/stats`, `GET /admin/menu-planner/comparison` and `GET /notices/afina/stats` in their own routers; `tokenRoutes.test.ts` pins the thirteen (and the files that use `metricsAuth`) from the source, so a new route behind the token fails until its view is checked. Those routers are mounted before the catch-all `router.use(authMiddleware)` routers (else token-only calls would be 401'd first).
- Unit tests never write to the database (ledger/activity/usage inserts are skipped under vitest).
- With the token, five routes that hold text written by or about users answer with counts, categories, severity and values from closed lists only (`services/agentView.ts`; the admin JWT keeps the full view): `GET /admin/feedback` (counts by channel and by page, possible allergies with their Madrid date), `GET /admin/errors` (error class from a closed list, route), `GET /admin/assistant-reviews/flags` (each value from its enum, no `reply` or `note`), `GET /admin/waitlist` (every object an explicit list of fields; `?ref=` labels, `utm_source` and `utm_campaign` as counts — total and in the target segment, `inTarget` (PRO-189) — under closed lists, unknown → `otro`; no referral codes or entry ids) and `GET /admin/menu-planner/comparison` (no household id or reasons). Every route or page in those answers is shown only in the shape of a real template — the Express path literals and the `apps/web/src/app` pages, `services/routeTemplates.ts`, pinned by a test that recomputes it from the code — with parameters as `:x` (`/lista/:x`, `/entrar/:x`, `/recipes/:x`) and anything else as `otra`, so codes, tokens and anything typed by someone never reach the token (`POST /client-errors` and `POST /waitlist` are public, and the feedback page and the utm values are set by the client). Free text from users reaches the token in one place only, as food names: `GET /admin/catalog-wishes` gives the dish a registered user asked for, cut to 80 characters (never who asked). `GET /admin/extension-gaps` and `GET /admin/extension-sends` give no typed text and no search (next point); the product name they give comes from the household's browser and passes a whitelist (Known limitations). Tests: `agentView.test.ts`, `feedback.test.ts`, `appErrorsRoute.test.ts`, `assistantFlagsRoute.test.ts`, `waitlistRoute.test.ts`, `blindComparisonRoute.test.ts`, `catalogWishes.test.ts`; smokes with real SQL: `usageRoute.smoke.ts`, `waitlistRoute.smoke.ts`, `blindComparison.smoke.ts`.
- `GET /admin/extension-gaps` and `GET /admin/extension-sends` crop for everyone (token and admin JWT alike): a line is its buy rule key, its catalogue name (only for an ingredient used by some system recipe, checked when the result is saved: one a user created is `tecleado`; the text must pass a character whitelist on its normalised form (typographic quotes and dashes folded, then NFKC) — Latin-script letters, digits, spaces and `, . ' ( ) % / + · × & ° € -`, no `www`, no domains, fewer than 9 digits; the store's product name too, and its id needs fewer than 9 digits) or `null` with `origen: tecleado` — never text a household typed, never a household, user or send id (`publicLineName`, `services/basketExtension.ts`; tests `basketExtension.test.ts`, `basketExtensionRoute.smoke.ts`).
- With the token only (PRO-322, norma 12.3), on top of that: the store's product name is `null` past 80 characters or 12 words, counted in `productosFiltrados` in the answer, and each send's `fecha` is only its Madrid day (`AAAA-MM-DD`); the admin JWT keeps the time and the full name (`basketSendsForToken` / `basketGapsForToken`; tests `basketExtension.test.ts`, `basketExtensionRoute.test.ts`).

## Known limitations

- **`producto` and `productoId` of the extension come from the household's browser** (the body of `POST /shop-orders/:id/extension-result`): the whitelist cannot stop a sentence made only of letters. Trust rests on `BASKET_EXTENSION_EMAILS` (households we control today); before opening the list to households we do not control, another defence is needed (e.g. give the product only for ids seen in two or more households, or drop it on `tecleado` lines). See [Shop orders](./shop-orders.md).
- **Los eventos de uso empiezan cuando se despliega esto.** Sin relleno hacia atrás: el embudo solo conoce las altas registradas desde entonces. Desde el 2026-10-19 (PRO-188) «ha cocinado» cuenta todos los canales: abrir el modo cocina en la web (`cook_mode_started`), «Marcar como cocinada» (`meal_cooked`) y lo que se le dice a Mimo por WhatsApp o en el chat (`log_cooked`, `start_cooking_mode`, `mark_meal_eaten` con `eaten: true`); antes, el modo cocina de la web y «ya lo hemos comido» no contaban. Abrir una pantalla sin llamada a la API (detalle de receta, perfil) no se registra. Las conversaciones de Mimo en la web no se guardan: `mimo_message` las cuenta, pero no hay texto que revisar.
- **History starts at deploy.** No backfill: weeks before `dataSince` under-report cost and resolved weeks (the old per-user advisor counter has no per-call history).
- **WhatsApp service messages are counted when sent, not when delivered** (Meta bills delivered ones), and the free tier is counted on the Madrid calendar month and over all `whatsapp_service` rows, so a second number or a failed delivery would make the estimate slightly high. Two messages sent at the same instant can both see the same count at the 1,000 boundary.
- Historical `voice_realtime` rows (until 2026-10-09) trusted client-reported minutes (the retired `POST /realtime/:userId/usage`); a crashed tab reported nothing.
- One-off catalog scripts with their own Claude clients (`regenerateRecipes`, `populatePrepRequirements`, `populateRecipeCourses`, `measure-tokens`) are not recorded.
- **App instalada y avisos:** las aperturas empiezan cuando se despliega PRO-83 (semanas anteriores a 0). Desactivar los avisos borra la suscripción, así que las semanas pasadas de `pushEnabledHouseholds` son un mínimo. Un iPad con iPadOS se presenta como Mac y cuenta como desktop.
- Households are resolved through the user's *current* primary household; a user who switches household moves their past activity with them.
