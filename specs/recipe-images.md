# Recipe Images

The hero photo of each recipe: the user's own photo (PRO-145), the generated house photo on create/import, "Regenerar imagen", and the catalogue photo audit. Split out of [Recipes](./recipes.md) (PRO-08). Household "look how it came out" photos are a different system: [Recipe Photos](./recipe-photos.md).

## Behaviour

- **Own photo** (PRO-145, `services/recipeOwnImage.ts`): the main photo can be the user's own instead of an AI one, to save the generation cost (~0,06 € per photo). (1) In **/recipes/new** the «Foto de la receta» card offers **«Generar con IA»** (selected by default; nothing is spent until saving) and **«Subir mi foto»** (camera or gallery, `accept="image/*"` so iPhones hand over a JPEG); the preview shows the 4:3 crop and an «x» puts it back to IA. On «Crear receta» the form sends `POST /recipes?ownPhoto=1`, which **skips the AI photo** (`shouldGenerateHouseImage`), and then uploads the file; if that upload fails the recipe is still saved and the editor opens with `?foto=fallo` («tu foto no se ha podido subir»). (2) In **/recipes/[id]/edit** the same card has «Generar con IA»/«Regenerar imagen» and «Subir mi foto». (3) In the household gallery «así me quedó» the recipe's author (or an admin) gets **«Usar como foto principal»** in the photo viewer ([recipe-photos.md](./recipe-photos.md)). An own photo never counts against the monthly AI quota. `POST /recipes/:id/upload-image` (multipart field `image`, author or admin, else 403): jpg/png/webp/heic/heif up to 10 MB (413 over, 415 for another type or a file sharp can't read — the prebuilt sharp can't decode HEVC HEIC, so a raw HEIC is a 415 unless the phone converts it); EXIF rotation → centred 4:3 crop → ≤ 1200 px JPEG q85 at `${IMAGE_STORAGE_DIR}/<recipeId>.jpg`, `recipes.image_url` updated. Imports (URL, photo, WhatsApp, assistant) still get the AI photo; the WhatsApp «¿La pongo como foto de la receta?» when someone sends the finished dish is not built yet.
- **House photo** (`services/recipeHouseImage.ts`, 2026-10-08): (1) Claude Opus 5.5 (effort low) writes a one-line visual description of the plated dish from name + ingredients + steps (`describeDish`); (2) the prompt = name + that description + a meal-aware framing hint + the fixed house style (`STYLE_SUFFIX`, the same for every recipe) — home cooking in warm window light, artisan ceramic on worn wood or crumpled linen, and on purpose *not* studio-perfect (uneven cuts, a drip or crumb on the rim, a serving spoon or loose napkin, slightly off-centre; Miguel 2026-10-08: "en la realidad nada es tan perfecto"). The 8 per-recipe variants of PRO-59 (tableware × surface × angle × prop) were dropped on 2026-10-14 (PRO-89: "parece más artificial"); this is the style that generated the current catalogue, and no photo was regenerated by either change; (3) the image provider generates it — `RECIPE_IMAGE_PROVIDER=auto` (default) asks AiKit's OpenAI-compatible inference API first (`POST https://cms.aikit.es/api/inference/images/generations`, JSON `{ model, prompt, n: 1, size }`, answer in `data[0].b64_json`; model `AIKIT_IMAGE_MODEL`, default `gpt-image-2`; size by format: 4:3 → `1536x1024`, 1:1 → `1024x1024`, 3:4 → `1024x1536`, and the answer is centre-cropped to the exact ratio; ≈ 11–13 s and 0,0044 € a photo — PRO-265, D-090) and falls back to OpenAI `OPENAI_IMAGE_MODEL`, default `gpt-image-2` (quality medium, 1536×1024 centre-cropped to 4:3, ≈ 0,041 $ a photo in OpenAI's estimate, unverified on a bill; PRO-1149, 2026-11-13: until then the reserve asked for `gpt-image-1`, which OpenAI switched off on 2026-10-23, so every fallback failed; a test fails if a default image model is in the list of retired ones) when AiKit refuses (403), is rate-limited or over budget (429: `rate_limit_exceeded`, `ORG_BUDGET_EXCEEDED`, `MONTHLY_CAP_EXCEEDED`), fails (5xx) or answers without an image; `aikit` / `openai` pin one. The old AiKit Imagen-fal route (403 `API_KEY_ROUTE_NOT_ALLOWED` to every key since 2026-10-08) is gone; the `imagen-4` family 500s on the inference route, so it isn't used. Photos already generated are not touched; (4) Claude Sonnet checks the result (`checkRecipeImage`: right dish? house style — ceramic on wood/linen/cream, warm light, no text/logos/people?); a miss gets **one more try**; it keeps the first that passes, else the first that at least shows the right dish, else saves nothing. **Automatic on create and import**: after `POST /recipes` (when no photo, or a pasted external URL, and not `?ownPhoto=1`) and after every `saveExtractedRecipe` (URL, WhatsApp photo, assistant), fire-and-forget, cost billed to the author, skipped when the author's monthly AI allowance is spent or no provider is configured. It only ever replaces an image that isn't ours (null or a source og:image/YouTube thumbnail) — never a user upload, a generated photo or a seed JPG — and re-reads the row before writing, so a photo uploaded meanwhile wins. Catalogue audit: `services/recipeImageAudit.ts` checks every recipe's photo (right dish, house style, ≥ 1000 px wide); `scripts/auditRecipeImages.ts` runs it read-only from a laptop, and `cli(['--fix'])` inside the ona-api container regenerates the failing/missing/low-res ones onto the volume (2026-10-08 run: 35 ok, 43 wrong dish or off-style, 3 without photo).
- **Nano Banana Pro for every photo** (Miguel 2026-11-13, after the same strogonoff in the four image models AiKit has: https://claude.ai/artifact/FdWKJhA1k9ZR7ofC7kBPz1; gpt-image-2 gave grey, rubbery-looking meat): production sets `AIKIT_IMAGE_MODEL=nano-banana-pro` (Railway, ona-api), so the first photo and the retry after a failed vision check (`AIKIT_IMAGE_RETRY_MODEL`, default `nano-banana-pro`) are both **nano-banana-pro**, 0,133 € each. The code default is still gpt-image-2 in high quality (`AIKIT_IMAGE_QUALITY`, default `high`; nano-banana-pro accepts and ignores it), so a missing variable falls back to the cheap model (D-117, 2026-10-22). AiKit only has four image models (gpt-image-2, nano-banana-pro, flux-2-pro, gemini-25-flash): it answers any other name with gpt-image-2 without saying so, so the served model (`model` in the answer) is logged when it differs and is what the cost ledger prices (`nano-banana-pro`, `gpt-image-2-high`). Cost per new recipe ≈ 0,13 € (two tries ≈ 0,27 €), counted in `cost_events` (`feature='recipe_image'`).
- **Words the image models block** (2026-10-22, `promptSafe` in `recipeImageGenerator.ts`): a Spanish dish word that reads as a blocked English word is swapped in the prompt only, never in the recipe — «rape» (monkfish) goes as «pejesapo» («Rape alangostado» came back 422 from AiKit's content policy).
- **Catalogue: the photo before it goes out** (2026-10-21, `services/catalogPhotos.ts`): the API makes the house photo of every catalogue draft right after the import saves it (at once from the admin page; ≤ 10 minutes for the command's), and a draft isn't published without one — a publish asked for meanwhile goes out by itself when the photo lands. Published catalogue recipes still without a photo are done first. Safety net (`services/catalogImageOnDemand.ts`): one still without a photo when it appears in a menu (any menu read, `hydrateMenuImages`) or is opened (`GET /recipes/:id`) asks for it then. One ask per recipe every 6 hours, shared by both, cost on Mimoia. See [Catalogue import](./catalog-import.md).
- `POST /recipes/:id/regenerate-image` (auth, author or admin) — the house photo above on demand (describe → generate → check → one retry); 502 "La imagen no ha salido bien" when no attempt shows the dish. Pipes the PNG through sharp (1200 px wide, JPEG q85 + mozjpeg) and writes to `${IMAGE_STORAGE_DIR}/<recipeId>.jpg`; updates `recipes.image_url` to `${IMAGE_PUBLIC_URL_BASE}/<recipeId>.jpg`. Per-user monthly quota (`IMAGE_GEN_MONTHLY_LIMIT`, default 20) tracked atomically on `users.image_gen_count` + `users.image_gen_month_key`: a single conditional UPDATE bumps the counter only if the user is under the cap and the month matches; mismatched month → reset to 1; cap reached → 429 with `{ quota: { used, limit, monthKey } }` and no AiKit call. Failed generations refund the slot. Other users' recipes return 403 (admins may regenerate any); no image provider configured returns 503. Frontend (`useRegenerateRecipeImage`) renders a "Regenerar imagen" button on the author-side detail page and an "Imagen" section in `/recipes/[id]/edit`; both show a "X/20 este mes" counter (on the detail page it sits above its button in eyebrow style, and «Editar receta» and «Regenerar imagen» share one row with the same top edge at any width — PRO-86, `apps/web/e2e/recipe-regenerate-quota.spec.ts`; in the editor it sits under the photo buttons) and append `?v=<updatedAt>` to the hero src to bust the long-cached browser image after each regen
- **Recipe without a photo** (`imageUrl` null, or the photo fails to load): the detail `/recipes/[id]` (mobile hero and desktop sticky photo, same size and rounding) and the catalogue card show the same neutral placeholder — `cream-deep` with a pot icon (`recipe-photo-placeholder` on the detail) — **never a stock photo of another dish** (until 2026-10-21 the detail fell back to an Unsplash salad, which read as the recipe's own photo). Over the placeholder the detail drops the dark bottom gradient and the «Mimoia · Receta» label turns `ink-muted`. Link previews of a recipe without a photo carry no image.
- **Seed recipes**: a real `image_url` for each recipe is either committed under `apps/web/public/images/recipes/<slug>.jpg` (seed assets) or generated on demand via `POST /recipes/:id/regenerate-image` for user copies. Only JPGs still referenced by production/staging, by `seed/recipes.ts` (explicit `imageUrl` or a seed name's slug, which `scripts/linkSeedRecipeImages.ts` links) or by code (onboarding photos) are kept; 15 orphans left over from the 2026-10-08 regeneration were removed on 2026-10-12 (PRO-25) and remain recoverable from git history.
