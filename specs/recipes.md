# Recipes

Recipe catalog, recipe detail, and the data needed to actually cook a recipe.

## User Capabilities

- **Catálogo público — `/recipes` without an account** (2026-10-15): the recipe list has one URL for everyone. Signed out, `/recipes` is the public catalogue: public chrome (PublicNavbar «Recetas» + Footer, no sidebar, bottom bar or Mimo; content on the public grid `public-container`, so no left gap on desktop), an editorial header (eyebrow «Catálogo Mimoia», h1 «Recetas con *criterio*.», «Las recetas de Mimoia: de temporada, con sus tiempos reales y paso a paso. Ábrelas y cocínalas sin cuenta.»), then the same search, chip row, «De temporada» hero and card grid as the app. Only the **generic browsing filters** are there: search, «De temporada», «En 30 min», Desayuno/Comida/Cena/Merienda and «Más filtros» (Temporada, Tiempo total, Comida). Hidden signed out, because they need an account: «Nueva receta», «Mis recetas» and «Selección Mimoia» (everything shown is Mimoia's catalogue; the sheet's «Recetas» group too), «Con lo que tengo», household tags. The API answers an anonymous `GET /recipes` with system recipes only (`authorId IS NULL`). Cards open `/recipes/[id]`; the list ends with the waitlist block «Para hacerlas tuyas · Apúntate y Mimoia te plantea la semana con ellas.» → «Únete a la lista de espera» (`/?ref=recetas#lista-de-espera`, `CatalogueWaitlistCta` — see [Waitlist](./waitlist.md)). Signed in, `/recipes` is unchanged (below). **`/recipes-ona` is a permanent redirect (308) to `/recipes`**, query kept (`next.config.ts`); its old page is gone. In the sitemap. Tests: `e2e/app-signed-out.spec.ts` (390×844 + 1440×900).
- **Catalogue order** (PRO-140, signed in and out, `services/recipeCatalogOrder.ts`): `GET /recipes` lists first the recipes **more households have in favourites** (the count is never shown and filters nothing); on a tie (today, all at 0) **Miguel's featured list** `FEATURED_RECIPES` in `@ona/shared`, in its order (by id; on staging or a fresh database by name, accents and case ignored); then the rest, oldest first. The page doesn't re-sort; the seasonal «De temporada» hero is still picked apart. To change the featured list, edit `FEATURED_RECIPES`, not the sorting.
- **Retired recipes** (PRO-140): a catalogue recipe with `retirada` in `internal_tags` (`RETIRED_RECIPE_TAG`) is not listed by `GET /recipes` (signed in or out), the menu never picks it (generator and every automatic swap, via `loadMatchableRecipes`) and Mimo's suggestions don't offer it; whoever has it in a menu, favourites or a cookbook still sees it and opens it by id. Example: «Crema de zanahoria», retired for «Crema de zanahoria con pollo, aguacate y granada».
- **Catalogue drafts** (PRO-154, [Catalogue import](./catalog-import.md)): a catalogue recipe brought in by the batch import is `draft` (`recipes.status`) until its batch is published — not listed, 404 by link (except for an admin, who reviews the sample that way), never picked by the menu or offered by Mimo. Its house photo is made while it's a draft, and it isn't published until it has one (so nobody sees a catalogue recipe without its photo).
- **Names** (PRO-140): no «Gipsy» in catalogue names and accents put back. The seed uses the new names (`Fideuá`, `Pastela vegetariana`, `Tacos caseros`, `Pollo agridulce`, `Curry cremoso de tofu`, `Albóndigas express`, `Cocido madrileño`…); `CATALOG_RENAMES` (`services/recipeRenames.ts`) lists old → new: `db:seed` renames an old row before upserting (no duplicate), and the boot-time source-link backfill finds a renamed recipe's original link under its old Notion name, so «Ver fuente» stays. Tests: `recipeCatalogOrder.test.ts`, `recipeCatalogOrder.smoke.ts` (real API + DB), `e2e/recipe-catalog-order.spec.ts` (390×844 + 1440×900).
- **Página de receta — one page for everyone** (2026-10-15): `/recipes/[id]` is the only recipe detail. For a catalogue recipe it opens **without an account**, complete: photo, eyebrow, ingredients with the servings stepper, steps, Equipo/Alérgenos/Temporada/Etiquetas, nutrition, the recipe's own notes, **Compartir** and **Empezar a cocinar** (cook mode `/recipes/[id]/cook` works signed out too, without Mimo's hands-free). Signed out the page wears the **public chrome** (fixed PublicNavbar on top, Footer at the bottom; no sidebar, bottom tab bar, Mimo button, install sheet or health-consent gate; photo, sticky tabs and the desktop sticky photo start below the navbar) and ends with the **waitlist block** «¿Te gusta? Guarda *X* y plantéate la semana con ella.» → «Únete a la lista de espera» (`/?ref=receta#lista-de-espera`, `RecipeWaitlistCta`). Everything personal (favorite, Añadir al menú, Cocinada, recetario, *Tus notas*, galería, editar, Añadir a mis recetas, ingredient overrides) is behind `user &&`; back links fall to `/recipes` (public too). Signed in, nothing changes (app shell). A **private recipe opened signed out** (the API answers 404, never 403) shows «Esta receta es privada.» with «Entrar» (`/login?next=/recipes/<id>`) and «Ver el catálogo» (`/recipes`). **Signed in, a 404** (deleted recipe, someone else's, or a broken link) shows «Esta receta ya no está.» with «Ir al menú» (`/menu`) (PRO-181). The chrome is chosen in the root layout by `RootShell` from the route (`signedOutChrome` in `lib/routeAccess.ts`, which uses `publicRecipeRoute` from `lib/recipeShell.ts`) and the session; while the session (localStorage) resolves on first load these routes paint an empty cream page, so the wrong chrome never flashes. `/recipes/new` and `/recipes/[id]/edit` need an account (signed out → `/login?next=…`, see [Auth](./auth.md)). The old public detail **`/recipes-ona/[id]` is a permanent redirect (308) to `/recipes/[id]`**, query kept (`next.config.ts`). Tests: `e2e/recipe-public-page.spec.ts` (390×844 + 1440×900), `recipePublicPage.test.ts` (unit)
- **Link previews** for `/recipes/[id]`: a server `app/recipes/[id]/layout.tsx` fetches the recipe from the API **without a token** (2.5 s timeout, cached 5 min, fails soft) and sets title «<nombre> · Mimoia», a description («Receta para 4 personas · 45 min · 9 ingredientes. Ingredientes, pasos y modo cocina en Mimoia, …»), Open Graph (article, absolute photo URL — a relative `/images/recipes/…` is resolved against `https://mimoia.com`), `twitter: summary_large_image` and `canonical` `https://mimoia.com/recipes/<id>` (`recipeMetadata` in `lib/recipeMetadata.ts`). A private or missing recipe gets generic, non-indexed metadata («Receta · Mimoia», `robots: noindex`), so a link never reveals a private recipe. The root layout skips its default `<title>`/description on `/recipes/<id>/…` (`isRecipeSegment`) so the tags aren't duplicated
- Logged-in users browse the catalog at `/recipes` ("D · Luz y foto", 2026-10-08): header "Recetas" + ink "+" (**Nueva receta**), one search field (placeholder "Busca una receta" — search matches names only), **one chip row**, then photo cards (2-column masonry on mobile). A card is the photo with only a **time pill** (total time, else prep time; omitted when unknown) and the Fraunces title — nothing else: no season badge, no ownership badge, no "Selección Mimoia" mark (nearly every recipe is curated, so it would be noise; "Selección Mimoia" is only a chip). Recipes without a photo show a quiet pot placeholder (no stock photo). **Other users' recipes are never returned** — every authenticated caller (including admins) sees only system recipes + their own. When nothing is searched or filtered, a **"De temporada" hero** tops the grid (mobile: one full-bleed 220 px photo; `lg+`: two 290 px cards) with a paper caption "De temporada · N min" + title: an in-season recipe with a photo (curated seasonal ones first, then curated all-year), rotating daily (`pickFeaturedRecipes`). A small "N recetas" line (+ "Quitar filtros" when anything is on) sits above the grid. When the user has copied a system recipe via "Añadir a mis recetas", the catalogue listing **suppresses the original** from this user's view (via the `copied_from_recipe_id` back-reference) so the same dish doesn't appear twice
- Users can copy a system (or another user's) recipe into their own catalog with the **"Añadir a mis recetas"** button on the recipe detail (visible only when `recipe.authorId !== user.id`). The copy is independent — editing it doesn't affect the original — and inherits ingredients, steps, times, nutrition cache and image. The new row gets `internalTags: ['copied-from-catalog']` and `sourceType: 'manual'`
- Users can search recipes by name (case-insensitive substring match)
- Users filter from the **chip row** (toggle buttons with `aria-pressed`; none active = "Todas"): **De temporada** (current season), **En 30 min** (total time ≤ 30), **Desayuno / Comida / Cena / Merienda**, **Selección Mimoia** (system recipes only — was the "Catálogo Mimoia" tab) and **Mis recetas** (the caller's own — asked to the API with `?mine=1` since PRO-299: filtering the first 100 catalogue cards left out the newest copies, which the catalogue order puts last, so a household saw 7 of its 8 recipes). Scope persists in `localStorage.ona.recipes.scope`. **Más filtros** (button inside the search on mobile, link at the end of the chip row at `lg+`) opens the advanced filters dialog (bottom sheet on mobile, centred panel at `md+`; Escape / backdrop close it): Temporada (any season, "Ahora: otoño" hint), Tiempo total (15/30/60 min), Comida, Recetas (Todas / Selección Mimoia / Mis recetas), Etiquetas propias, "Limpiar todo" and "Ver N recetas". Active filters with no chip (another season, 15/60 min, tags) show as a count badge on the button. Season, time and scope filter client-side (`filterCatalogRecipes` in `@ona/shared`): a season matches recipes listing it **or with no seasons**, a time filter uses the total time and drops recipes of unknown time; meal, search and tags are server-side
- **Con lo que tengo** (PRO-31, 2026-10-11) is the first chip of the row: it opens a paper panel under the chips («¿Qué tienes? Elige hasta 3 ingredientes. Sal, aceite, agua, pimienta y harina se dan por hechos.») with a search over the ingredient catalogue (`GET /ingredients?search=`, exact name first, no «crear ingrediente») and the picked ones as removable ink chips. With ≥1 picked the grid shows `GET /recipes/with-what-i-have` instead of the plain listing: visible recipes (catalogue + household's own; a copied original stays hidden) that use at least one of them, ranked by how many they use, then by how little is missing, then by name. Each card adds a line «Te falta: puerro, cebolla» or «No te falta nada más» — never the basics nor optional ingredients. A picked ingredient also matches other catalogue rows whose name contains it as a word («Huevo» → «Huevos camperos»). Recipes that break the user's allergies, diet or dislikes never appear (same rules as Mimo's `suggest_recipes`). The other chips still narrow the results client-side (search and meal too). No hero while it's on; turning it off or «Quitar filtros» brings the catalogue back. Mimo runs the same search (`cook_with_what_i_have`, see [Advisor](./advisor.md))
- Users can open a recipe detail view at `/recipes/[id]` (layout "D · Luz y foto", 2026-10-08). **Mobile (< lg)**: 390 px hero photo (without a photo, the same neutral `cream-deep` pot placeholder as the cards — never a stock photo of another dish, see [recipe-images.md](./recipe-images.md); back · share · favorite on 44 px paper circles; for the author/admin, a pencil at the photo's bottom-right that opens `/recipes/[id]/edit`, PRO-03), a cream sheet with an eyebrow (meals · category · total time · difficulty) + title (+ the credit line «Receta de la Yaya» / «Inspirada en…», "Rinde…", "Ver fuente", "Cocinada N× · última…" when present), then a tablist: **Ingredientes** (default — "Para [− N raciones +]" stepper, the ingredient list, "Editar ingredientes", the **"Para hacer la compra"** card for the author/admin when some row can't go to the shopping list or a shop order as written — see [recipe-quality.md](./recipe-quality.md) → Shoppability; the same card sits above the ingredient rows on `/recipes/[id]/edit`, and typing an amount on a row "al gusto" there moves it to "ud"/"g" so the card goes away after saving, PRO-90 — then Equipo, Alérgenos, Temporada, Etiquetas) · **Pasos · N** (prep/cook timeline + numbered steps) · **Nutrición** (only when nutrition is cached, or when it is incomplete — then without figures, PRO-176) · **Notas** ("Cocinada" + "Añadir a recetario", the recipe's own notes / sustituciones / conservación, *Tus notas*, Galería, "Editar receta" + "Regenerar imagen" for author/admin, "Añadir a mis recetas"). Tabs stick to the top while scrolling, follow ←/→/Home/End, and the open tab lives in the URL hash (`#pasos`, `#notas`…) so a reload or link reopens it. A sticky bottom action bar (84 px) holds the single "Empezar a cocinar"; the bottom tab bar is hidden on this route. **Desktop (lg+)**: sticky rounded photo on the left ("← Recetas" pill; author/admin also get the edit pencil top-right), long-scroll right column — eyebrow, 48 px title, meta (time · difficulty · kcal por ración), action row (Empezar a cocinar · share · favorite), Ingredientes (stepper + 2-column list), Preparación (big terracotta 01, 02…), Equipo/Alérgenos/Temporada/Etiquetas, Nutrición, Notas. **"Añadir al menú"** (PRO-04): a calendar button beside "Empezar a cocinar" in the mobile action bar and a pill in the desktop action row open a sheet (`AddToMenuSheet`) with the 7 days of this week, each with Comida / Cena. A free slot shows "Libre" and takes the recipe (`POST /menu/:menuId/day/:day/meal/:meal { recipeId }` when the day lacks the slot, `PUT` when it exists empty); an occupied slot shows its dish and swaps it for this recipe (`PUT … { recipeId }`); a locked slot ("Fijada") or one that already holds the recipe is disabled. After placing it: "«X» está en tu menú: domingo, cena" + "Ver mi menú". No menu this week → "Aún no tienes menú esta semana" + "Ir a mi menú". Logic in `apps/web/src/lib/addToMenu.ts` (unit test `addToMenuSlots.test.ts`, e2e `recipe-add-to-menu.spec.ts`)
- Users can change the number of diners (1–12) with the "Para [− N raciones +]" stepper on the detail; ingredient quantities scale on the fly and "Empezar a cocinar" carries `?servings=N`
- A **coeliac household** (restrictions with gluten, profile or memory) sees «Elige embutido sin gluten» above the ingredients of a recipe with a cured meat whose gluten depends on the brand (chorizo, morcilla, butifarra, salchicha, foie, jamón de york…; PRO-196). `GET /recipes/:id` sends it as `dietNotices` only to that signed-in household (`DietNotices.tsx`, `data-testid="diet-notices"`); Mimo's `get_recipe_details` adds the same notice. Set by imports (URL, WhatsApp, Mimo, and the photo extractor on `/recipes/new` until the user types the number); saving the edit form stores `explicit` (the author has reviewed it); an ingredient stored with quantity 0 (imported without an amount) reads «cantidad sin indicar», never «0 g» (`formatQuantity` in `apps/web/src/lib/recipeView.ts`, also in cook mode and step chips; `pizca`/`al gusto` keep their text); the Nutrición block (`NutritionCard` on `/recipes/[id]`) ends with «Estimación a partir de los ingredientes; no es consejo médico.»; and «Ver fuente» under the title links to the original when there is a `sourceUrl`. Tests: `recipeEstimated.test.ts` (unit), `e2e/recipe-estimated.spec.ts` (390×844)
- **The ficha says where a catalogue recipe comes from** (D-067, 2026-10-20): right under the title, one line in Cormorant italic, `ink-muted`, 18 px (21 px at `lg+`; testid `recipe-credit`) — «Receta de la Yaya», «Inspirada en una receta de Ferran Adrià, «La comida de la familia»»; a long one wraps. It is `sourceCredit` on `GET /recipes/:id`, read from `recipes.catalog_source` by `catalogSourceCredit` (`services/catalogImport.ts`): the import's `credit` as written; without one, a book of Miguel's reads «Inspirada en <libro>»; Cocina's recipes and every other recipe get `null` and no line. Nothing else of `catalog_source` (file, batch, audit notes) leaves the API. A personal copy («Añadir a mis recetas») has no line: the copy doesn't carry `catalog_source`. - Users can favorite/unfavorite a recipe (toggle via heart button); the heart turns at once (optimistic, flipped back if the call fails) and remembers: `GET /recipes/:id` and `GET /recipes` carry the signed-in reader's own `is_favorite` (until 2026-10-21 they didn't, so the saved heart looked dead — «el botón me gusta no funciona o no cambia de color»). The toggle is queued offline and replays on reconnect — see [PWA](./pwa.md)
- Users can create their own recipes (form at `/recipes/new`)
- Authors can edit their own recipes via `/recipes/[id]/edit` (a "Editar receta" link sits at the end of the detail's Notas tab / section; hidden for non-author non-admin viewers). The edit form supports name, servings, prep/cook times, difficulty, meals, seasons, tags, full ingredient list (per-row "opc" toggle, optional «Nota» + trash), drag-and-drop **reorderable** step list (grip handle on the left of each step row; works with mouse, touch, and keyboard via `@dnd-kit`), a **unified multi-entry Notas list** (persists into `recipes.notes`; the legacy `recipes.tips` column drains on every save — historical content is merged into the notes list on load so nothing is lost), and a "Guardar igualmente" path that re-submits with `?force=1` when the lint validator returns soft warnings (the button lives in the "Avisos" card above the sticky "Guardar cambios" pill; same on `/recipes/new` with "Crear receta"). Voice users can edit metadata fields (name, prepTime, cookTime, difficulty, notes) via the `edit_recipe` skill and ask "abre el editor" to navigate to the form for ingredient/step changes
- **Admins can edit and delete any recipe** — system catalogue rows (`authorId IS NULL`) included — so the curation workflow lives in the same form as authoring. The "Editar receta" link surfaces on the detail page whenever `user.role === 'admin'`; a small "Admin" badge is shown next to it when the admin is editing someone else's recipe (or a system one). PUT/DELETE on the API short-circuit the author check when `req.user.role === 'admin'`, and the persisted row preserves the original `authorId` (admin edits on a system recipe stay system; admin edits on another user's recipe stay under that user). The "Añadir a mis recetas" copy affordance is hidden for admins (they have direct edit access instead)
- Authors can delete their own recipes (not system recipes; admins can delete any)
- Users can extract a recipe from a photo (image upload → AI extraction)
- Users can share a recipe via the native share sheet (Web Share API) from a Share2 button in the detail hero (mobile) or action row (desktop) — see [PWA](./pwa.md). **"Pásalo"**: a catalogue recipe shares **only a title and the link** `/recipes/:id?ref=receta` (the page opens without an account, with the waitlist block; the link preview says what Mimoia is). No `text` goes with the `url`: some apps glue url + " " + text into one broken link (`…?ref=receta%20Pollo…`). A private recipe is shared as text (name + ingredients) with a link to Mimoia, since its page is private (`recipeSharePayload` in `@ona/shared`)
- Users can start "Cooking mode" from the detail view ("Empezar a cocinar" — one entry point: the sticky bottom action bar on mobile, the action row on desktop). It navigates to `/recipes/[id]/cook?servings=N`, which holds the screen-wake Wake Lock for the duration of the cook session — see [PWA](./pwa.md) and [Cooking Mode](./cooking-mode.md)
- Users can apply **structured ingredient overrides** to any recipe (Mimoia, theirs, or another user's) from the detail view. Toggling "Editar ingredientes" (under the ingredient list) unlocks three actions per row — quitar, modificar cantidad/unidad/nota, and a "+ Añadir ingrediente" at the bottom of the section. In read-mode the recipe renders with the overrides baked in: removed rows are struck-through and faded, modified rows show the original quantity struck-through alongside the new value in terracotta, added rows live in a forest-green block underneath the original list. Overrides are per-household (one row per `(household, recipe)` in `recipe_notes.ingredient_overrides`), persist across navigation, and apply every time the household sees the recipe. The **shopping-list aggregator consumes these overrides** before scaling: removed lines drop out of the basket entirely, modified lines use the override's quantity/unit, and added lines (when the free-form `label` resolves against the ingredient catalog) get added to the basket. Adds whose name doesn't match the catalog stay visible on the recipe but are skipped by the shopping list. The recipe matcher itself still scores against the original ingredient list, so a "sin cebolla" override doesn't change which recipes Mimoia picks for the menu — it only changes what ends up in your basket and on the recipe view
- Users can mark a recipe as **"siempre la cocino para al menos N"** (1–24 raciones; guardan o congelan lo que sobra) in *Notas → Tus notas → Raciones mínimas* on the detail. It's per household (`recipe_notes.min_servings`, migration 0035, `PUT /recipes/:id/notes { minServings }`, `null` clears). Each time the recipe is cooked, the shopping list buys for at least N; a planned leftover belongs to the same batch (see [Shopping](./shopping.md)). The detail's servings scaler starts at N until the user moves it — unless the URL carries `?servings=N` (links from the menu, PRO-75: the batch the menu cooks), which wins. The assistant sets it too (`update_recipe_notes`, "las lentejas siempre las hago para 6").
- Users import recipes (photo, URL, WhatsApp) and auto-create missing ingredients — see [Recipe Import](./recipe-import.md). Recipes get a generated house photo — see [Recipe Images](./recipe-images.md)

## Recipe Model

Each recipe has:
- `name` — required, text
- `imageUrl` — optional
- `servings` — required, positive integer; the canonical number of diners the listed quantities cover
- `yield` — optional human-readable string (e.g. "12 albóndigas", "1 L de salsa")
- `prepTime`, `cookTime`, `activeTime` — minutes (integer, optional, editable). `activeTime` is the hands-on time («de trabajo»); the menu's time limits use it (else `prepTime`) and `totalTime` (else prep + cook). System recipes get the empty ones filled on boot (PRO-138, see [Menus](./menus.md) → Time to cook)
- `totalTime` — minutes, derived by the API on save: sum of `step.durationMin` if all steps have it, else `prepTime + cookTime`. **System recipes (PRO-284, 2026-10-21):** on every boot the total follows the overlap rule — prep + cook − the prep that can be done while a step goes by itself (oven, low heat, pressure cooker, boiling with minutes, resting; up to half the prep, never more than those steps' minutes) — never below the cook time or those steps' minutes, never above the total it had; `cookTime` is never touched. Their prep was also made realistic once (× 0.8, for someone who cooks at home with ease; internal tag `tiempos-pro284`) and the hands-on time drops by the same amount, never above the total. Example: a 40-min oven with 20 of prep → prep 16, total 48. See [Menus](./menus.md) → Time to cook
- `difficulty` — enum `easy | medium | hard`
- `meals` — array of `breakfast | lunch | dinner | snack`
- `seasons` — array of `spring | summer | autumn | winter` (empty = all seasons)
- `equipment` — string array of tools required (e.g. "horno", "procesador", "batidora")
- `allergens` — string array (auto-aggregated from ingredients on save; see [Nutrition](./nutrition.md)). The detail payload (`GET /recipes/:id`, the ficha's «Alérgenos») returns `effectiveAllergens`: the stored union **plus** what the ingredient names say today (`inferAllergenTagsFromName`) — additive, computed on read, no DB write (PRO-61: «Pizza de colores» with «Harina de fuerza» and «Arroz tres delicias» with «Salsa de soja» showed no gluten). The milk tag (`lactosa`, shown as «leche») also comes from cheeses called only by their name (gouda, emmental, brie, camembert, cheddar, edam, gorgonzola, roquefort, ricotta, burrata, provolone, pecorino, grana padano, manchego…), kéfir (not «kéfir de agua»), ghee, «mantequilla clarificada», suero de leche, caseína and bechamel (PRO-332, whole word; «pisto manchego» and plant drinks «leche de coco/avena…» are not milk). A boot step (`applyNameAllergenTags`, `allergenBackfill.ts`) adds `lactosa` to the stored `ingredients.allergen_tags` of those names and to the stored `recipes.allergens` of every recipe that uses them, additive only, so Mimo and the lists that read the stored union agree with the ficha (on the 2026-10-23 staging catalogue: 4 recipes use one of those names, all already «leche» through «queso…»)
- `notes`, `tips`, `substitutions`, `storage` — long-form text, optional
- `advancePrep` — «preparativos con antelación» (PRO-220, migration `0077_recipe_advance_prep`): up to 5 `{ text, hoursBefore }` (3–140 chars, 0 < h ≤ 72), e.g. «Saca el filete del frigorífico» · 1,5; «Pon los garbanzos en remojo» · 10. Filled by Cocina (COC-12) through `POST`/`PUT /recipes`; a `PUT` without the field keeps what the recipe had (the edit form doesn't show it yet). On the detail payload when non-empty; copied by «Añadir a mis recetas». They become prep alerts without the household's prep habits — see [Notifications](./notifications.md)
- `nutritionPerServing` — cached object: `{ kcal, proteinG, carbsG, fatG, fiberG, saltG }`. Computed when the recipe is saved
- `nutritionIncomplete` — boolean (`recipes.nutrition_incomplete`, migration 0066, PRO-176): an ingredient that matters couldn't be counted (see [Nutrition](./nutrition.md) → Incomplete nutrition). Set on save and recomputed on every boot. The ficha then shows **no figures**: no «kcal por ración» in the desktop meta, and the Nutrición tab/block reads «Aún no podemos calcular la nutrición de esta receta.» (`NutritionUnavailable`). Test: `e2e/recipe-nutrition-incomplete.spec.ts` (390×844)
- `tags` — public-facing string array, normalized (no internal labels, no `meal`/`difficulty` duplicates)
- `internalTags` — string array hidden from public UI (e.g. `compartida`, `auto-extracted`, `from-url`, `tiempos-pro284`). A `PUT /recipes/:id` without the field keeps the recipe's (PRO-284; until 2026-10-21 every save from the edit form wiped them)
- `sourceUrl` — origin URL when imported from an article / YouTube video (null otherwise)
- `sourceType` — provenance enum: `manual | image | article | youtube` (null for legacy seeded rows)
- `sourceCredit` — read-only, detail payload only: where a catalogue recipe comes from, as the ficha shows it (D-067; `null` when there is nothing to credit)
- `authorId` — null for system, user id for user-created
- `ingredients` — list of recipe-ingredient rows (see below)
- `steps` — list of step rows (see below)

### RecipeIngredient

Each row:
- `ingredientId` — references the global ingredient catalog
- `ingredientName` — denormalized for display
- `section` — optional string for sub-grouping (e.g. "Para la masa", "Para la salsa"); `null` = ungrouped
- `quantity` — number
- `unit` — enum `g | ml | u | cda | cdita | pizca | al_gusto`
- `optional` — boolean. Editable from the recipe edit form (and the `/recipes/new` creation form) via an `opc` pill toggle next to each ingredient row. When true, the recipe detail renders an "opcional" badge inline and the shopping-list aggregator skips the row when scaling
- `note` — optional free text («en lomos», «picada»). Editable from `/recipes/new` and `/recipes/[id]/edit`: each ingredient row has a «Nota (opcional)» field under quantity/unit (max 200 characters, trimmed; emptying it clears the note on save, PRO-109). The detail shows it next to the ingredient. Tests: `recipeFormContract.test.ts`, `e2e/recipe-ingredient-note.spec.ts`

### Meal & season fit (3-state)

Recipes carry **three-state fit maps** for meals and seasons next to the legacy on/off arrays:

- `mealFit: { breakfast?, lunch?, dinner?, snack? }` — each entry is `'mid'` (encaja a veces) or `'perfect'` (encaja perfecto). Absent key = `'none'`.
- `seasonFit: { spring?, summer?, autumn?, winter? }` — same shape.

The recipe edit / create form exposes these via a single chip that cycles **vacío → mid → perfect → vacío** on tap. Visual progression: outline (none) → soft fill (mid, with a centered `·`) → solid fill + `★` (perfect). Ink palette for meals, forest palette for seasons.

The menu generator's matcher honours both:
- **Filter**: a slot is eligible only when the recipe's fit for that meal/season is `'mid'` or `'perfect'`. `'none'` excludes the recipe entirely.
- **Pool weighting**: `pickRandom` multiplies by `FIT_WEIGHT` (`mid = 1×`, `perfect = 3×`) for the meal AND for the season, then by `2×` if the recipe is a household favourite. A perfect/perfect favourite weighs `18×` against a mid/mid non-favourite at `1×`.

Stored as parallel `recipes.meal_fit` / `recipes.season_fit` jsonb columns (migration 0024). The `meals: text[]` / `seasons: text[]` arrays stay in sync as a derived view so the public catalogue endpoint and the assistant skills keep their existing shape. Legacy recipes saved before the migration have `NULL` in the fit columns — the read layer falls back to deriving `'perfect'` for every entry in the array tagging so old recipes keep their pre-fit semantics.

### Scheduling frequency hint

Each recipe carries an optional `frequency` enum (`recipes.frequency`, migration 0026) that drives how often the menu matcher picks it:

- **Normal** (default; `NULL` in DB) — baseline weight 1×.
- **Frecuente** (`frequent`) — pool weight ×2. Same magnitude as the favourite boost; the two compose multiplicatively.
- **Ocasional** (`occasional`) — pool weight ×0.4. Still selectable when the matcher has no better option (floor of 1 entry in the pool), just rare.
- **Solo finde** (`weekends_only`) — **hard filter**: the recipe is excluded from any Mon-Fri slot (`dayIndex < 5`). On Saturday / Sunday it enters the pool with weight 1×.

The edit form exposes four mutually-exclusive chips under "Planificación"; "Normal" is the default state that maps to a NULL column. Persisted via `createRecipeSchema.frequency` (zod `nullable().optional()`); the DB CHECK constraint clamps writes to the canonical enum.
- `note` — optional inline note (e.g. "picada fina", "del día anterior")
- `displayOrder` — integer, controls UI ordering inside its section

### Step

Each row:
- `index` — integer, position in the recipe (0-based)
- `text` — required, the instruction sentence
- `durationMin` — optional integer, time the step itself takes
- `temperature` — optional integer °C (oven, pan, water bath…)
- `technique` — optional short label ("sofreír", "hornear", "marinar")
- `ingredientRefs` — array of `recipeIngredientId`s used in this step (used to render quantities inline and for cooking-mode highlighting)

## Tag Visibility

The catalog and detail view display only **public** tags. Filtering rules:
- Any tag in `internalTags` is excluded
- Tags that duplicate the `meal`, `season`, or `difficulty` fields are excluded (no more "compartida · easy · lunch" leaking)
- All tags are normalized to the user's display language (Spanish)

## Quantity Scaling

When the user changes the diner count from `recipe.servings` to `target`:
- Each ingredient `quantity` is multiplied by `target / recipe.servings`
- Counted units (`u`) round to the nearest whole; if the result is non-integer, the UI shows a small note (e.g. "1.5 huevos → redondea a 2")
- `pizca` and `al_gusto` never scale
- **The note's countable amount scales too** (PRO-184, Laura 2026-10-16: «Para 1 ración · Ajo · 6 dientes, laminados · 6 g»): when an ingredient's note starts with a number and a unit you count (diente, hoja, rama, ramita, hebra, rodaja, loncha, trozo, tira, cabeza, vaina, guindilla, cayena, pieza, unidad, bola, gajo, tallo, manojo — singular or plural), that number is multiplied by the same factor and rounded to halves, never below ½, with singular/plural fixed («6 dientes, laminados» for 4 → «1½ dientes, laminados» for 1; «2 hojas» → «½ hoja»). Any other note («laminados», «200 g de…», «2 latas») is shown as written. Done in `scaleRecipe` (`?servings=N`) with `scaleIngredientNote` (`@ona/shared`), so the detail and cooking mode show it (`ingredientNoteScaling.test.ts`, `e2e/recipe-note-servings.spec.ts`). Mimo's «la herramienta de raciones me devolvió otra receta» is PRO-183
- Mass and volume units round to a culinary-friendly precision (1 g, 5 g, 25 g, 50 g bands depending on magnitude)
- Step text references via `ingredientRefs` are recomputed at the same scale

## Display Constraints

- A `prepTime` of `0` (or any falsy value) is **not** rendered on cards or detail meta — instead, the field is omitted entirely (fixes the prior "0" leak). Cards show `recipeMinutes` (total time, else prep time). **Season rule**: "now" is `detectSeason(date)` — meteorological seasons for Spain (Sep–Nov otoño, Dec–Feb invierno…), browser-local month, the same rule as the menu generator. A season is never derived from the order of `recipe.seasons` (until 2026-10-08 cards showed `seasons[0]`: "Primavera" on every all-year recipe in October). Catalogue cards (signed in and out) show no season. Guarded by `catalogSeason.test.ts`
- All meal/season labels go through `MEAL_LABELS` / `SEASON_LABELS` before render (no raw `lunch`/`dinner` in the UI)
- Spanish copy uses correct accents (Otoño, Año, Añadir, Preparación) — no mojibake fallbacks
- The detail view groups ingredients by `section` if any ingredient has one set; otherwise renders a flat list
- The "Para X" caption next to the ingredients title reflects the live scaler value, not a hardcoded number

## Course classification (`recipes.course`)

Optional enum tagging the recipe's role in a multi-dish meal: `'starter' | 'main' | 'dessert' | null`. Spanish labels via `COURSE_LABELS` in `@ona/shared` (`Entrante / Principal / Postre`).

`null` means "versatile" — the menu generator treats null-tagged recipes as valid stand-alone dishes for single-dish slots. The matcher uses this field when a slot is configured with 2 or 3 dishes (see [`menus.md`](./menus.md) "Multi-dish slots").

Population:
- Seed catalogue + existing user recipes: one-shot LLM script `pnpm --filter @ona/api course:populate` (→ JSONL → optional manual review → `course:apply`). Same two-step pattern as `prep-requirements:populate`. Source: `apps/api/scripts/populateRecipeCourses.ts`.
- New recipes: optional dropdown in `/recipes/new` and `/recipes/[id]/edit` (defaults to "Sin clasificar (auto)" = `null`).

## API Endpoints

- `GET /recipes?search=&meal=&season=&maxTime=&perPage=&page=&fitsMe=1&mine=1` — list with filters; returns the lightweight card shape. `mine=1` (PRO-299) keeps only the caller's own recipes (anonymous: none). `fitsMe=1` (authenticated only; ignored anonymously) hides recipes that break the caller's allergies or diet (profile + memory, same rules as the menu generator; dislikes not applied) — used by the menu's «Elegir otra receta» picker (PRO-61). **Optional auth:** with a valid Bearer token the response is the system catalogue + the caller's own recipes (other users' recipes are never listed; a personal copy hides the system original it was copied from); without a token only system recipes (`authorId IS NULL`) are returned, so the same endpoint backs `/recipes` both as the public catalogue (anonymous) and as the app list (authenticated).
- `GET /recipes/with-what-i-have?ingredient=<id>[&ingredient=<id>…]` (auth) — «Con lo que tengo»: 1–3 catalogue ingredient ids (400 with none or more than 3) → card shape + `uses` (chosen names the recipe uses) + `missing` (required non-basic ingredients not chosen), ranked; at most 100. Service: `services/withWhatIHave.ts`
- `GET /recipes/:id?servings=N` — single recipe; if `servings` is provided and differs from `recipe.servings`, quantities are scaled server-side and a `scaledFrom` field is included. Carries `sourceCredit` (string or `null`, D-067) and never `catalog_source`. Anonymous callers can only fetch system recipes; requesting a user-authored recipe without a token returns 404 (same shape as "not found" to avoid leaking which IDs exist privately). **An id that isn't a uuid** (`/recipes/no-es-un-id`, a cut link) is the same 404 `Recipe not found` on every `/recipes/:id...` route of `routes/recipes.ts` (GET, PUT, DELETE, copy, regenerate-image, upload-image, favorite), answered by `requireRecipeId` (`middleware/recipeId.ts`) before the database, so nothing is logged as an error (PRO-181; before, Postgres rejected the uuid cast → 500). Notes, photos and cookbook routes already answered 400/404 for it. Test: `recipeIdGuard.test.ts`.
- `POST /recipes` (auth) — create user recipe; runs lint validator
- `PUT /recipes/:id` (auth, author only) — update; runs lint validator and recomputes `nutritionPerServing` and `allergens`
- `DELETE /recipes/:id` (auth, author only)
- `GET /user/:id/recipes` (auth) — user's own + favorited recipes
- `POST /user/:id/recipes/:recipeId/favorite` (auth) — toggle favorite. **PR 1B:** each user toggles their own `user_favorites` row, but `GET /user/:id/recipes` returns the household-wide union of favorites when `SHARED_HOUSEHOLD_SCOPE` is on. See [Household](./household.md)
- `POST /recipes/:id/copy` (auth) — clone a recipe into the caller's catalog. Refuses with 409 if the user already owns the source. Returns the new recipe

## Constraints

- `name` and `servings` are required; everything else is optional but `difficulty` defaults to `medium` if absent
- Saving a recipe **fails** if the lint validator finds issues (see [Recipe Quality](./recipe-quality.md))
- `nutritionPerServing` and `allergens` are recomputed automatically on every recipe save — never edited by hand
- **Ingredient names on screen (detail, shopping list, pantry, staples)** read as a sentence — «Aceite de oliva virgen», «Pimentón dulce» — via `ingredientDisplayName` (`packages/shared/src/utils/shopFormat.ts`): only the first letter is raised and catalogue accents are restored; brands/acronyms the user typed («Kerrygold», «AOVE») stay. Display-only; stored names are untouched (PRO-02).
- `totalTime` is read-only on the client; clients can edit `prepTime`/`cookTime`/`activeTime`
- Schema migration is destructive (wipe + reseed acceptable; no production data preservation requirement)
- **Drafts** (PRO-154): `visibleRecipeWhere` also requires `status = 'published'`, so every path below skips catalogue drafts; `GET /recipes` filters it explicitly; `GET /recipes/:id` and `POST /recipes/:id/copy` answer 404 for a draft unless the caller is an admin
- **Recipe visibility** (`services/recipeVisibility.ts`): a user can see, be served, or have Mimoia pick the system catalogue (`authorId IS NULL`) + their own recipes + recipes authored by members of their primary household. Another user's private recipe never reaches them through the menu generator, slot regeneration, manual slot pick (`404`), cook-from-pantry, the nutrition advisor or any assistant skill (web chat + WhatsApp). `GET /recipes/:id` returns `404` for an invisible recipe. Before 2026-10-07 the generator and the assistant loaded the whole `recipes` table. Guarded by `recipeVisibilityCoverage.test.ts` (no unscoped read of `recipes` in those files)
- Structured **ingredient overrides** (`recipe_notes.ingredient_overrides`) flow through to the shopping list and the recipe detail, but the *menu generator/matcher* still scores recipes against their original ingredient list. So a household that "removes cebolla" from every recipe will still see the same recipes get selected by the planner — they just won't see cebolla on the recipe detail or in the basket
