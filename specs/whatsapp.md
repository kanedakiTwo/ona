# WhatsApp

Talk to **Mimo**, Mimoia's assistant, from WhatsApp (the bot speaks as Mimo / Mimoia since the 2026-10-08 rename; the old project name stays only in identifiers: env var names and Meta template names such as `ona_aviso`, which are registered in Meta and don't change). WhatsApp is another way to reach the same assistant as Mimo in the app, with the same skills, user memory and monthly € budget, through Meta's WhatsApp Cloud API. Since 2026-10-14 Mimo answers from a real number, **+34 626 68 55 11** (display name «mimoia», the spoon-and-heart logo as profile photo), on Mimoia's own Meta app; who can use it is still limited by `WHATSAPP_ALLOWED_EMAILS`. Before that, v1 ran on Meta's test number (+1 555 183 2642, at most 5 verified recipients, shown as «Test Number») under a Meta app that wasn't Mimoia's.

- [La semana en el chat](./whatsapp-semana.md) — «tu menú está listo», la semana en una imagen, el acierto, la invitación en la semana reenviada, la lista en el chat, varias peticiones en un mensaje, cada respuesta a su pregunta y los «me pongo con ello».
- [Avisos, quién cocina hoy y la pregunta única](./whatsapp-avisos.md) — los mensajes proactivos (guías, comprobación, pausas, idioma, esperas, interruptores, plantillas), «hoy cocina Pablo» y la pregunta única de Admin.
- [Cómo se tratan los mensajes y el revisor de conversaciones](./whatsapp-mensajes.md) — el manejo de cada mensaje que llega y el agente que revisa las conversaciones cada día.

## Linking

- The code has 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I) and always contains at least one digit, so an ordinary 6-letter word is never mistaken for a code. It expires after 10 minutes and works once. Generating a new code invalidates the user's previous unused one.
- Sending a valid code links `phone ↔ user` one-to-one:
  - If the phone was linked to another account, the link moves to the new owner.
  - If the user had another phone linked, the old phone is replaced.
  - Messages the phone sent before linking are assigned to the new owner.
- Phones are stored as Meta's `wa_id`: digits only, with the country code.

## Data model

- `whatsapp_links(user_id UNIQUE, phone UNIQUE, profile_name, notify, prefs jsonb, linked_at, last_inbound_at)`. `last_inbound_at` marks the start of Meta's 24 h customer-service window.
- `whatsapp_link_codes(code PK, user_id, expires_at, used_at)`: used by both the profile card and `/whatsapp/conectar`.
- `whatsapp_messages(wamid UNIQUE NULL, phone, user_id, direction in|out, kind, body, status, error_message)`.
  - Inbound statuses: `received` / `processed` / `failed` / `ignored`.
  - Outbound statuses: `sent` / `failed`.
  - Outbound kinds `system` (budget, linked, errors), `link` (how to connect) and `ack` ("me pongo con ello") are left out of chat history. `image_failed`: a week picture whose send failed and whose text went out instead (status `failed`, also out of history).
- `whatsapp_questions(id, text UNIQUE, created_by, created_at)` and `whatsapp_question_sends(question_id, household_id, user_id, phone, status sent|failed, error_message, sent_at, answered_at; UNIQUE(question_id, household_id))`: the Admin «pregunta única» (PRO-1091, migration `0102_whatsapp_questions`, additive).
- Migration `0030_whatsapp.sql`, which only creates new tables and is idempotent. `users.whatsapp_nudge_at` (migration `0052_whatsapp_nudge.sql`, additive): when the reminder card was shown.

## API

- `GET /whatsapp/webhook` (public): Meta's verification handshake. It echoes `hub.challenge` when `hub.verify_token` matches `WHATSAPP_VERIFY_TOKEN`; otherwise **403**.
- `POST /whatsapp/webhook` (public, signed): **503** when the channel isn't configured.
- `GET /whatsapp/status` (auth): `{ available, linked, nudge, phone, notify, prefs, chatLink }`. `nudge` = show the one reminder card on `/menu` (PRO-107, rule in `services/whatsapp/nudge.ts`). `available` = configured AND email allowed. The profile card is hidden unless `available || linked`, so a user can always disconnect.
- `POST /whatsapp/nudge/seen` (auth): the reminder card was shown; stamps `users.whatsapp_nudge_at` once (keeps the first date). **204**.
- `POST /whatsapp/link-code` (auth): `{ code, expiresAt, message, waLink }`. **403** `WHATSAPP_UNAVAILABLE` when not available.
- `PATCH /whatsapp/link` (auth) `{ notify?: boolean, prefs?: { <kind>: boolean } }`: **404** when not linked.
- `DELETE /whatsapp/link` (auth): **204**.

## Configuration (`ona-api`)

- Required: `WHATSAPP_ACCESS_TOKEN` (permanent System User token with `whatsapp_business_messaging`), `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`.
- Recommended: `WHATSAPP_DISPLAY_NUMBER` (the sender's number as digits, for `wa.me` links), `WHATSAPP_ALLOWED_EMAILS` (comma-separated account emails; empty means everyone), `WEB_PUBLIC_URL` (base for deep links; defaults to the Railway web URL; prod sets `https://mimoia.com` since 2026-10-07 — links sent earlier keep working on the Railway URL).
- `SUPPORT_EMAIL`: the human contact shown for HUMANO and in the suspended copy. Unset → "escribe a hola@mimoia.com" (`BRAND_SUPPORT_EMAIL`, the same address as the footer and Mimo; PRO-179).
- Optional: `WHATSAPP_TEMPLATES` — JSON map *kind → approved template* (`daily_brief`, `weekly_nudge`, `cooking_reminder`, `dinner_checkin`, `shopping_reminder`, `alert`, `review`; and `pregunta_unica`, used only by the Admin question — see *Pregunta única por WhatsApp*), preferred over the generic one (Meta reviews templates per use; one generic `{{1}}` wrapper for everything is what its policy discourages). Malformed JSON is ignored with a warning. `WHATSAPP_TEMPLATE_NAME` + `WHATSAPP_TEMPLATE_LANG` (generic fallback for proactive messages outside the 24 h window; template body must have one `{{1}}` and not start or end with it, e.g. "Aviso de Mimoia: {{1}} Respóndeme por aquí si quieres cambiar algo." — the template *body* is registered in Meta, so templates approved with the old name in their text keep saying it until they're re-submitted), `WHATSAPP_GRAPH_VERSION` (default `v26.0`) and `WHATSAPP_GRAPH_BASE_URL`, which local E2E points at a mock server.
- Meta dashboard webhook: `https://ona-api-production.up.railway.app/whatsapp/webhook`, subscribed to the `messages` field.

## Constraints

- **No health data over WhatsApp** (LEG-03, Meta's terms 4.2; PRO-24): allergies, intolerances, restrictions and physical data are never stored from a WhatsApp conversation, with or without the health-data consent. The engine passes `channel: 'whatsapp'` in the skill context; `update_profile` and `update_memory` drop those fields and reply «Por WhatsApp no guardo datos de salud… Añádelos en tu perfil de la web: <WEB_PUBLIC_URL>/profile» (other changes in the same message still apply), and the WhatsApp prompt tells the model so. Restrictions already saved from the web are still respected. Telegram turns run in this same mode, so the rule holds there too ([Telegram](./telegram.md)). Test `whatsappHealthData.test.ts`
- **An allergy said and not saved still shapes the menu** (PRO-1041, Seguridad; also in the web chat without the consent). Test households 2026-10-24 → 31: «soy celíaca», «alérgico al marisco», «alergia a frutos secos» in the first message; the first menus brought them and only Mimo's manual check took them out (on 2026-10-28 it failed: «caldo de pollo» for a vegetarian). Now: when the allergy is the reason something isn't saved, `update_profile` and `update_memory` reply with the link to «Tus alergias y tu dieta» with it marked (`saidAllergyReply`, [Household](./household.md)), and `generate_weekly_menu` and `complete_onboarding` apply, **for that menu only and without storing it**, what Mimo passes in `restrictions_said` plus the allergens named in the person's own messages of the last 30 days (WhatsApp inbound by the linked phone; earlier web-chat turns), by the fridge reader's keyword rule plus «sin gluten» / «sin lactosa» (`services/saidRestrictions.ts`), minus what anyone in the household has saved. They ride on the generation's async call (`withMenuOnlyRestrictions`, `services/menuOnlyRestrictions.ts`) and `withHouseholdRestrictions` adds them to every pick inside it. The tool tells Mimo «Aplicado solo a este menu (no esta guardado): sin gluten…» with the link to send; the prompts tell it to pass them and never to refuse the menu over it. **In the WhatsApp sign-up**, with its dishes of 2026-11-19: a dish they make often never comes in as a recipe with what someone at home can't eat, said to Mimo or saved (`signupDishes`, `assistant/skills.ts`, the generator's own list). It is left out, not even as a note (`swap_meal` by name would bring that same recipe back), and the tool tells Mimo «No he puesto «macarrones con tomate»: su receta lleva algo que en casa no pueden comer…» to say so in a line; when a dish the catalogue doesn't have goes in as a note, the tool adds that the household's recipe Mimo writes for it can't have it either. The sign-up's one closing message carries one more line, the link (`signupReply.ts` doesn't count the «?» of a link as a question, so it isn't dropped with the extra questions; `WHATSAPP_ONBOARDING_PROMPT` says where it goes). Diets that aren't health data (vegetarian) are not covered here (PRO-1053, PRO-1082). Tests `saidRestrictions.test.ts`, `assistant-skills.test.ts`, `firstMenuWhatsApp.test.ts` and `whatsappInbound.test.ts` (the sign-up), smoke `saidAllergies.smoke.ts` («soy celíaca» by WhatsApp, no consent: first menu without gluten, `restrictions: []`, `healthConsentAt: null`)
- **AI disclosure (EU AI Act art. 50):** both first messages Mimo can send in a conversation — the unlinked "Hola, soy Mimo, el asistente de cocina de Mimoia…" hint and the "¡Listo!" after linking — include "Soy un asistente de inteligencia artificial (IA): puedo equivocarme y no sustituyo a un profesional sanitario." (`AI_DISCLOSURE_FIRST_PERSON` in `@ona/shared`). Pinned by `whatsappInbound.test.ts`.
  - **Messages Mimo sends on its own (PRO-1169, LEG-34):** inside the 24 h window every proactive message (`sendProactive`: avisos, prep alerts, «hoy cocina X», the founder offer, the daily review) ends with the fixed line «— Mimo, asistente con IA» (`AI_SIGNATURE`), added by the code after the text is written (`withAiSignature`, `services/whatsapp/aiNotice.ts`; as its own message when a button body or caption would go over Meta's limit). It is stripped from the history the model and the guide writer see (`stripAiSignature`), so they never copy it. Outside the window the template carries it in its footer, «Mimo, asistente con IA. Responde BAJA para no recibir avisos» (60 characters, `AI_TEMPLATE_FOOTER`), registered by hand in WhatsApp Manager (MIG-05), not by the code.
  - **Back after 30 days (PRO-1169):** when a linked number writes after 30 days or more without writing (`whatsapp_links.last_inbound_at`, read before it's updated), Mimo's first message of that turn starts with `AI_DISCLOSURE_FIRST_PERSON` (`withReturnDisclosure`). Tests: `aiDisclosureMimo.test.ts`.
- No WhatsApp groups. Signing up happens on the web (the connect link offers "Crear cuenta"), not inside the chat.
- The business isn't verified (D-004): the display name may show as the number until Meta approves it, and business-initiated conversations are capped at 250 a day. Business verification lifts the cap and is needed before opening the channel widely.
- In-process queue: if the API restarts mid-turn, that message stays `received` and gets no answer (no sweeper; messages older than 2 h are dropped as stale anyway).
- Every turn checks the chat's € budget **and** the monthly cap on all paid AI work (`USER_MONTHLY_SPEND_CAP_EUR`, see [Advisor](./advisor.md)) before any paid step. Every paid call is recorded in the cost ledger ([Metrics](./metrics.md)), including each template message (`meta_whatsapp/utility_template`) and, since 2026-10-15, every free-form message Mimo sends (`meta_whatsapp/service_message`, feature `whatsapp_service`): Meta bills these from the 1,001st of the month per number, so the first 1,000 are recorded at 0 € and the rest at €0.0166 (`services/whatsapp/serviceCost.ts`).
- "Today" and "this week" use the Europe/Madrid clock (`services/madridTime.ts`), for the assistant's `get_todays_menu` / `generate_weekly_menu` and for the daily brief.
- **Week picture rendering** runs in the API with no browser: `satori` (layout → SVG, flexbox only) + `@resvg/resvg-js` (SVG → PNG) + `sharp` (photo crops, JPG q85). Fonts (Fraunces, Cormorant Garamond italic, Inter; SIL OFL) and the meal icons (Noto Emoji PNGs, Apache-2.0) and logo are bundled in `apps/api/assets/` (licences in `assets/NOTICE.txt`); nothing is cached. Recipe photos are fetched per send (`image_url`; relative catalogue paths resolved against `WEB_PUBLIC_URL`), 2.5 s timeout and 6 MB cap each, 8 at a time; a photo that fails becomes a tile, never a failed picture. About 1 s to draw (measured locally) plus the photo downloads.
- The model sees text only: photos are never shown to the chat model, they go straight to recipe import (a photo of the fridge is not understood yet). Cooking-mode hints (`set_timer`, `cooking_step`) have no effect on WhatsApp; the reply points to the app instead.
